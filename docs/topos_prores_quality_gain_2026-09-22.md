# TOPOS 画质追平 ProRes 攻坚报告（2026-09-22）

> 起点：用户反馈「TOPOS 422 proxy 与 ProRes 422 Proxy 直观差距明显——能看到压缩
> 小色块，边缘锯齿感更强；希望在体积与编解码速度不变的前提下提升画质」。
> 本文给出同源实测、根因定位、落地改动与**未解决项**。

---

## 0. 结论速览

1. **码流本身不是主因。** 同输入同量级码率对照下，TOPOS 的 PSNR/边缘 PSNR/
   高频保留**全面不劣于** ProRes，唯一确定的编码器级差距是**块界台阶**
   （TOPOS 为 ProRes 的 4.3 倍）——本轮已修掉。
2. **"ProRes 更锐"是语料构造假象。** 语料 ProRes 是 Apple 自家缩放器喂出来的
   （高频保留 1.431）；换成与 TOPOS 逐位相同的输入后，ProRes 的高频保留只有
   **0.737**，低于 TOPOS 的 0.837——而它用的码率还高 37%。
3. **观感差距的主要嫌疑在预览渲染路径，不在编解码器。** TOPOS 10-bit 平面走
   R16UI **整数纹理 → GL_NEAREST 点采样**，ProRes（macOS VideoToolbox）走
   IOSurface → **GL_LINEAR 双线性**；两者都在 YUV→RGB pass 内做视口缩放，
   非整数倍缩放时点采样**同时**产生小色块与边缘锯齿。详见 §4。
4. **顺带修掉两个产品级 bug**：422 10-bit 的**目标体积导出在首帧直接失败**
   （P6 引入）；以及 `ToposMediaSource.open()` 的 `UnboundLocalError` 掩盖真实
   打开错误。
5. **v2.1（同日晚续批）修掉一个致命门控 bug**：v2 门控用无符号比较代替取幅值，
   而该等价式只在 `q0 > p0` 时成立 → **只有单向台阶被滤**。反向台阶占帧内台阶
   能量 53.4%，也就是"块效应只降了一半"。修复后 4K proxy 块界台阶
   1.035/1.371 → **0.037/0.074** LSB，Y PSNR 不降反升（§3.4）。
6. **P6 去块的解码开销已偿还**：滤波曾是帧级串行段（16 线程只快 2.45×）；v2.1
   把两趟按"访问窗口不相交"切进常驻线程池 → 线程扩展回到 6.1–6.9×，2K proxy
   16 线程 **300 fps**、4K proxy **85 fps**（均为含滤波的产品实测）。滤波本身仍
   占 ~45% 解码时间（§5）——这是下一批 SIMD 的明确目标。
7. **预览路径（缩放交付）此前完全不过滤**：`r->scaled != 0` 把滤波整个跳过，
   而 4K 源在预览里正是走 1/2 抽样 —— 这是"4K 预览能看到小色块"的直接来源。
   v2.1 在**目标网格**（1/2 抽样 → 周期 4）补上滤波：4K proxy 预览块界台阶
   1.402/1.337 → **−0.230/−0.373** LSB（§3.5）。

## 2. 编码器级真实差距：块界台阶

- 测得 TOPOS 块界台阶 2.19/2.00 LSB（10-bit），ProRes 同输入 0.51/0.50——**4.3×**。
  这是唯一在公平对照下稳定成立的编码器级差距，也正是"小色块"的物理对应物。
- 此前的 `blockiness` 度量曾把"块界台阶"与"块内差分"的判平坦阈值设在同一点，
  导致**把要测的台阶本身滤掉**（合成自检才发现）；改为**用参照图判平坦**后
  才得到可用数字。工具：`tools/panel_topos_blockiness.py`（含误差放大图）。

## 3. 本轮落地的改动

### 3.1 去块滤波器 v2（`native/topos_codec/src/codec/deblock.c`）

三处都是**代码级修正**，不是调参：

| 问题 | 现象/证据 | 修正 |
| --- | --- | --- |
| 水平边界**抽头几何错误**：p1/q1 取了"同一行内相邻列"（pu[x−1]/qu[x+1]），而跨水平边界的正确样本序列是"**同一列相邻行**" | 校正方向虽对，但"台阶 vs 斜坡"判别用了与边界无关的横向抽头；A/B 显示 block_h 已归零而 block_v 仍停 1.2–1.5 | 改用 pu2[x]/qu2[x]（上上行/下下行），单测 `test_horizontal_step` 钉死 |
| 弱滤波权重台阶响应只有 3Δ/16 ≈ 19% | 平坦邻域纯 DC 台阶下只抹掉 44% | 由两个不变式联解 W1=4、W0=12：**纯台阶响应 Δ/2（整段抹平）、均匀斜坡响应严格 0**。v1 的 (4,1) 同构但响应过弱 |
| 无输出钳位 | p0=1023 时 p0+d 可写出 >1023 的越界样本 | 增 `bit_depth` 参数，结果钳到 [0, 2^bd−1]，单测 `test_bit_depth_clamp` |

另补一条**中点上界**：|d| ≤ |Δ|/2 且 sign(d)=sign(Δ)，即校正不得越过 p0/q0 的
中点。纯台阶下 (12,4) 恰给 Δ/2，但在**振铃/过冲**邻域（p1−q1 与 Δ 同号——线条
边缘经 DCT 量化后极常见）权重和会让 d 超过 Δ，把台阶**翻到另一侧**（幅度不减、
位置互换）。加上界后 block_h 均值由 2.1802 降到 2.0802。

**性能**：滤波从"逐边界 × 8 行跨 stride 遍历"改为"垂直方向逐行扫描 + 水平方向
整行平坦扫描"（无 8 对齐掩码、无无效位置、可向量化），强度（含一次整数除法）
从每条边界一次提到每平面一次。2K proxy 解码中位数 5 轮：旧 v1 **166.0 fps** →
新 v2 **164.8 fps**（−0.7%）。

> ⚠ 本节的 A/B 表与逐帧数字都是**门控 bug 未修**时测的（见 §3.4）：那时只有
> 单向台阶被滤，所以"台阶降幅"被系统性低估、"高细节帧持平"也含此因。门控
> 修复后的实数见 §3.4/§5；本节保留原值仅作 v1→v2 的演进记录。
> 原文另称"门控用无符号比较替代 `abs()`（每点省 3 条指令）"——**该写法是错的**，
> 已在 v2.1 改回取幅值。

**效果（单库进程内，同码流）**：

| 指标 | 旧 v1 | 新 v2 | Δ |
| --- | ---: | ---: | ---: |
| block_h（均值） | 2.1848 | **2.0802** | −0.105 |
| block_v（均值） | 2.0024 | 2.4546 | +0.452 ※ |
| Y PSNR | 38.7713 | 38.7104 | −0.061 dB |
| 边缘 PSNR | 35.1763 | 35.1697 | −0.007 dB |
| 高频保留 | 0.8373 | 0.8384 | +0.001 |

逐帧 block_h：1.01→1.01 / 0.85→**0.75** / 2.27→**2.04** / 2.91→**2.73** / 3.88→3.87
——**平滑帧全面改善，高细节帧持平**。

※ block_v 的"回退"是**统计噪声**：该指标只在参照图平坦处取样，而帧 240/300

### 3.2 产品级 bug 修复

- **422 10-bit 目标体积导出首帧直接失败**（P6 引入）：
  `ToposVideoEncoder._probe_budget_and_open_mux` 的探测配置把 `reserved[0]` 钉成 0
  （T1.5 历史口径）却留下 `reserved[5]`（P6 输出特性）——该槽仅在 em=8 下合法，
  native 域校验按 `reserved[0]` 分支 → 整个 sized 探测被拒。
  修复：探测配置一并清零 `reserved[5]`。验证 `tests/media/test_topos_export.py`
  135 项全过（修复前 4 档 422 全部失败）。
- **`ToposMediaSource.open()` 的 `UnboundLocalError`**：函数内重复
  `from ... import ToposCodecError` 使整个函数体的同名引用变成局部名，前面的
  `except ToposCodecError` 在缺文件等路径上抛 `UnboundLocalError`，掩盖真实错误。
  修复：删除重复导入，用模块级符号。

### 3.4 v2.1：门控对称性 + 两趟并行（本批）

**门控 bug（决定性）**。v2 的门控写成

```c
return ((uint32_t)(q0 - p0) < (uint32_t)alpha) && ...;   /* 注释："|v| < t 的等价式" */
```

`|v| < t ⟺ (uint32_t)v < (uint32_t)t` **只在 v ≥ 0 时成立**：负差转无符号是巨值、
比较必然失败。于是门控退化成"只滤 `q0 > p0` 一侧"——同一幅度、同一 qp，左高右低
的台阶原样保留。合成探针一眼可见：400→404 被滤成 (401,402,402,403)，404→400
**一个像素都没动**。真帧统计：4K proxy 反向台阶占边界 45.2%、占帧内台阶能量
53.4%。修复即取幅值后比较（`db_absu`），新增单测 `test_gate_sign_symmetry`
（已验证：对旧门控必然失败，失败信息就是四个采样点全数未变）。

**效果（同一码流、只换库；12 个交付档，5 帧均值）**：

| 文件 | block_h 前→后 | block_v 前→后 | Y PSNR 前→后 |
| --- | ---: | ---: | ---: |
| 2K proxy | 2.674 → **−0.245** | 3.233 → **−0.761** | 37.945 → 38.036 |
| 2K lt | 1.816 → **0.039** | 2.164 → **−0.012** | 41.986 → 42.032 |
| 2K standard | 1.553 → 0.535 | 1.861 → 0.735 | 45.178 → 45.182 |
| 2K hq | 1.174 → 0.321 | 0.631 → −0.115 | 46.455 → 46.453 |
| 4K proxy | 1.035 → **0.037** | 1.371 → **0.074** | 41.977 → 42.041 |
| 4K lt | 0.936 → 0.267 | 1.120 → 0.275 | 47.094 → 47.090 |
| 4K standard | 0.654 → 0.281 | 0.694 → 0.277 | 53.352 → 53.323 |
| 4K hq | 0.414 → 0.256 | 0.406 → 0.225 | 59.748 → 59.667 |

（4:4:4 的 4444/4444_XQ 四档**不带宽高比位**、本就不去块，前后逐位相同，未列。
其 PSNR 列不可用：对照台按 `yuv422p10le` 参照取样，12-bit 流会得到无意义的负值。）

**两趟并行**。滤波此前是整帧唯一的串行段（16 线程只快 2.45×）。并行化的依据
不是近似而是**访问窗口不相交**：垂直趟按行带切分；水平趟的每条边界行 y0 只读写
`{y0−2..y0+1}`，相邻边界行相隔 unit ≥ 4 ⇒ 窗口两两不相交。两次
`tc_parallel_for` 之间天然构成"垂直完成 → 水平开始"的屏障，故**任意线程数输出
逐位一致**（单测 `par_eq_serial(8/4)` + 帧级 SHA-256 复验，见 §5）。

> 副产品发现：原并行单测的内容用 ±128 的 8×8 棋盘（远超 alpha=18），门控全灭，
> 用例一直是**恒等通过**——新加的"滤波确实落了像素"断言把它抓了出来（`git log`
> 里该用例从未失败过）。

### 3.5 v2.1：缩放交付（预览路径）补滤波

缩放交付是"每格取首样本"的整数抽样（`codec.c` slice 任务的 `dst_w/dh`），源
8×8 块界在目标域落到 `8/d` 的倍数上（1/2 抽样 → 每 4 个目标像素一条块界）。
此前 `r->scaled != 0` 直接跳过滤波，于是 **4K 源在预览里（1/2 抽样）完全没滤波**
——这是"预览里能看到小色块"的直接来源，也是此前把观感差距归因于采样器（§4）
之外被漏掉的一环。

做法：把滤波器按**目标域周期** parameterize（`tc_deblock_plane_scaled(..., unit)`，
unit = 8/d），在目标网格上重放同一套 (12,4) 权重与同一个 alpha/beta——抽样是
DC 保持的，台阶幅度不随抽样改变，故强度推导无需改。只认 d = 2（unit = 4）：

| 4K 预览（1920×1080） | block_h | block_v | Y PSNR |
| --- | ---: | ---: | ---: |
| 改前：HALF 解码（不过滤） | +1.402 | +1.337 | 38.926 |
| 改后：HALF 解码（目标域滤波） | **−0.230** | **−0.373** | 38.927 |
| 参照上界：全尺寸滤波后 1/2 抽样 | +0.176 | +0.092 | 39.107 |

**这不是"源域滤波后抽样"的逐位等价物**：抽样丢掉的 p0/q1 校正无法在目标域
复现，所以它比理想上界略偏平滑（block 值更负），是**预览级近似**（把目标图当作
周期 4 的合法图像过滤）。交付路径（全尺寸）不受影响（逐位不变）。d = 3（如
6K→2048 的 1/3）网格非整数、相位逐块漂移，d ≥ 4 时边界窗口重叠（并行等价性
不成立），二者保持不过滤——归后续批次。

## 4. 观感差距的主因：预览路径采样器不一致（未修，待决）

子代理只读调研（证据均带 文件:行号）：

| | TOPOS | ProRes |
| --- | --- | --- |
| 解码 | 自研 native → CPU uint16 planar | macOS VideoToolbox → CVPixelBuffer/IOSurface（零拷贝） |
| GPU 纹理 | `YUVGPUUploader` → **R16UI 整数纹理，filter = (NEAREST, NEAREST)** | CGLTexImageIOSurface2D → **GL_LINEAR** |
| 缩放到视口 | 在 YUV→RGB pass 的纹理采样中完成（**点采样**） | 同一步，但**双线性** |

- `src/shared/video/yuv_gpu_upload.py:735-739` — "Create R16UI pool with NEAREST
  filtering (**required for integer textures**)"；`:1199-1204` 10/12/16-bit 一律走
  R16UI；TOPOS 只有 10/12/16-bit ⇒ **恒为点采样**。
- `src/shared/media/macos_vt/iosurface_gl_bridge.py:865-866` — IOSurface 路径显式
  `GL_LINEAR`。
- 对照：8-bit 池与默认 float16 池都是 LINEAR（`yuv_gpu_upload.py:159`、`:720-723`）。
- 另有编辑页未接线 `chroma_uv_scale/offset`（4:2:2 半色度样点相位差，仅调色页接了
  `async_renderer.py:3082-3083`），表现为边缘色边而非块状。

**这不是"设个 GL_LINEAR 就能修"**：整数纹理在 GPU 上**不可线性过滤**，这是硬约束
（导出路径也有同源注释：`timeline_gpu_export_renderer.py:1275`）。可选方案：
把 10-bit 平面提升为可过滤的归一化/浮点纹理（R16F）后再缩放、或在解码侧按视口
尺寸做高质量重采样、或预览走"点采样 + 一级预降采样"。**属独立子系统改动，需要
你决定方向后再动手。**

**建议的最小验证**（10 分钟，能立刻证伪或坐实）：
把时间线视口调到与素材 1:1（如 1920×1080 源配 1920 宽的监视器）——若块感/锯齿
**消失**，即确认是缩放采样而非码流质量。

## 5. P6 去块的解码开销：已并行化，SIMD 是下一批

**线程扩展（v2.1 后；同一码流、全片 487 帧、中位数、位精确已复验）**：

| 文件 | 1 线程 | 4 线程 | 16 线程 | 扩展比 |
| --- | ---: | ---: | ---: | ---: |
| 2K proxy | 47–54 | 165–192 | **296–338** | 6.3× |
| 2K standard | 33.1 | 115.4 | **227.6** | 6.9× |
| 4K proxy | 12–13 | 45–51 | **85–92** | 6.9–7.4× |
| 4K standard | 8.9 | 33.8 | **65.5** | 7.4× |

> 本机重复测量噪声 **±12%**（同一二进制、同一码流、3 轮中位数，2K proxy 16
> 线程在 296–338 之间摆动），跨机/跨时段引用时请带上这个带。±12% 以内的
> "提升"一律按噪声处理——下面 SIMD 的判定就是这么被纠正的。

（`tools/bench_topos_decode_threads.py`；每档 1/4/16 线程的全片 SHA-256 **完全
一致**——这是并行切片"窗口不相交"的帧级复验。缩放路径同样复验：REDUCED/HALF
在 1/4/16 线程下逐位一致。）

**滤波净成本**（产品库 vs 只在调用点关掉 bit2 门控的同源库，同码流）：

| 文件 | 线程 | 含滤波 | 无滤波 | 滤波净成本 | 占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2K proxy | 1 | 21.1 ms | 12.1 ms | **9.0 ms/帧** | 43% |
| 2K proxy | 16 | 3.33 ms | 1.86 ms | **1.47 ms/帧** | 44% |
| 4K proxy | 1 | 84.0 ms | 45.7 ms | **38.4 ms/帧** | 46% |
| 4K proxy | 16 | 11.8 ms | 6.13 ms | **5.67 ms/帧** | 48% |

即滤波值 ~45% 的解码时间（此前"3.2× 解码时间"的口径是串行版，已随并行化作废）。
**这是当前 CPU 侧最大的一笔可回收开销**（按 45% 占比、滤波快 3× 估算，可换回
~30% 整体吞吐，利好纯 CPU 解码的机器）。

**SIMD 第一批（自动向量化）已试并否决**：把 apply 写成无分支 select 让 clang
向量化——H 趟确实被向量化（`-Rpass=loop-vectorize` 从"not beneficial"变成通过），
输出**逐位一致**（全片 SHA-256 与标量版完全相同），但**吞吐无差异**：两版都落在
本机 ±12% 噪声带内（296–338 fps）。根因清楚：真实码流里**门控稀疏**，"门控不过
就整段跳过"省下的算力 ≥ 向量宽度买到的那点。**结论：真做 SIMD 必须保留跳过的
掩码/早退路径**（按 8/16 个边界一组：先向量判门控，全不过则整组不落地），
而不是把 apply 无条件化；垂直趟还需 gather 型布局（8 行 × 1 边界列）。归下一批，
本批不动标量内核。

**GPU 滤波的判定（实测，结论：不做）**：GPU 侧两趟 fragment pass 实测
0.29 ms/帧（4K 三平面，纹理常驻）。但预览平面是 CPU 解码产物、每帧都要上传，
滤镜只能在**上传之后**跑，且预览目标是 2K 级（1920×1080）——那里的 CPU 滤波
只有 1.47 ms/帧（16 线程），GPU 省下的绝对量小于一帧预算（40 ms @25fps）的 4%，
却要额外背上 GLSL 接入、GPU 能力探测、CPU↔GPU 位精确自检三件长期维护成本。
按"不是远快就不做"的既定口径，**本批不做 GPU 滤波**；预览的块效应已由 §3.5 的
目标网格滤波在 CPU 侧解决（对所有机器生效，含无独显机器）。

## 6. 未做的杠杆（有数据，未改默认）

**预算留白**：2K proxy 当前只用到同档 ProRes 的 **84.8% 文件体积 / ~90.3% 视频
码率**（产品 P2 目标是 ≤98%）。实测把 `target_bpp` 提到 0.7448（+15.5%）后：

| | 现状 | 用足预算 | Δ |
| --- | ---: | ---: | ---: |
| Y PSNR | 40.127 | 40.579 | **+0.45 dB** |
| 边缘 PSNR | 36.373 | 36.960 | **+0.59 dB** |
| 色度 U/V | 46.91 / 45.57 | 47.28 / 45.94 | +0.37 |
| 高频保留 | 0.838 | 0.846 | +0.008 |
| 块界台阶 h | 3.878 | 1.963 | ≈减半 |

但这会**增大文件体积**（TOPOS/ProRes 由 84.8% → 98%），与"体积没有大变化"的约束
冲突，**故未改默认值**；若你接受这一档体积，收益在 `tools/bench_topos_qgain.py`
里一条 `--patch proxy:target_bpp=0.7448` 即可复现。

## 6.1 滤波强度旋钮还剩多少空间（2026-09-22 续查，结论：没有）

门控修复后 v2/v2.1 选定的权重与强度工作点（W0=12/W1=4/spread=1、α=clamp(2·step,3,48)）
是**在 buggy 门控下扫出来的**，故 v2.1 后又复扫了一次，三处都到点：

1. **图片档的 α 恒为 3**（floor 吸收）：`scale` 表到 qp68 时 `2·step` 仍 < 3，产品
   图片档 qp 45–63 全在死区——强度旋钮在图片链路上按定义无效（实测改
   `DB_ALPHA_MIN/MAX` 输出 SHA 不变）。
2. **抬起 floor 是纯亏**：4K 422-ultra 上 α 3→6/8/12/20，块界台阶只从 0.31/0.29
   降到 0.28/0.25 → 0.16/0.13，Y PSNR 却 −0.38 → −8.92 dB（边缘 PSNR −3.7 dB）。
   α=3 就是该档的正确工作点。
3. **生效区（低档）强度也已到点**：2K proxy 扫 α×0.5…×2.5 与 spread，块界台阶与
   PSNR 互相抵消，全部落在 ≤0.1 dB / ≤0.3 LSB 的带宽内。

⇒ 解码端无免费画质空间；剩余杠杆只剩编码端预算（体积）、SIMD（速度）与
"图片 CLI 是否默认开位"（解码时间）。详见
`docs/image/toos_deblock_verify_2026-09-22.md` §1。
