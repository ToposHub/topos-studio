# 调色页拖拽预览与 DaVinci Resolve 对齐计划

2026-11-25 · 代码基线 `fix-ui` 的 `2207a1cb` · Topos Studio（PyQt6、ModernGL、GLSL，macOS 可用 VideoToolbox 和 Metal）。优先处理新开工程后的第一次拖拽，然后优化调色页反拖与换向。已有同屏结果覆盖部分单轨手势。完整的多轨、串行 LUT 和冷工程矩阵需按下文建立和复测。

## 2026-11-25 实施与复测

本轮代码对照为 `fcb0bbed`。测试机为 Intel Core i9-9900K、Radeon RX 6900 XT，macOS 15.3.1，显示器实测 60 Hz。正式单轨对照使用 Resolve 21.2.0.6、同一段 4K25 H.264 原片和同一 33³ LUT。两个查看器中的画面都为 704×396，采中心 320×180 区域，按 WindowServer 的显示时间戳计算变化间隔。拖拽使用 3840×2160 的原片解码帧，Topos 常规播放沿原有路径直接从原片解码到 1920×1080。每秒可见更新计数受捕获影响，25 fps 播放另用 Topos 画布的源帧号核对。此组 Topos 对照工程只编排视频轨，冷工程与持续运行测试另用关联音轨。此轮未测量音画时差。

Color 快速拖动在每次换向时按画布已经绘制的源帧接续。相邻输入在同一个 Qt 定时器周期内先到顶点再折返时，旧方向也会立即失效。Intel Mac 的 UHD 软件 H.264 路径可复用独立 master 解码源已交付的原片平面。缓存仍有 256 MiB 字节上限，按实际持有的平面核算。常规播放复用每个解码源的 FFmpeg 缩放器。混音台首次显示时才建立音轨条带，音频引擎随时间线继续同步。切到单片段调色页时，隐藏的剪辑页停止预取邻近帧。打开合成监看或返回剪辑页时恢复预取。

调色页的「查看 → 时间线合成监看」打开独立的 Program 监看窗口。可在原调色画布编辑选中片段，同时用监看窗口的播放和定位控件查看时间线全轨输出。该窗口与剪辑页共用同一个 Program 查看器和逐片段调色、GPU 合成路径。

冷工程用新进程、独立工程、原片副本和缓存做了五对交错测试，从剪辑页进入调色页后立即反拖。按下到第一张方向正确的画布绘制，中位数从 1503.2 降至 1216.8 ms，首个有效移动到该绘制从 253.2 降至 210.4 ms。拖动中的绘制间隔 P95 为 126.8 → 126.1 ms。每轮最长间隔的中位数为 161.1 → 153.5 ms，五轮最差为 171.3 → 181.3 ms。每轮拖动期间的可见帧数中位数为 10 → 9。十次都精确停在源帧 177，缩略图和波形均恢复。最终版有一轮在松手后 77.3 ms 到达精确帧，其余四轮松手时已到位。

单因素诊断显示，一次冷拖中，隐藏剪辑页的邻帧任务入队由 25 次降到 0，GPU 快照由 12 次降到 0。正式五对测试均使用产品默认的 D 组策略，按下时缩略图和波形都已空闲。P0 的冷态 A 至 D 在途负载对照仍待完成。

原片回放逐次核对了 277 个请求的帧号、PTS、格式和各个 YUV 平面的 CRC。59 个快拖请求的物理 seek 从 36 次降到 12 次，实际解码从 612 张降到 214 张。master 缓存峰值从 47.5 MiB 增至 249.2 MiB。4K → 2K → 4K 切换时，缓存帧数上限分别为 24、4、24，关闭后帧引用释放。缩放单独按每种编码 24 帧、五轮交替测量，四种原片输出平面哈希均一致。缩放耗时 P95 的轮次中位数分别为 H.264 25.3 → 1.8 ms、H.265 19.4 → 3.8 ms、ProRes 422 HQ 24.8 → 3.0 ms、DNxHR HQX 10 位 24.9 → 3.3 ms。

多轨实测使用独立的 640×360 Program 画面。单轨单节点、双轨三节点、四轨六节点 H.264 的 Color 各块可见更新分别为 23.5、23.2、23.0 次/秒，同工程 Edit 为 21.2、19.5、19.5 次/秒。H.264、H.265、ProRes 422 HQ 和 DNxHR HQX 混合四轨、每轨六节点时，Color 各块约 14.0 次/秒，Edit 各块约 8.0 次/秒。这些是各四秒一次的测量。第 110 帧的两页输出逐块逐像素一致，四轨画面分别匹配源帧 135、190、260、325。

H.264 的 1／2／4 轨 × 1／3／6 节点九种组合都测过一次正常播放。考虑各轨的独立采样，Color 为 22.2–23.7 次/秒，Edit 为 18.0–23.0 次/秒。九组加混合组的 25 块静帧都比独立源参考的前后相邻帧更接近目标，也通过两页的逐像素比对。

Resolve 使用独立项目副本 `Topos 4K25 matrix 0fdddc68b5`。双轨 H.264 三节点、四轨 H.264 六节点和混合四轨六节点合计 54 个 LUT，逐个旁路后，以 16 位 TIFF 核对。每个节点都改变了所属轨的画面，其余轨采样区的最大差为零。两应用同位置对应的 10 块画面相关系数为 0.958–0.998，8 位 RGB RMSE 为 4.8–22.6。跨应用颜色仍有差异。一张 Resolve 静帧重复返回了前一时间点的画面，已剔除并使用重新导出的同帧参考。

上述原始对照按 Resolve API 读回的源起点匹配，起点 80、215 的两轨在 TIFF 中却各晚了一帧。另建校准时间线，将这两轨的 API 读回值调至 79、214，独立 TIFF 才分别匹配 Topos 的源帧 190、325。完成源帧校准后，跨应用的逐轨 8 位 RGB RMSE 为 3.7–18.0。Resolve 当前 Color 窗口未通过完整四分屏画面核对，暂不报告该窗口的四轨播放速率。

Resolve 的 Edit Program 窗口经四块画面配准后，四轨六节点 H.264 各块为 23.6–24.1 次/秒，混合四轨六节点为 22.7–23.2 次/秒。该独立测量的查看器为 797×448，各一次四秒，保留作 Edit 参考。

持续运行测试使用带关联音轨的 4K H.264 原片，在调色页轮流播放、反拖和顺拖。首轮持续 601.8 秒，157 次播放与 314 次拖拽全部正确，关闭工程约 16 秒后仍有 9 个 VideoToolbox 句柄、1 个 FFmpeg 容器和 0.52 MiB 剪辑帧缓存。现已在确认关闭工程后归还 Program 显示纹理并释放时间线渲染器与共享解码器。上表同屏手势采集于此项关闭修复前。

修复后的第二轮持续 603.4 秒，154 次播放都向前出画，308 次拖拽全部有正确方向的画面，松手全部精确。关闭工程后，被跟踪的 VideoToolbox 句柄、FFmpeg 容器及帧缓存均为零。独立补测在关闭后 18.012 秒内采样六次，句柄与缓存均保持为零。保持同一应用进程重新打开工程后，播放再次从源帧 229 前进至 265，反拖、顺拖精确停在 177、225。

### 冷工程复测与后台任务恢复

本轮已接入拖拽优先级，正常松手和中断后等待 250 ms 空闲再恢复，随后优先补当前可见项目。下一步在长片和连续短拖中记录重复解出的音频秒数、丢弃的缩略图张数和可见区域补齐时间。若波形频繁从片头重算，试验分块保留已完成的峰值和源采样位置，按素材、音轨、声道、采样配置及效果版本失效。若缩略图在同一 GOP 反复定位，按媒体和关键帧组归并可见请求，一次顺解生成多个尺寸相容的图，滚出视口时回收尚未开始的任务。逐项比较冷态总读取字节、解码帧数、首张可见耗时及整屏补全耗时，并复核波形接缝和缩略图源帧号。

四组保持同样的 UI 可见项、已有缓存绘制和手势。每组每轨数至少 5 次，应用顺序和 A 至 D 顺序交错。Resolve 在相同工作量的独立冷工程测正常行为，有对应公开控制时另记对照。记录暂停前后的待处理、在途与完成数、取消原因和延迟、首张缩略图和首条有效波形、完全填满可见区的耗时。关联输入至首次真实画面、拖拽 P95、变化率、最长无变化区段和精确松手延迟。

默认方案在播放头**按下时**暂停新增缩略图和波形生成。在途任务通过现有队列取消或在安全检查点让出，前台预览持有的素材会话继续工作，缓存命中仍然可见。松手或取消后，按当前工程和可见范围重排工作，波形和缩略图自动补齐。双轨、四轨逐一核对恢复和可见范围填满时间，并在后台恢复的同一试次验证所有可见片段同时到达松手的精确源帧。已有的播放、缩放等暂停理由与手势叠加，只有所有暂停理由结束才恢复。覆盖松手、离窗、鼠标抓取丢失、切页、打开第二工程、关闭窗口和连续两次按下。持续看到正在使用的画面，避免用清空查看器换取测试指标。复用 `timeline_panel.py` 已有的缩放让步、普通和效果波形调度及缩略图调度，保留解码会话、缓存和渲染线程的所有权规则。 [时间线面板](../../src/features/edit/ui/timeline_panel.py)

每次冷跑使用新的测试工程副本、独立测试素材目录和独立应用缓存。Topos 要确认 `TOPOS_CONFIG_PATH`、素材旁 `.cache`、全局兼容缩略图目录及 Qt `AppCacheLocation` 的波形缓存都指向本次隔离范围或处于空测例范围。分别核对软链接是否仍解析到共用素材目录。需要时使用独立测试账号、独立工作树及同一 SSD 上的素材副本。Resolve 使用测试工程库及新的缓存目录。只使用此次生成的路径，保留用户工程和缓存。热跑用同一副本等缩略图和波形完成，再重复同一手势。磁盘缓存热但进程重开的用例单独记账。关闭磁盘波形缓存可做内存实验，作为独立条件记录。

## 调色与剪辑验收矩阵

下表各项全交叉。每种公开编码各跑完整矩阵并按重复规则采样。另跑混合 4 轨，四个区块分别是 H.264、HEVC、ProRes、DNxHR。优先用 H.264 和 ProRes 建立矩阵样板，再扩展其他素材。4K25 统一为 3840×2160、25 fps、已探测的原片。同一可见片段在两应用使用相同源身份、源起点和关键调色参数，1／2／4 轨保留同一时间线坐标。

| 维度 | 条件与验收口径 |
| --- | --- |
| 时间线和构图 | 1 轨全屏，2 轨各缩小为 50% 左右并排，4 轨各缩小为 50% 拼田字格。所有可见区域用不重叠的采样框，固定画面边缘和布局以识别缺轨。多轨使用不同源偏移或可区分的素材，另做带帧号的正确性图卡。 |
| 每条可见片段的串行节点 | 1／3／6 个 LUT 节点。在两端使用相同 `.cube`、节点顺序、应用域和强度。选定正常、暗部和高饱和帧，分别切换每个节点并比较像素，确认每个节点对最终输出有真实贡献。对照夹取饱和后不起作用的节点时重新选片段或强度。无 LUT 只用于定位开销。 [已入库的 33³ LUT](../../bench_out/resolve_vs_topos_2026-11-22/Topos_Resolve_AB_33.cube) |
| 主要手势 | 正常播放至少 4 秒。纯反拖从时间线 200 到 20，慢档约 3 秒，快档约 0.684 秒。慢、快往返复用双方同一事件序列，固定路径与各腿用时，分腿记录。每档再做按住停在目标至少 500 ms、松手到精确帧及松手后持续保持。增加标尺任意位置按下立即拖动、跨切点与进出空白。 |
| 调色入口 | 每个构图先逐一选中可见片段测调色预览，再在调色页用该时间线测真正的多轨输出。切换片段后节点面板、帧号和调色预览跟同一片段。合成模式中选择当前片段只决定编辑目标，所有可见片段各跑自己的 LUT 链。1 轨两种视图也分别核对入口与颜色。 |
| 剪辑回归 | 用刚才同一工程、时间线、原片、节点、布局和手势测实际 Program Viewer。每块画面分别报告帧号和变化率。比较播放、层间同步、跨切点和停住／松手。 |
| 缓存与环境 | 冷态与热态分别形成数据集，记录应用、硬件、显示刷新、实际解码/渲染后端、预览分辨率、缓存状态、音频与示波器状态。关闭自动缓存、代理和主动自适应画质供原片主对照，另测两边日用默认配置并单列。 |

基线中从 Edit 切到 Color 解析的是所选片段，常规预览沿 `video_controller` 到 `AsyncRenderer` 执行完整调色。旧时间线预览分支是 CPU 合成，只有部分一级调色且缺乏预缓冲，入口已关闭。本轮通过可选的「时间线合成监看」接入 GPU 时间线输出。复用 Edit 的时间线渲染计划、可见层和原片解码能力，并复用 Color 的完整节点图渲染能力。各片段先按自己的源和色彩设置完成节点链，再按时间线合成并应用统一的监看变换。工程、时间线和颜色栈原有 revision 驱动失效与撤销。记录时分别注明选中片段画布或时间线合成监看，并逐块核对多轨结果。 [调色入口](../../src/app/controllers/page_controller.py) · [调色运输与旧预览入口](../../src/app/controllers/file_controller.py) · [调色渲染线程](../../src/features/color/core/async_renderer.py)

## 优化阶段与验收

以两个应用实际窗口输出配对验收。用真实屏幕刷新周期 `T` 表达响应目标，60 Hz 时约 16.7 ms。先校准捕获时钟和显示刷新，记录样本交付抖动。首变按手势首个有效输入计时，换向按每次实际进入新方向的输入计时，只认第一次呈现符合新方向的画面。超过该腿结束仍没有新画面时记未响应，单独报失败率、最大停顿和每腿明细。稳定播放同时记录 25 fps 的实际呈现帧数、掉帧与音画同步。

| 阶段 | 实施内容 | 完成条件 |
| --- | --- | --- |
| P0 冷首次拖动 | 建 A 至 D 四组实验，落默认按下让步、松手或取消恢复和缓存命中直出。 | 与 A 配对比较，冷态首变中位数或间隔 P95 至少降低一个刷新周期，其他冷态指标和热态指标没有超出一个刷新周期的退化。公开最差组。预览无黑闪、死锁，缩略图和波形可完整恢复，取消后队列继续处理。 |
| P1 单轨调色反拖 | 给每次求帧建立从输入、队列、seek／解码、ready、GPU 提交／完成到真实 blit 的同一身份。分解换向的旧任务取消、指针追过已画帧、再次解码和显示等待。先跑 H.264 的纯反与快往返，再查播放。 | 中期目标 P95 ≤ Resolve 的 1.35× 且可见变化率 ≥ 85%，快换向单腿都能出画。先明确冷、热首变和换向 P95 的差距，测量误差以一刷新周期计。 |
| P2 多轨调色 | 实现独立的 Color GPU 真合成路径，按同一时间线帧 gather 每层源，完成各自节点图再合成。可复用已证明正确的媒体帧与节点缓存，使用资源预算和过期释放。 | 完成 1／2／4 轨、1／3／6 节点和全部手势的同工程 Color、Edit 实机记录。每块图都能更新，帧号与 LUT 图参考一致，支持取消和切换工程。 |
| P3 最终对齐 | 按实测差距继续优化解码、渲染和呈现。补跑公开编码、混合轨、Topos 原生解码和第二台独立机型。 | 公共素材每组 Topos 可见间隔 P95 ≤ 对应 Resolve 的 1.10×，可见变化率 ≥ 90%。首变及每腿换向单列，配对差值中位数 ≤ `T`、P95 ≤ `2T`；按住精确和松手精确的新增延迟 P95 ≤ `2T`。两端都须精确落帧，明显漏响应、错向帧、黑闪或色变直接计失败。 |

| 耗时位置 | 有证据时优先做的改动 | 保护项 |
| --- | --- | --- |
| 原片解码、GOP 或 ready | H.264／HEVC 分别查 GOP、PTS/DTS、B 帧重排、硬件会话、返回前的旧代际工作。比较现有 FFmpeg 原始帧历史、VideoToolbox 重用、并发解码、单张换向预取和预算化 GOP 缓存。帧内 ProRes／DNxHR 优先看 I/O、帧格式、转换和上传。每次只改一个瓶颈并记录路径选择。 | 严格源帧索引、媒体/帧身份和 generation。反放、变速、冻结、VFR、跨 GOP、素材切换和关窗仍正确。预取候选不越过指针，缓存计实际保留字节。 [VideoToolbox 源](../../src/shared/media/macos_vt/source.py) · [调色求帧](../../src/shared/video/video_playback.py) |
| 输入、队列或呈现 | 先看是否真的排队延迟，再调整合并节奏、ready 信号或成本较低的轮询补偿、渲染取消和前台同步。只允许与交付代数匹配的纹理呈现在当前查看器。窗口刷新争用时继续画上一张可信画面。 | Qt UI 保持响应；GPU 创建、同步、回收走现有上下文与队列。记录 GPU 完工与真实绘制，压测播放／暂停互换、连续换向及关闭。 |
| LUT、合成或 GPU | 分轨统计输入转换、LUT 节点、合成、输出变换、示波器、纹理上传和 GL／Metal 同步。优先复用纹理、已解析 LUT 和结果身份吻合的节点缓存。比较 GPU 各层并行收益与实际显存成本。 | 避免同一数据的 CPU 往返、失效风暴和资源超额。能力不足时显示最近可信帧及清晰状态，允许降呈现频率。降采样如要启用需显式标示并单独统计，停住及松手回到准确的完整调色。 |

T2 解码候选先用同一段 H.264 的闭 GOP 分离出独立反向游标试验，复用现有 Edit／VideoToolbox 的原生重用接口与缓存预算。用内容身份、候选的实际解码帧号与 PTS、片段、方向和当前代际判定是否可用，逐轨核对目标与实际帧的差值。关闭或不支持闭 GOP 的素材走当前精确路径。多轨与各游标共同使用可保留帧的全局字节预算，按平面实际分配和引用生命周期计价，队列与独立游标均可取消。分别比较无预取、现有单张候选和独立闭 GOP 游标，只有屏幕 P95 和换向确有改善才保留复杂度。

资源随每次测试记录。CPU 分 UI、解码、渲染工作线程、缩略图与波形，GPU 分图形忙时、实际 GPU 完成时间、上传、显存或统一内存和独立媒体解码引擎。记录 RSS、私有/共享内存、已保留帧字节、系统内存压力、磁盘读吞吐、媒体会话数、缓存命中/淘汰和每次有效出画解了多少张帧。前后台任务各自记录等待与运行时间。采集不到的硬件计数标为不可用。对比每组峰值、P95 和拖拽结束后的回收，另跑 10 分钟播放／拖拽循环，检查资源峰值和会话数量稳定。GPU 纹理、缓冲、FBO、CVPixelBuffer 的所有权和释放依 `.clinerules` 复审。

颜色验收先对齐中性画面、源范围、矩阵、输入／工作／显示色域、ICC、LUT 插值和缩放。停住或松手取得 Topos 同时刻同规格的静态参考，在同一路径应逐像素一致。跨应用另用无损 16 位 TIFF，比对逐轨和合成的 10 位 RGB RMSE、最大通道差 P95、最大差与偏差位置。独立图卡加实片覆盖肤色、暗部、高饱和与高光。分离显示变换与源解码偏差，先记录两端同一路径重复测量的漂移，固定该信号链的容差后再做性能迭代。拖拽过程查看每轨真实帧身份、静止后帧稳定性和黑／白／色闪，并以源帧画面比对排除素材自带变化。HDR、10 位和 Alpha 走原精度路径分组验证。 [调色对照流程](../validation/resolve_comparison_workflow.md)

公开编码入口先测 `4K_H264.mov`、`4K_H265.mov`、`4K_prores422HQ.mov`、`4K_DNxHR HQX 10bit.mov`。TOPOS 原生媒体如 `4K_topos_422_HQ.mov` 走独立原生解码基线，按相同手势统计延迟、画质、字节上限与正确帧。Resolve 能否直接读同码流先验证，不能直接读时只提供成对 ProRes 参考及 Topos 自身改进比率。编码端若需要改善自家格式 GOP、索引或快速代理生成，另列编码耗时、码率、回解质量、兼容性和既有工程迁移。原片拖拽的指标继续使用原片播放数据，导出和转码另记。 [样片与生成方法](../../tests/test_videos/README.md)

## Windows 实机复测与优化注意事项

Windows 沿用上文的素材、手势、构图、LUT 节点数和 P0–P3 验收目标。每台 Windows 机器都要先测本机 Resolve，再用 Topos 复现同一手势。上文的毫秒数和暂停后台任务的收益均来自 macOS，Windows 调色页的起画、换向与屏幕呈现数据待采集。

| 顺序 | 怎么测 | 根据结果做什么 |
| --- | --- | --- |
| 1 · 建同机基线 | 记录 Windows 版本、GPU 型号与驱动、Topos 提交、Resolve 版本及 Free／Studio 版别。两端使用同一显示器、本地 SSD 上的同一批原片、相同查看器像素尺寸和 LUT。固定供电模式、刷新率、系统缩放、HDR 和监看设置。在原片基线中关闭代理、优化媒体和渲染缓存，冷、热工程分开，按同一输入序列交错测至少 5 对。 | 按机器、驱动、缓存状态分别报告。混合显卡机器分别登记解码、调色渲染和显示输出所在的适配器，能取得时记录适配器标识 LUID。更换驱动或 GPU 路径后重测配对基线。 |
| 2 · 首次拖拽争用 | 用带可见音轨的 1／2／4 轨冷工程，按 P0 的 A–D 四组分别控制缩略图和波形。在测试中记录按下时两类任务的排队数、在途数，以及首次移动到首张新方向画面的延迟。另跑一次两类后台任务都已结束的热态对照。 | 核实产品默认在按下时暂停两类新任务，在途任务及时让出。松手或取消后检查 250 ms 空闲恢复、可见区补齐时间和再次按下时的响应。分别报告 Windows 的首帧收益和恢复代价。 |
| 3 · 调色页优先 | 从单轨 4K H.264、单个 33³ LUT 开始，分别测第 200 帧到第 20 帧的慢反拖和快速反复换向，再补快反拖、慢换向与正常播放。再按验收矩阵扩至双轨左右并排、四轨田字格，每个可见片段分别串联 1／3／6 个 LUT。剪辑页复用同一工程。 | 调色页的选中片段预览和时间线真合成分别登记。真合成接通后逐格核对首次换向、帧序、闪烁、颜色和松手精确帧。屏幕采样框避开光标、播放头及叠字，防止把 UI 变化计为素材出画。 |
| 4 · 核实解码路径 | 默认配置先跑。剪辑页从 `decode_manager.create_source` 核对实际源与解码器。调色页默认使用独立 `VideoSession`，从该会话记录实际源类型、解码后端和输出像素格式。启用共享帧提供器的试次单列。对能提供适配器信息的后端同步记录设备。 | 若输入到解码就绪占主耗时，按 GOP 记录每次换向的 seek 次数、实际解码帧数和废弃旧请求耗时，再比较本机可用的硬解与经日志确认的软件回退。`TOPOS_DISABLE_WIN_HW_DECODE=1` 仅关闭专用 Windows 硬解路径，仍可能选中通用硬解。诊断后恢复默认配置。 |
| 5 · 定位调色与呈现延迟 | 按请求代际和每轨源帧号／PTS 串起输入、解码就绪、纹理上传、LUT／合成提交、GPU 完工、查看器绘制，并用屏幕采样核对实际可见时间。重点看换向后第一张方向正确的新帧，以及解码已就绪但屏幕仍停留的区间。 | 若解码已就绪，检查实际解码表面进入调色纹理时的 CPU 回读、重复上传、跨 GPU 拷贝及同步等待。若延迟随节点数增长，再拆分各 LUT 的 GPU 耗时。按测得的主耗时决定改解码器、表面传递还是呈现调度，同时复核 8／10 位、色彩范围和显存峰值。 |

Windows 的最终验收对象是**同一台 Windows 机器上的 Resolve**。每组屏幕可见更新间隔 P95 ≤ 对应 Resolve 的 1.10 倍，可见变化率 ≥ 90%。首变和换向的配对延迟差中位数 ≤ 一个实测刷新周期，P95 ≤ 两个周期。错向回跳、黑闪、色闪和松手错帧按 P3 计失败，每块可见画面独立核对。

## 复测步骤

1. 在仓库根目录运行下列命令记录版本、样片和 LUT 指纹。测试工程另存为测试副本，确认 4K25、音轨、源偏移、色彩设置和工程缓存均一致。将同一 `Topos_Resolve_AB_33.cube` 导入两端。
2. 用下列 Topos 启动命令打开测试副本。Resolve 在专用测试工程库中打开对拍工程，设置独立工作缓存目录。冷跑检查实际缓存读写路径，分别记录在途与空闲任务。两个应用在同一屏幕按交错顺序复测，同一轮仅一个应用执行播放或拖拽。
3. 以画面宽度换算两个窗口的指针落点，复用同一时间线帧/时间戳序列。每个条件先做探索测量，确认正确显示和颜色后至少 5 次配对有效采样。报告中同时保留各次值、中位数、最差值、长尾、空腿、真实刷新周期和捕获误差。测试代码或素材版本改变时重测 Resolve 配对参考。
4. 保存每次原始输入、真实呈现事件、屏幕采样、逐块帧号与截图、资源统计、版本和缓存路径至独立运行目录。达标后保留达到目标的配置、关闭优化的对照和对应的 Resolve 数据，建立后续回归基线。补跑最后一组相关回归测试。历史脚本若在本机存在，可读取当时的单片段 Color 和 Edit 数据。旧脚本的 Color 采样框固定为单画面，完整矩阵需要按新模式拆分采样与登记结果。
