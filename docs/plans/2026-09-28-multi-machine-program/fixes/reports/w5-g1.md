## 1. AUD-39003 — export_to_json 确定性死锁 [FIXED]

### 根因（复核属实）

`export_to_json`（原 :363-371）在 `with self._events_lock:` 内调用
`self.get_statistics()`，而 `get_statistics`（:326）内部再次
`with self._events_lock:`；`_events_lock = threading.Lock()`（:270）非重入，
同线程二次 acquire 永久阻塞，调用即冻结。

### 修复（锁内收集、锁外序列化——按任务首选方案）

```python
with self._events_lock:
    events_snapshot: List[FallbackEvent] = list(self._events)
data = {
    'events': [e.to_dict() for e in events_snapshot],
    'statistics': self.get_statistics(),   # 锁外调用，锁内不再嵌套加锁
}
return json.dumps(data, indent=2)
```

未改用 RLock：锁内只做快照拷贝、序列化（含 to_dict/json.dumps 的全部
CPU/IO）留在锁外，同时保持了 `log()` "锁外执行日志 IO" 的既有纪律。

### 回归测试

- `test_export_to_json_does_not_deadlock`：后台线程调用
  `export_to_json`，join 超时 3s 判定不死锁（旧代码确定性挂满超时）。
- `test_export_to_json_output_shape`：导出 JSON 含 events 与
  statistics（total_events/reason_counts/codec_counts）。

## 2. AUD-39100 — 锁外释放媒体源的 use-after-close 竞态 [FIXED]

### 根因（复核属实）

`_close_clip_sources`（原 :2043-2073）关闭 master/proxy/disk_proxy 源时不持
`session.decode_lock`（仅 vt_source 持 vt_lock）；而解码路径 `_decode_frame`
（:2118-2122）在 `decode_lock` 内执行 `source.read_frame()`。`close_clip`/
`shutdown` 调用 `_close_clip_sources`（:1231/:2333）时，与在途解码并发释放
PyAV 解码器/容器 → C 层 use-after-free。审查另指出 `update_disk_proxy_info`
两处同款违规：原 :1023 在 `self._lock` 内（不持 decode_lock）close
proxy_source；原 :1047-1054 完全锁外 close disk_proxy_source。

### 前置安全分析（防引入新死锁）

- `decode_lock` 是 `threading.RLock`（:204，注释明确为支持
  request_frame→_decode_frame 嵌套而设计），同线程重入安全。
- 全文件无任何 `self._lock` 与 `decode_lock` 的嵌套持有（request_frame
  :1311/:1350、prefetch :1589/:1624 均先释放 self._lock 再取 decode_lock）。
  修复保持"两锁不嵌套"的既有顺序，未引入 inversion。
- `_close_clip_sources` 的两个调用点（close_clip :1231、shutdown :2333）
  均在 `self._lock` 释放之后调用，持 decode_lock 时不持有任何其他锁。

### 修复（对齐 :2118-2122 的锁协议）

1. `_close_clip_sources`：master/proxy/disk_proxy 的 close + 置 None +
   缓存清理整体移入 `with session.decode_lock:`；vt_source 维持 vt_lock
   （与 VT 读路径互斥）不变。close 先等在途 `read_frame` 完成，之后新解码
   因源已置 None 走 `get_source_for_quality() is None` 安全返回。
2. `_decode_frame`：源选择 `session.get_source_for_quality(quality)` 从
   decode_lock 外移入锁内（与 `read_frame` 同一临界区）。原实现在锁外取
   引用，close 线程置 None 后，等待 decode_lock 的解码线程会在锁内对已
   close 的源执行 read_frame——这同样是 use-after-close，一并关闭。
   （RLock 重入：request_frame :1358 / prefetch :1627 的持锁调用路径不受影响。）
3. `update_disk_proxy_info` READY 分支：`self._lock` 内只摘引用
   （`old_proxy_source` 局部变量 + 置 None），释放 `self._lock` 后在
   `decode_lock` 内 close。
4. `update_disk_proxy_info` STALE/MISSING/FAILED 分支：先在 `self._lock`
   内置 None（新解码不再选中该源），再在 `decode_lock` 内 close。
   （两分支均不嵌套 self._lock 与 decode_lock。）

### 回归测试

- `test_close_clip_sources_waits_for_decode_lock`：主线程持 decode_lock
  模拟在途解码，`_close_clip_sources` 后台线程必须阻塞（1s 内未完成）且
  未 close 任何源；释放锁后按 master→proxy→disk_proxy 顺序全部关闭、
  字段置 None、is_open=False。
- `test_update_disk_proxy_info_stale_close_waits_for_decode_lock`：同法
  验证 STALE 分支 close 等待 decode_lock，释放后完成关闭并置 None。

## 3. AUD-39305 — 缺 `import os`，READY 磁盘代理路径 NameError [FIXED]

### 根因（复核属实）

`playback_clock.py:365`（现 :366）`os.path.isfile(proxy_path)`，而文件头
仅 import logging/threading/time。传入 `is_ready` 的 disk_proxy_info 且
proxy_path 非空即 NameError，被 `open()` 外层 except 吞掉后 close() 并返回
False——整个 SourceManager.open() 失败（session.py 调用方会 raise）。

### 修复

文件头补 `import os`（logging 与 threading 之间，保持字母序）。

### 回归测试

- `test_playback_clock_module_imports_os`：模块级 `hasattr(module, 'os')`。
- `test_source_manager_open_with_ready_disk_proxy`：用 fake source_factory +
  tmp_path 构造 mtime/size 一致的 READY DiskProxyInfo，走完整 open()：
  修复前该路径 NameError → open() 返回 False；断言 `open() is True` 且
  `_disk_proxy_source` 成功挂载（校验通过时不应被拒）。
