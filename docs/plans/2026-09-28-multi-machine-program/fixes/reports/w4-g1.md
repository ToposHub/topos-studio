## AUD-27018 — FIXED

**位置（修复前）**：`src/features/teaching_animation/ai/service.py:75`
（`replace_clip`）。

**根因**：服务在把操作交给命令栈之前，先手工执行
`_without_manifest(timeline.with_clip_removed(clip_id), (clip_id,))` 预删除原
clip。宿主 `MotionGraphicClipCommand.apply`（host_adapters.py:203-208）在
overwrite 模式下只把它**自己**移除的 clip 记入 `_removed_clips` 并在 undo 恢复
（host_adapters.py:221-225）；预删除的原始 clip 从未进入该记录，undo 只移除新
插入的 clip，原 clip 及其 `teaching_animation_references` manifest 永久丢失。

**修复**：删去预删除，将原始 `timeline` 直接交给
`insert_motion_graphic_clip(..., mode="overwrite", command_stack=...)`。
新 clip 起点即原 clip 起点、时长 ≥ 1，原 clip 必然与新 clip 区间重叠，被
overwrite 循环移除并连同 manifest 一起记入 `_removed_clips`，undo 完整还原。
顺带清理了 service.py 中因此不再使用的 `_without_manifest` 导入。前向语义不变
（原 clip 同样消失、manifest 同样清除、其他重叠 clip 的处理路径不变）。

**回归测试**：`test_replace_clip_undo_restores_original_clip_and_manifest` —
经真实宿主 `EditCommandStack` 执行 replace_clip 后 undo，断言新 clip 被移除、
原 clip 按原起点/轨道恢复、manifest 恢复；另
`test_replace_clip_requires_confirmation_and_unknown_clip` 固定 confirmed 门禁
与 KeyError 路径不回归。

## AUD-27400 — FIXED

**位置（修复前）**：`src/features/teaching_animation/core/commands.py:46`
（`RemoveElementCommand.undo`）。

**根因**：`TeachingSceneDocument.with_element_removed`（model.py:667-672）在移除
元素的同时按 `element_id` 过滤删除其全部动画轨；而 undo 只调用
`with_element_added` 插回元素，动画轨永久丢失。与同文件专门为动画可撤销而捕获
前态的 `RemoveAnimationCommand` 自相矛盾。

**修复**：`RemoveElementCommand` 新增 `removed_animations: tuple[SceneAnimation, ...]
| None` 字段；`apply` 时捕获 `tuple(a for a in scene.animations if
a.element_id == self.element_id)`；`undo` 先 `with_element_added`（恢复原索引），
再逐条 `with_animation_added` 恢复动画轨（元素必须先存在，
`with_animation_added` 会校验 element_id 引用）。redo 路径 apply 会重新捕获，
对称成立。

**回归测试**：`test_remove_element_undo_restores_animation_tracks`（经
`SceneCommandStack` 执行 → undo → redo 全循环，断言元素次序、动画轨 to_dict
逐项相等、redo 后再次双双移除）与
`test_remove_element_undo_restores_multiple_tracks_in_order`（一个元素挂两条轨，
apply 后少 2 条、undo 后 `anim-0`/`anim-1` 均在）。

## AUD-27704 — FIXED

**位置（修复前）**：
`src/features/teaching_animation/core/motion_graphic_template_store.py:165-174`
（`import_template_folder`，`import_template_zip` 直通同一逻辑）。

**根因**：template_id 来自第三方 manifest，加载侧仅 `str(...).strip()` +
非空校验。含 `/` 或 `..` 时 `destination = root / template_id` 越出库根；
`_atomic_copytree` 的 `destination.parent.mkdir(parents=True)` 会创建逃逸路径并
`os.rename` 写到库外；`overwrite=True` 更会先 `shutil.rmtree` 库外任意同名目录。

**修复**（两层防御）：
1. `_validated_template_id`：白名单 `^[A-Za-z0-9_.-]+$` 全匹配，且拒绝空串、
   `.`、`..` 及任何含 `..` 的 id（`root / "."` 即库根本身，必须一并拒绝），
   违规抛 `TemplateStoreError`（ValueError 子类，符合本模块"一切失败抛类型化
   异常"的约定）；
2. `_ensure_inside_root`：`destination.resolve()` 必须严格位于
   `root.resolve()` 之下（不相等），纵深防御，任何未来绕过白名单的路径构造
   也会被拦截。

`import_template_folder` 在计算 `destination` 前调用第 1 层、计算后调用第 2 层；
`import_template_zip` 经由 `import_template_folder` 自动获得同一保护。discover /
remove 路径只消费库根下的真实目录，无越界面，未改动（保持对存量包 id 的读取
宽容度）。

**回归测试**：`test_import_rejects_unsafe_template_ids`
（参数化 `../escape`、`sub/dir`、`..`、`.`、`a..b`、`with space`：抛
TemplateStoreError、库根零写入、逃逸目标不存在）、
`test_import_overwrite_cannot_rmtree_outside_root`（overwrite=True 时
`../precious` 不得 rmtree 库外目录）、`test_import_still_accepts_whitelisted_ids`
（`My_Template-01.v2` 正常导入，白名单不误伤）。
