## AUD-16309 — FIXED

**位置（修复前）**：`src/features/edit/core/consolidate.py:430`（`used_names` 声明后全文未用）、
:474-477（base 生成）、:497（still 路径 `f"{base}_c1{still_ext}"`）、
:524-525（分段路径 `f"{base}_c{idx}{ext}"`）。

**根因**：输出名只由 display_name 基名 + 分段序号 + 扩展名决定。两个素材
同名（多卡 DSC_0001.MP4；或 transcode 模式 a.mov/a.mp4 均产出 a_c1.mov）
时，第二个素材的 ffmpeg `-y` 覆盖第一个刚生成的分段文件：第一个素材的
`new_asset.path` 仍指向该文件但内容已是第二个素材的画面，首个记录的
sha256 与最终文件不匹配。`used_names` 死变量表明去重计划过但从未实现。

**修复**：
1. 新增 `_unique_out_name(candidate, media_root, used_names) -> str`
   （consolidate.py:699-720）：候选名与 `used_names`（同批冲突）或
   `os.path.exists(media_root/name)`（对同一 target_dir 重复整理）冲突时，
   在扩展名前追加递增序号（`a_c1.mp4` → `a_c1_2.mp4` → `a_c1_3.mp4`），
   登记后返回。
2. 两条落盘路径全部接入：still 整份复制路径（plan.out_name）与视频分段
   路径（remux/transcode 的 out_name）。
3. 死变量清理：`used_names: set` → `used_names: Set[str]` 并附注释，转正
   为去重登记表（typing 导入补 `Set`）。

**回归测试**（`TestAud16309UniqueOutName`，4 用例）：
- `_unique_out_name` 单元（批内冲突 + 磁盘冲突 + 不同分段序号不冲突）；
- 两个同名图片素材：分段文件互不覆盖，每条 record 的 sha256 与其源内容
  一一对应，新工程素材指向正确媒体内容（修复前 img-1 的记录指向 img-2
  的内容）；
- 两个同名视频素材（transcode 路径，`_run_ffmpeg` 桩替换，无需真实
  ffmpeg）：两条 archived_path 去重、sha 与文件一一对应；
- 对同一归档目录重复整理：上一轮文件不被覆盖（磁盘存在性去重生效）。

## AUD-16500 — FIXED

**位置（修复前）**：`src/features/edit/core/edit_gpu_decode_manager.py`
`invalidate_all_sources`（2984-3016）、`close_source`（2878-2911）、
`close_all`（2926-2969）三条路径先清空 `_sources/_source_cache/_source_refs`
再在锁外逐个 `source.close()`，完全不检查 `_source_refs` 租约；租约契约
（文件头 186-190 注释）此前仅对 `_evict_sources_if_over_cap`（1348）生效。
运行中用户切画质（`timeline_preview_renderer.set_preview_quality` →
`invalidate_all_sources`）可在 PreviewRenderWorker/解码池线程持租约解码时
关闭 VT/FFmpeg 会话 → C 层 use-after-free（SIGSEGV，仓库注释自认复现）。

**根因修复**（与同文件 `_evict_sources_if_over_cap` 的租约协议对齐）：
1. `_wait_for_source_leases(keys, timeout=None)`（新，1360-1392）：关闭前
   排水——轮询等待目标 key（含此前推迟关闭的 key）租约归零；超时
   `_CLOSE_LEASE_DRAIN_TIMEOUT = 2.0`（新常量，与
   `_join_playback_prefetches` 的 2s join 预算对齐）后放弃等待并由下条
   机制兜底，不强行 close。timeout 缺省在调用时解析模块常量（测试可注
   入短超时）。
2. `_partition_close_units_locked(units)`（新，1394-1418）：锁内按租约
   拆分每 key 的关闭单元（主源 + 池克隆）：租约为 0 → 立即关闭列表；
   租约 > 0 → 登记 `_deferred_close_sources`（新状态，`__init__` 声明，
   key → [主源, *池克隆]）。关键不变量：登记发生在从
   `_sources/_source_cache` 摘除的同一临界区，此后该 key 不可能再被
   `_lease_source` 加租，计数只减不增 → 零点穿越可安全触发关闭。
3. `_release_source`（改写，1337-1356）：最后一个租约归零时若 key 在
   `_deferred_close_sources`，弹出并在**锁外**补 close（复用
   `_close_source_object`，遵守"close VT 会话不占管理器锁"）。租约归零
   顺手清理 `_source_refs` 零值条目。
4. `_sweep_deferred_close_locked(match_asset=None)`（新，1420-1443）：
   下一次 close_all/invalidate（全部）/close_source（按素材）时收走租约
   已归零的历史推迟单元，防御兜底。
5. 三条关闭路径重写为同一结构：取消交互预取/预置位（既有协作等待）→
   **排水** → 锁内摘除 + 按租约拆分 → 锁外关闭"归零"单元；原先的
   `_source_refs.clear()` 整体清空删除（会抹掉推迟单元的计数，使补关闭
   永远无法触发）。
6. 空闲路径行为不变：无在飞租约时同步关闭（既有测试
   `test_close_all_closes_idle_sources_immediately` 与 P2-09 全套验证）。

**未及项（超出本批次范围，见 AUD-16501/16503）**：交互预置位线程的
注册表 join、`_closing` 不阻止迟到重建——本修复的排水机制对前者是
纯改善（至少多等 2s），不改其结论。

**回归测试**（`TestAud16500ClosePathsRespectLease`，6 用例）：
- 空闲会话同步关闭（行为不变基线）；
- close_all / invalidate_all_sources / close_source 三路径：持租约时会话
  **不被关闭**、从 registries 摘除、进入推迟表；`_release_source` 后锁外
  补关闭且推迟表清空；
- 端到端线程场景：解码 worker 阻塞在源读取内（持租约）时 close_all
  返回后会话仍存活，解码线程 finally 归还租约后会话被补关闭——即
  use-after-free 窗口的直接回归锁；
- 历史推迟单元（租约已归零）由下一次 close_all 收走。
