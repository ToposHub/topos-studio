## 逐条修复摘要

### AUD-36104 — release_after 异常路径泄漏共享 lease（decode 池槽位永久损失）
- `d3d11_passthrough_chain.py` run() 的 `except (RuntimeError, ValueError)` 分支新增兜底：立即 `surface.release()` 同步归还共享 lease（surface 与来源帧共享同一 lease，悬空即丢 decode 池槽位）；兜底 release 自身抛错（重复归还类所有权缺陷）再包一层 `except (RuntimeError, TypeError, ValueError)` 并 `logger.error` 留痕，不再向上抛。
- 测试：`test_release_after_failure_releases_shared_lease`（断言 in_use 归零）、`test_release_after_double_release_guarded`（双层兜底不逃逸）。

### AUD-36105 — record_stage 未防御 trail 重复登记 ValueError（二次 run() 即抛 + 已读帧泄漏）
- `record_stage` 内部对 `trail.record_stage(...)` 包 `except (TypeError, ValueError)`：同一 trail 二次 run() 命中 ExportGpuTrail 的"段名唯一"守卫时，warning 留痕后继续流转（首轮证据仍有效），不再让异常带着已读出的 frame 逃逸（frame 泄漏 = decode 池槽位泄漏）。
- 测试：`test_second_run_on_same_trail_is_absorbed`（同一 trail 连续两次 run，第二次 frames_completed==2、双池 in_use==0、trail 段名仍唯一）。

### AUD-36107 — D3D11TimelineRenderer 状态无锁（release 与 render_frame 并发 AttributeError 逃逸）
- 新增 `self._state_lock = threading.Lock()`；`prepare()` / `render_frame()` / `release()` 全程持锁。`render_frame` 在锁内快照 `backend`/`plan` 局部变量，锁跨越原生调用——teardown 侧 `release()` 的状态清空必须等待在途帧提交完成（反向亦然），"检查非 None → 被置 None → 使用"窗口在结构上消失，AttributeError 不再可能逃出"只返回 D3D11RenderResult"的契约。锁只串行化 Python 侧状态切换与原生调用进出，逐帧渲染仍由调用方顺序驱动。
- 测试：`test_release_waits_for_in_flight_render`（阻塞式 backend + 双线程，断言 release 严格发生在原生 render_frame 返回之后、无异常逃逸）、`test_render_after_release_fails_closed_without_raising`。

### AUD-36109 — fence 回收线程静默丢槽 / 永不 signal 时线程无限堆积
- `d3d11_texture_pool.py` 新增模块级 `_spawn_fence_reclaimer(release, wait, label, thread_name)`，`D3D11TextureLease.release_after` 与 `D3D11ExternalTextureLease.release_after`（原 126-137 / 178-189 两处同构）共用：
  1. 有界等待：`wait(_FENCE_RECLAIM_TIMEOUT_S=10.0)` 替代 `wait(None)`（D3D11Fence 协议本身支持 `wait(timeout_s)`）——fence 永不 signal 时回收线程在超时后保证终止，不再无限堆积常驻阻塞线程；
  2. `wait` 返回 False（超时）或抛 `OSError`（原 except 只有 RuntimeError/ValueError，OSError 直接杀死线程）时：兜底**同步归还** lease 并 warning 留痕——等待失败意味着管线已 wedge，"槽位永久泄漏累积到池耗尽→导出死锁"比保守归还更危险；
  3. 归还自身抛错（重复归还）`logger.error` 留痕不上抛；fence 已 signal 的快速路径保持同步 release 不变。
- 测试：超时归还并可重新 acquire（断言 `wait` 收到的是有界超时而非 None）、OSError 归还、External 变体同语义、signal 快路径与 EventFence 正常路径回归。

### AUD-36114 — destroy() 清空 _active_slots 与 in-flight bind_texture 竞态（ring 槽双重占用）
- `d3d11_gl_bridge.py`：
  1. `destroy()` **不再清空** `_active_slots`，只撤销初始化态（持锁）——in-flight bind 已登记的槽位由其 `_release_slot` 幂等归还；清空会让后续 bind 拿到同一 ring 槽与在途句柄双重占用。fail-safe 取向：宁可 `ring_exhausted` 也不双占。失败计数与 last_reason 保持保留（既有测试契约"destroy 不是诊断擦除"）。
  2. `bind_texture` 的初始化态检查、空纹理检查、槽位查重与登记收敛进**同一临界区**（消除 check-then-act 窗口；reason 优先级保持原契约：未初始化 > 空纹理 > 槽耗尽）；`initialize()` 置位同样持锁。
- 测试：`test_destroy_keeps_active_slots_no_double_occupancy`（bind→destroy→重初始化→同槽 bind 被拒 ring_exhausted→归还在途句柄后可复用）、`test_bind_after_destroy_reports_not_implemented`。

### AUD-36201 — open() 失败路径不清理 hwaccel 容器、_is_open 失真
- `hw_planar_source.py`：open() 拆为 `open()` + `_open_with_hw_session()`；`super().open()`（CPU 容器）成功后的全部硬解装配包进 `try: ... except MediaOpenError: self.close(); raise`——失败路径复用父类 close() 的完整复位（关闭残留容器、`_container/_video_stream=None`、`_is_open=False`），消费方按"open 抛错 = 源不可用、无需 close"的契约回退 CPU planar 源时不再泄漏容器句柄。
- 测试：无硬解器失败路径、`_reopen_with_hwaccel` 抛 MediaOpenError 路径（均断言容器 close 恰一次、`_is_open` 复位）、成功路径不受影响的回归。

### AUD-36203 — probe 格式支持/纹理池层实际检测 A8_UNORM(65) 而非 NV12（根因在 d3d11_device.py:51）
- **本文件内修复（已完成）**：`windows_zero_copy_probe.py` 新增 `DXGI_FORMAT_NV12_ABI_TRUTH = 77`（dxgiformat.h 真值）一致性门禁——包常量与真值不符时在格式支持层**显式 fail-closed**（reason：`gpu_probe_failed:dxgi_constant_mismatch:nv12=65!=dxgiformat.h:77`），绝不把 A8 的支持证据记入 NV12 层证据或误放行；包常量修正后（77）门禁自动放行、探测照常走真实 CheckFormatSupport。
- **根因 BLOCKED**：`src/shared/media/windows_hw/d3d11_device.py:51` — `DXGI_FORMAT_NV12 = 65` 应改为 `DXGI_FORMAT_NV12 = 77`（65 是 `DXGI_FORMAT_A8_UNORM`）。该文件属并行兄弟批次白名单（其已改 vtable 槽位，见 wd17-g93 报告），本批次严禁越界。**注意**：在根因修正前，真机 Windows probe 会在格式层 fail-closed（诚实降级为软件回退），这优于把 A8 支持误报为 NV12。
- 测试：`test_probe_checks_true_nv12_value`（常量=77 世界：CheckFormatSupport 收到 77）、`test_probe_fails_closed_on_wrong_package_constant`（常量=65 世界：门禁先于 CheckFormatSupport 拦截、即使驱动对 65 报支持也不采信）。

### AUD-36206 — DXGI 格式码沿用包内错误常量（NV12=65/P010=100）传过原生桥 ABI（根因在 d3d11_device.py:51-52）

### AUD-36208 — load_windows_native_bridge 对 factory()/capabilities() 异常无防护
- `native_bridge.py`：`factory()` 与 `bridge.capabilities()` 分别包 `except (OSError, RuntimeError, TypeError, ValueError)`，收敛为显式 probe-failure 结果（reason 前缀 `native_bridge_factory:` / `native_bridge_capabilities:`），不再让原生扩展初始化异常逃逸击穿 zero-copy probe——与 docstring"malformed APIs are reported as probe failures instead of being swallowed"的承诺一致。正常加载路径不受影响。

### AUD-36302 — undo_fn/redo_fn 抛错被吞后 action 仍在双栈间转移（栈/模型失配）
- `undo_stack.py`：`undo()` 失败时 action **放回 undo 栈**（同位置 append）、emit changed 后返回；`redo()` 对称放回 redo 栈。闭包失败意味着模型可能未同步，转移会造成"栈说已撤销、模型没回滚"的失配；留在原栈保持动作可重试（测试覆盖"失败→重试成功→正常转移"）。异常仍只记日志不向 UI 传播（`except Exception` + noqa 保留——闭包由任意调用方提供，无更窄的有意义类型；与仓库既有惯例一致）。
- **既有测试同步更新（白名单外，1 个测试文件内 2 个用例）**：`tests/ui/test_undo_stack.py` 的 `test_undo_fn_raises_does_not_corrupt_stack` / `test_redo_fn_raises_does_not_corrupt_stack` 原样钉死了被审计的缺陷行为（"action 仍移到 redo"），已按新契约更新断言并注明 AUD-36302；该文件其余 20 个用例零改动。此举与 wd17-g93 批次更新既有测试的先例一致。
- 测试（新文件 4 个用例）：失败留原栈、redo 对称、可重试、成功路径回归；更新后的既有套件 22 用例全绿。
