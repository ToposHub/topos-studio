## AUD-18802 [Major/bug] roll_trim_clips source 侧未按 effective_speed 缩放

**状态：FIXED**

**根因**：roll 的 source 增量直接 `± delta_frames`（timeline 帧数），未按
`clip.effective_speed()` 换算（split_clip / trim_clip_left / ripple_* 均已换算）。
speed=2.0 的片段 roll +10 后 source_duration 只加 10（应加 20），播放内容错位。

**修复**（timeline_ops.py `roll_trim_clips`）：新增
`left_source_delta = int(delta_frames * left_clip.effective_speed())` /
`right_source_delta = int(delta_frames * right_clip.effective_speed())`，
左片段 `source_duration`、右片段 `source_start/source_duration` 及 delta<0 的
source 下界校验全部改用缩放增量。docstring 同步说明。

## AUD-18803 [Major/bug] insert_clip_at_playhead 不分割跨越播放头的片段

**状态：FIXED**

**根因**：起始 < playhead < 结束的片段既不在后移集合（`timeline_start >=
playhead`）也不被分割，`with_clip_added` 重叠校验抛
`ValueError("Clip overlaps")`，播放头落在片段中间时 Insert 整体失败。

**修复**（timeline_ops.py `insert_clip_at_playhead`）：

1. 先按 copy_clip_with 分割每个跨越片段（左半片保留原 clip_id；source 侧按
   `effective_speed()` 缩放，与 split_clip 同口径；扩展字段全部保留——沿
   AUD-18800 的 copy_clip_with 模式）；
2. 后移集合改在分割后的轨道上计算（右半片起始 = playhead，随之后移）；
3. `with_clip_added` 的模型层 ValueError 转译为 docstring 承诺的
   `TimelineOperationError`。

**锁定旧行为测试更新**：`tests/edit/test_edit_mode_toggle.py::
TestInsertModeDropSemantics::test_insert_mid_clip_raises_like_explicit_insert`
（更名 `test_insert_mid_clip_splits_like_explicit_insert`）。该测试原锁定
"拖放与显式 Insert 在片段中间落点都抛重叠异常"——锁定的正是本条目判定为
缺陷的共享旧行为；更新为锁定新的共享分割语义（c1[0,48)+c2[48,96)、playhead=24
→ 4 片段 [0,24)/[24,72)/[72,96)/[96,144)，断言逐一）。更新后的测试通过。

## AUD-18804 [Major/bug] roll / ripple 右延长无素材上界校验

**状态：FIXED**

**根因**：`ripple_trim_clip_right` 仅校验 `new_source_duration > 0`；
`roll_trim_clips` delta>0 仅校验右片段最短 1 帧——source 末端可无限越过
素材实际长度（左入点的 `source_start < 0` 下界校验存在，上界不对称缺失）。

**修复**（timeline_ops.py）：两个函数新增 `max_source_frames: int | None =
None` 参数，提供时校验 `source_start + 新 source_duration <= max_source_frames`
（roll 校验左片段延长侧；ripple 仅在 delta>0 时校验，缩短不受影响），越界抛
`TimelineOperationError`。与审计建议一致（"增加参数并校验"）。

**关于 None（无素材信息）保持宽容**：审计建议的"None 时按 numeric 路径保守
策略禁止延长"会使鼠标 Roll/Ripple 延长（RollTrimCommand / RippleTrimCommand
不携带素材长度，commands.py 不在本批白名单）整体不可用，且与已锁定旧行为
（tests/edit/test_fix_w6g8_aud6.py 的 roll/ripple 用例）冲突。数值入口
`build_numeric_trim_command` 已有独立的保守钳制（无素材信息时 headroom=0，
禁止延长），该防线不变。模型层给出校验能力 + 参数，调用方按已知信息传入。

## AUD-18901 [Major/bug] GPU 路径 solid 分支缩进缺陷（sc 未定义/串色）

**状态：FIXED**

**根因**：`if sc is not None:` 与 `if solid_asset is not None:` 同级——素材
解析返回 None 且本层未给 sc 赋值时 NameError（整帧 render_error）；若本帧
先渲染过另一个 solid 层，sc 从上一层泄漏，第二层渲成前一层颜色。

**修复**（timeline_preview_renderer.py GPU 装车循环）：`sc = getattr(...)`
与 `if sc is not None: solid_rgb = sc` 移入 `if solid_asset is not None:`
块内（`gen_params` 读取一并入块）。回归测试用 inspect 源码钉住缩进关系
（sc 赋值与判空的缩进必须严格大于 solid_asset 判空行），防同类缩进回归。

## AUD-18902 [Major/risk] stop() 超时后仍强制关闭在飞解码资源（SIGSEGV 窗口）

**状态：FIXED**

**根因**：`wait(5000)` 超时后仅记 warning 就继续
`_decode_executor.shutdown(wait=False)` + `close_all()`——wait=False 放任
在飞解码 future 继续持有 VT 源，close_all 销毁正在使用的会话，复活注释自认
的 SIGSEGV 路径（慢源 >5s 解码时触发）。

**修复**（timeline_preview_renderer.py `PreviewRenderWorker`）：

1. 新增幂等方法 `_teardown_decode_resources()`（close_all +
   _clear_direct_preview_sources + comp renderer 清理，`_decode_teardown_done`
   标志防双跑）；
2. `_decode_executor.shutdown` 统一改 `wait=True, cancel_futures=True`
   （排队任务取消、在飞 future 等待完成——线程池与解码管理器之间不再有
   并发窗口）；
3. `wait(5000)` 超时分支：不再立即销毁共享解码资源——经
   `self.finished.connect(self._teardown_decode_resources)`（receiver 为
   worker 自身，queued 回 UI 线程）推迟到线程真正退出后执行；connect 与
   isRunning 复查之间线程退出的窄窗直接补调（幂等保护）。

回归测试：stop() 源码钉（wait=True / 无 wait=False 调用 / finished 延迟
connect）+ teardown 幂等行为测试（第二次调用 no-op）。

## AUD-18903 [Major/bug] CPU 回退把 limited-range yuv420p 按 full-range 转换

**状态：FIXED**

**根因**：`cv2.COLOR_YUV2BGR` 按 full-range（JPEG）矩阵转换；limited-range
源（yuv420p，广播 H.264/HEVC 常见）黑位 16 / 白位 235 被当作 0/255——对比度
压扁，与 GPU 路径肉眼可见不一致。注释自认"简化处理"。

**修复**（timeline_preview_renderer.py `_convert_planar_to_bgr` yuv420p
分支）：limited 分支先做 studio→full 摆幅拉伸（Y: 16-235 → 0-255（×255/219）；
UV: 16-240 以 128 为中心（×255/224）），float 中间精度、clip 后回 uint8 再用
原矩阵转换；yuvj420p（full range）分支不变。行为测试：Y=16 → BGR ≤8、
Y=235 → ≥245（旧实现 ≈16 / ≈235）；yuvj420p Y=16 仍 ≈16（两路径可区分）；
色度插值仍生效（U 高 V 低 → 偏蓝）。

## AUD-19202 [Major/bug] dip 判定不继承用户转场 base

**状态：FIXED**（catalog 集中判定 + 预览 CPU 路径；导出侧与 GPU 合成器侧
调用方不在白名单，见"遗留"）

**根因**：`custom_transitions._BASE_TYPES` 允许 `dip_to_color` 作 base，但
一切判定（COMPOSITE 集合、dip 颜色 pass 的字符串相等）都不解析 user_* 的
base：CPU 双源循环跳过、颜色 pass 不匹配 → 用户 dip 转场渲染成普通溶解，
dip 效果完全丢失；GPU 侧 spec 解析到 dip base 返回 None → 整帧回退 CPU
（回退后同样是溶解）。

**修复**：

1. `transition_catalog.py`：新增 `resolve_transition_base_type()`（user_* →
   内置 base）与 `is_dip_transition()`（内置 dip + 用户 dip base）；
   `is_full_frame_transition` / `is_composite_transition` 统一按解析后的
   base 判定（替代调用方各自内联的冻结集合判断；dip 不入 composite——经
   颜色 pass 渲染，与内置 dip 既有路径一致）。
2. `timeline_preview_renderer.py` CPU 合成路径：
   - 双源预合成循环与 wipe_inject 标记改用 `is_composite_transition()`——
     内置类型行为逐一不变，用户 spatial base（wipe/slide/iris）由此进入
     几何 mask 预合成（同一根因的连带修复，不再退化为溶解）；
   - Dip 颜色 pass 改用 `is_dip_transition()`：内置 dip 走原
     `get_color_factor()/blend_color`；用户 dip 按同一三阶段公式
     （`blend_factor*2` / `(1-blend_factor)*2`）+ 新增
     `_resolve_user_dip_color()`（合并定义级/实例级 params 后按 dict /
     list / "#RRGGBB" 解析颜色，规则与 render plan 相同）补齐——dip 效果
     真正渲染。
3. GPU 侧维持既有整帧 CPU 回退（回退路径现已正确渲染 dip），代码内注释
   指明 GPU 直渲需 edit_gpu_preview_renderer 的 dip_jobs 过滤器同步解析
   base（不在白名单）。

测试：resolve/is_dip/is_composite/is_full_frame 的 base 继承矩阵；用户 dip
颜色解析四种格式 + 默认黑。
