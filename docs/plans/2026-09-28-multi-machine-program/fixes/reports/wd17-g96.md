## 逐条明细

### AUD-37009 — FIXED
`src/shared/project/topos_project_controller.py`
- 问题：docstring（模块 :13 与类 :191）声明"线程安全，所有状态变更通过信号"，但 `is_dirty`/`is_page_dirty`/`mark_dirty`/`clear_dirty`/`clear_all_dirty`（原 :245/:254/:267/:313/:351）以及 `to_dict`/`from_dict`/`get_all_dirty_states` 均无锁直接读改 `_page_dirty_states`，check-then-act 在并发下会双重发射 dirty_changed、快照可撕裂。
- 实现：
  - `__init__` 新增 `self._state_lock = threading.RLock()`；全部状态方法（含 `get_dirty_summary`/`get_last_save_timestamp`/`reset`）在锁内完成读改写与快照。
  - 选 RLock 而非 Lock：`mark_dirty` 发射的信号在 DirectConnection 下会在持锁线程内同步执行槽，槽再回调 controller 方法（如 `clear_all_dirty` 内调 `is_dirty`、save 回调内再 mark_dirty）需要重入。
  - `save()` 重构：锁内只做回调存在性 + dirty 检查，`self._save_callback()`（可能的长 IO）**不持锁**执行，成功后回锁清 dirty + 记时间戳；`save_completed` 在锁外发射。
  - 两处 docstring 改为如实契约："dirty 状态字典与保存时间戳由内部可重入锁保护……状态变更仍通过 Qt 信号广播；QueuedConnection 投递 UI 线程"。
- 测试：8 线程 × 30 轮 barrier 竞争 mark_dirty 同一页，断言每轮恰好 1 次 clean→dirty 转变（check-then-act 原子性）；并发 churn 下 500 次 `get_all_dirty_states`/`to_dict` 快照恒完整；save 回调内再 mark_dirty 不死锁（5s watchdog）；正例 save 流程清 dirty + 时间戳。

### AUD-37101 — FIXED
`src/shared/project/topos_project_io.py` `save()`（原 :379-391）
- 问题：`dict(existing_manifest)` 打底后 `update(manifest.to_dict())` 让新建 manifest 全量覆盖旧值，而 `ToposManifest.create()` 会把 `created_at` 重置为当前时间、`created_by` 重置为默认产品名、`required_features`/`optional_features` 重置为空 —— 每次保存都改写工程"出生信息"；同理会把更高版本的 `schema_version`/`edit_content_schema_version` 降级。
- 实现：保留原合并方向（未知/未来键仍从旧 manifest 存活），update 之后显式回填 4 个 provenance 键（仅在旧 manifest 确有该键时，老工程缺键则用新值兜底）；两个版本戳取 `max(旧, 新)`，绝不降级；`modified_at`/`last_saved_by`/`present_modules` 仍按次刷新。
- 测试：旧 manifest（created_at=123.0、created_by="Topos Edit"、required/optional 非空、schema_version=99）→ 保存后 4 键逐一原样、schema 不降级、modified_at 前进、last_saved_by 非空；反例：全新路径首存获得全新 provenance 且不崩。

### AUD-37102 — FIXED
`src/shared/project/topos_project_io.py`（save 原 :369/:514-526，load 原 :585-595）
- 问题：save 是无锁读-改-写（Phase B 读 payload → mkstemp 写 → os.replace），两个并发保存（自动保存 vs 手动保存，或跨进程）都读到旧包时后写者丢弃前写者的模块更新；load 的缓存目录替换是 `rmtree(cache_dir)` + `os.replace`，中间窗口读者看到缓存目录缺失，且两个并发 load 互相 rmtree 对方正在读的目录。
- 实现：
  - 模块级 `_ARCHIVE_LOCK = _ArchiveLock()`：每路径 `threading.Lock`（进程内互斥）+ 归档旁 `.<name>.lock` 咨询文件锁（flock POSIX / msvcrt Windows，跨进程互斥；不可用时降级仅进程内并告警）+ 同线程重入深度登记（save 回调间接触发同路径 load 不自死锁）。锁文件常驻（删除反而引入竞态，注释说明）。
  - `save()`：Phase B 到 os.replace（含临时文件清理）全程持锁——读-改-写原子化。
  - `load()`：全程持锁；缓存目录换入改为 rename-aside：旧目录原子改名 `.retired-<uuid>` → 新 staging 原子 rename 入位（失败则回滚旧目录）→ 事后清理 retired。任何时刻 `cache_dir` 要么旧要么新，绝无"缺失/半拷贝"状态；失败路径（`OSError/BadZipFile/ValueError/RuntimeError` 窄捕获）清理 staging+retired 后返回 (None, None)。
- 测试：两个线程并发保存不同模块（人为放慢 `write_to_zip` 拓宽 RMW 窗口），断言最终包内两个模块标记都在（无锁时后写者必丢其一）；二次 load 换入新版本且 `.topos_cache` 无 `.loading-*/.retired-*` 残留；损坏包 load 失败不清空既有缓存目录；`_ARCHIVE_LOCK` 同路径嵌套获取不死锁（5s watchdog）、4 线程同路径临界区互斥（峰值并发=1）。

### AUD-37103 — FIXED
`src/shared/project/topos_project_io.py` `save()`（原 :368-369）
- 问题：既有 .topos 不可读（BadZipFile/OSError）时，save 按空 payload 继续，把其它产品模块数据全部静默覆盖丢失。
- 说明：根因修复（`ProjectArchivePayload.load_from_file` 对不可读归档抛 `ProjectArchiveReadError` 而非返回空 payload）已由上一批 wd17-g95 的 AUD-36902 落地（提交 fd8383d1a）。本条补齐 save 侧显式契约：在泛化 `except Exception` 之前新增 `except ProjectArchiveReadError` 分支——明确的 ERROR 日志（"refusing to overwrite … lose preserved module data"）+ 返回 False，使"拒绝覆盖"成为被测试锁定的设计行为而非泛化兜底的副作用。
- 测试：既有损坏文件保存返回 False 且字节原样（未被覆盖）、无 `.tmp`/staging 残留；反例：无既有文件时正常保存产出合法 ZIP。

### AUD-37104 — FIXED
`src/shared/project/topos_project_io.py` `_extract_archive_to_cache`（原 :290-291）
- 问题：解压逐成员 `shutil.copyfileobj` 无成员数/总大小上限，恶意或损坏 .topos（zip bomb）可解出 PB 级数据耗尽磁盘。
- 实现：模块常量 `MAX_ARCHIVE_ENTRIES = 50_000`、`MAX_ARCHIVE_TOTAL_BYTES = 32 GiB`（宽松到不影响 4K EXR 烘焙资产的合法大包，又足以拦截 bomb）。双层强制：
  1. 前置快检：新公开助手 `ToposProjectIO.validate_archive_limits(zf)` 校验成员数与中央目录声明的未压缩总大小（返回声明总量，供审计复用）；
  2. 流式强制：`copyfileobj` 改为 1MiB 分块循环，累计**实际写入**字节超限即抛 ValueError（防撒谎的 zip 头把 file_size 报小）。
  超限经 load 的窄捕获降级为 (None, None)，staging 目录被清理，不拖垮进程。
- 测试：monkeypatch 上限后，成员数超限、声明总大小超限两路均拒绝且无 staging 残留；把声明检查旁路（validate_archive_limits 打桩返回 0）后仅靠流式计数仍拒绝（防撒谎头）；正例：真实上限下正常包 save+load 往返成功。

### AUD-37112 — FIXED
`src/shared/project/topos_project_read_service.py` `_load_from_project_manager`（原 :150-156）
- 问题：新格式读取失败后，回退路径把不可信 ZIP 交给 `ProjectManager._load_zip_project` → 未加固的 `zf.extractall(temp_dir)`（佐证 `project_manager.py:94-97`），无任何 zip-bomb/符号链接/路径防护。
- 实现：回退前新增 `_assert_legacy_archive_safe(topos_path)`（仅 ZIP 文件走该校验，旧版纯 JSON 工程不受影响）：复用 io 模块的 `MAX_ARCHIVE_ENTRIES`/`MAX_ARCHIVE_TOTAL_BYTES` 做成员数与声明总大小校验，并逐成员拒绝符号链接、绝对路径、`..` 父逃逸、Windows 盘符/UNC 前缀（`os.path.splitdrive` 判定）。不安全归档 ERROR 落日志并返回 None，绝不进入 extractall。`project_manager.py` 本身不在白名单、未改动——其暴露面已被本条在路由入口封死（该文件的其它直接调用方不属于本条审计范围）。
- 测试：含 `../evil.txt` 成员的 ZIP 返回 None 且 ProjectManager.load_project 被打桩断言"绝不可被调用"；声明大小超限同样被拒且不触达 PM；正例：安全 legacy ZIP 仍正常路由 PM 并返回 bundle（防护不破坏合法回退）。
