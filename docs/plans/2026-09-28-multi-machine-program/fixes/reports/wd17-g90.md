## 逐条修复

### AUD-34700 [Major/bug] — total_frames 估算把 time_base 当除数 — **FIXED**

- 位置：`src/shared/media/ffmpeg_source.py` `_extract_total_frames`
- 问题：`int(duration_pts * fps.num / (fps.den * time_base))` 把 time_base 当除数，帧数虚高约 1/tb² 倍（tb=1/1000 时虚高 1e6 倍）。
- 修复：`duration_sec = float(stream.duration) * float(stream.time_base)`，`total_frames = int(duration_sec * fps.num / fps.den)`（time_base 作为乘数换算成秒）。
- 测试：`TestAud34700TotalFrames`（3 例）——tb=1/1000、10000 ticks、24fps → 240 帧；断言结果远小于旧值 2.4e8；`stream.frames` 优先路径保留。

### AUD-34701 [Major/bug] — _decode_to_target overshoot 静默返回 — **FIXED**

- 位置：`src/shared/media/ffmpeg_source.py` `_decode_to_target`（对照 `_seek_gop_session` 的正确处理）
- 问题：overshoot（`current_frame > target`）只打日志就 return，`_pending_av_frame` 为空而迭代器已越过目标——`read_frame` 随后交付错误帧内容且帧号错标。
- 修复：oversoot 分支按 `_seek_gop_session` 同一落地语义抛 `SeekError(target_frame, actual_frame)`；并在 except 链中加 `except SeekError: raise`，不再被"Decode error during seek"分支误吞误日志。
- 测试：`TestAud34701OvershootRaises`（3 例）——overshoot 抛 SeekError 且不缓存错误帧；精确落地缓存 `_pending_av_frame`；不可达目标抛 SeekError。

### AUD-34702 [Major/bug] — _main_resync_pts 不随 seek 会话续读更新 — **FIXED**

- 位置：`src/shared/media/ffmpeg_source.py` `_pull_next_frame_from_seek_session`
- 问题：`_main_resync_pts` 写入后从不更新，seek 会话耗尽/出错时 `_resync_main_session_if_needed` 把主会话回卷到 seek 落地点，重放已服务帧。
- 修复：每次从 seek 会话取到帧，把 `_main_resync_pts` 推进到该帧 pts（语义 = "最近已服务帧的 PTS"）。会话耗尽时主会话从最后已服务帧之后续读。
- 测试：`TestAud34702MainResyncPts`（3 例）——逐帧推进回同步点；耗尽后停在 200 而非 seek 落地点 50；`_resync_main_session_if_needed` 丢弃已服务帧、迭代器定位于下一帧。

### AUD-34704 [Major/bug] — planar 模式对 nv12/p010 按纯 planar 提取 — **FIXED**

- 位置：`src/shared/media/ffmpeg_source.py` `_extract_planes_from_frame` + 新增 `_extract_semiplanar_planes` + 模块级 `_SEMIPLANAR_LAYOUTS`
- 问题：`_is_yuv_pixel_format` 声明支持 nv12/p010 等半平面格式，但通用 planar 提取把交织 chroma 平面当单一分量切片（色度错乱）且永远缺 V 平面（hw 帧传回 CPU 后为 nv12 时必现）。
- 修复：新增 `_SEMIPLANAR_LAYOUTS`（420/422/444 家族 × UV/VU 交织序 × 位深）与 `_extract_semiplanar_planes`：Y 平面整幅提取，chroma 平面按 2×chroma_width 样本提取后奇偶列去交织为 U/V；尺寸按 FFmpeg 子采样向上取整；布局不符（<2 平面）抛 `MediaDecodeError` 显式失败。
- 测试：`TestAud34704Semiplanar`（6 例）——nv12 三平面 U=1/V=2 正确分离；nv21 VU 序；p010le uint16/10-bit；nv16 422 全高色度；畸形帧显式报错；布局表覆盖 `_is_yuv_pixel_format` 声明的全部半平面格式。

### AUD-34808 [Major/bug] — release() 回调抛异常状态不落位（双释放） — **FIXED**

- 位置：`src/shared/media/frame_path.py` `DecodeSurfaceLease.release`（对照 `abort`）

### AUD-34901 [Major/bug] — hwaccel 重开失败后 CPU 回退失效 — **FIXED**

- 位置：`src/shared/media/hwaccel.py` `_configure_hwaccel` + 新增 `_reopen_cpu_container`
- 问题：关闭旧容器后 `av.open(hwaccel=...)` 失败，`_try_enable_hwaccel` 捕获异常宣称"回退 CPU"，但容器已关、`_is_open` 仍 True——后续每次读取必抛 `RuntimeError("Container or video stream not initialized")`。
- 修复：hw 重开 + 流校验包在守护 try 中，任一步失败先调 `_reopen_cpu_container()`（CPU 重开、线程配置与父类 `open()` 一致、显式禁用自动 hw 路由）再重抛；CPU 重开也失败则 `_is_open=False`（显式不可用而非假开）。
- 测试：`TestAud34901HwaccelReopenFallback`（3 例，fake av 模块注入 sys.modules）——重开失败后容器恢复为 CPU 容器；回退后读取不再抛 RuntimeError；`_try_enable_hwaccel` 端到端真实回退。

### AUD-34902 [Major/bug] — 解码中途回退 CPU 是假回退 — **FIXED**

- 位置：`src/shared/media/hwaccel.py` `read_next_frame` 异常分支 + `_reopen_cpu_container`
- 问题：只翻转 `_using_hwaccel` 并丢弃迭代器——容器仍是 hwaccel 打开的（继续硬解、错误复现）、迭代器内已缓冲帧被丢（丢帧+帧号漂移）、残留 `_pending_av_frame` 吐陈旧帧。
- 修复：真回退三步——关 hwaccel 容器并清空全部迭代状态（pending/seek 会话）→ CPU 重开（含 `_current_frame` 归零对齐流头，防止 `seek_frame` 的 `current==target` 短路）→ `seek_frame(resync_frame)` 回到失败时正在交付的帧号 → 重读。CPU 重开失败抛 `MediaDecodeError`。
- 测试：`TestAud34902MidDecodeFallback`（4 例）——中途失败触发关容器+重开+resync=5；`_reopen_cpu_container` 清残留状态并归零帧号；resync 缓存落地帧；`fallback_to_cpu=False` 时原样抛 MediaDecodeError。

### AUD-34904 [Major/bug] — Linux QSV 探测回退 ffmpeg 构建项检查 — **FIXED**

### AUD-35101 [Major/bug] — packets() max_packets 守卫在取包后判断 — **FIXED**

### AUD-35120 [Major/risk] — IOSurfaceGLBridge.destroy 无属主线程守卫 — **FIXED**

- 位置：`src/shared/media/macos_vt/iosurface_gl_bridge.py` `destroy`
- 问题：跨线程调用在无 GL 上下文线程上执行 `glDeleteTextures`，静默泄漏全部纹理且 bridge 被误标记已销毁。
- 修复：与 `bind_pixel_buffer`/`initialize` 一致的 fail-closed：初始化状态下非属主线程调用 → 拒绝（记录 `bridge_thread_mismatch`、返回 False、状态不变），真正的销毁由属主线程稍后执行（延迟安全路径）；返回值改为 bool（旧调用方忽略返回值，兼容）。
- 测试：`TestAud35120DestroyOwnerThread`（2 例）——属主线程销毁成功；跨线程（线程池）销毁被拒、ring.destroy 未执行、属主线程稍后可真正销毁。

### AUD-35130 [Major/bug] — 单包提交且把"VT 暂无输出"当 EOF — **FIXED**

- 位置：`src/shared/media/macos_vt/source.py` `_read_next_decoded_pixel_buffer` + 新增 `_finalize_decoded_pixel_buffer`
- 问题：`packets(max_packets=1)` 单包提交，`decode_packet` 返回 None（重排/解码器延迟的正常中间态）被当 EOF——上层解码提前终止，且已消费的包被丢弃（丢包叠加）。
- 修复：三段式——(1) 先非阻塞 `get_decoded_frame(timeout=0.0)` 取上一包的延迟输出；(2) 有界预算（`_MAX_DECODE_PACKETS_PER_READ=32`，防坏流无界 stall）内逐包提交，None 只表示"暂无输出"继续喂包；(3) demuxer 耗尽后终态排空（`get_decoded_frame(timeout=0.2)` 等在飞帧落地；不用 `flush()`——它会清空输出队列反而丢尾帧）。帧时间线元数据补齐抽到 `_finalize_decoded_pixel_buffer`（pts→frame_index→time_seconds，异常防御收窄为 AttributeError）。
- 测试：`TestAud35130FeedUntilOutput`（6 例）——首包无输出继续喂包直至取帧（2 包全消费、无丢包）；延迟输出直接从队列取（不消费新包）；耗尽后终态排空取回尾帧（0.2s 排空等待）；真 EOF 返回 None 语义保留；未打开返回 None；预算有界（32 包封顶）。
