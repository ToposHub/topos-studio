## AUD-21901（Major/bug）转录路由追踪把终态质量归因到中间步骤

**状态：FIXED**

**根因**：`_infer_steps_from_selection` 只掌握终态质量（最终入库 transcript 的
`_analysis_quality`），却把它塞给每个反推步骤：`qwen3_asr_demucs_v4` 时 Qwen
原音频步拿到 Demucs 路径的最终质量并给出"高置信"类结论；`whisperx_fallback`
同理；`low_confidence` 分支的 Demucs 未胜出步质量编造 0.0。

**修复**（analysis_skills.py）：
1. `TranscriptRouteStep.quality` 类型改为 `float | None`——None 明确表示
   "该步质量未持久化、无法从终态反推"；`to_public_dict` 对 None 序列化 None。
2. 反推规则改为只有**最终选用**的步骤才使用终态质量：Demucs 胜出 → Qwen 步
   quality=None、note"质量未持久化（低于路由要求才转入后续路径）"；WhisperX
   回退 → Qwen 步 None；low_confidence → Demucs 尝试步 None（不再编造 0.0）、
   note 注明未持久化。`qwen3_asr_original`/`low_confidence` 选中时 Qwen 步
   质量仍为终态值（选中路径质量==终态质量，语义正确）。
3. provider 持久化路径（`extra["route_steps"]`）对 quality 做容错解析
   （None/畸形值 → None，不再 float() 崩溃）。

**测试**：`TestAud21901TranscriptTraceQuality` 5 用例（demucs/whisperx/low_
confidence/selected/公共字典 None 序列化）。

## AUD-21905（Major/bug）run 取消在 invoke 返回后不再传播到生成 job

**状态：FIXED**

**根因**：`poll_cancel_to_job` 只在 invoke 同步段（step 9）调用一次；真实
provider 进入 shared worker 后 run 的 cancel token 无任何链路翻成
`job.request_cancel()`，且 worker 回调里 `finish(success=True)` 优先于
cancel_requested → 终态 SUCCEEDED。

**修复**（generation_adapter.py）：
1. 构造器订阅 `runtime` 的 `RunEventKind.RUN_CANCEL_REQUESTED` 事件（新增
   `_on_run_cancel_requested` → `bridge.propagate_cancel(run_id)`），取消即时
   传播到已 bind/track 的生成 job；订阅回调带异常边界（传播失败只记日志，
   不打断发布方）。新增 `close()` 退订。
2. `_collect_generation_outcome` 在最终 `finish` 前再查一次 `is_cancelled`：
   已取消 → `poll_cancel_to_job`（补协作取消）+ `finish(success=False)` →
   终态 CANCELLED（worker 回调与同步路径共用此收尾）。

**测试**：`TestAud21905CancelPropagation`（异步路径：invoke 返回后 cancel →
job.request_cancel 被调；job 跑完 succeeded → run 终态 CANCELLED；
close 退订语义）。

## AUD-21906（Major/bug）job 的 cancelled 终态被一律映射为 FAILED

**状态：FIXED**

**根因**：`_collect_generation_outcome` 只判 `status_val == "succeeded"`，
job 面板直接取消（`JobStatus.CANCELLED`）时 run 未置 cancel token →

RunRecord/rollout 指标中不再混同。

**测试**：`TestAud21906JobCancelledTerminal`（cancelled→CANCELLED+诊断；
failed→FAILED 原语义保留）。

## AUD-22017（Major/bug）urllib 默认跟随重定向且保留 Authorization 头

**状态：FIXED（证据首选方案：自定义 opener 禁用重定向）**

**根因**：`urllib.request.urlopen` 走默认全局 opener，CPython 重定向处理把
Authorization（Bearer api_key）原样转发到 Location 目标（含 https→http 降级，
绕过构造期 localhost-only 校验）。

**修复**（mcp_http_transport.py）：
1. 新增 `_NoRedirectHandler(urllib.request.HTTPRedirectHandler)`，
   `redirect_request` 恒返回 None（30x 交还为 HTTPError）。
2. 构造器建**实例级** opener（`build_opener(_NoRedirectHandler)`），`_post`
   改用 `self._opener.open(req, timeout=...)`——不用 install_opener，不污染
   进程全局状态。
3. `_post` 的 HTTPError 分支对 30x 显式 fail-closed：抛
   `McpHttpTransportError`（含状态码与 Location 摘要），凭据绝不被转发。

**既有测试适配（非行为翻转）**：`tests/edit/ai_editing/test_mcp_vision_gateway.py`
两个用例原 monkeypatch 模块级 `urllib.request.urlopen`——传输层换 opener 后
该缝隙失效（且会真联网）。改为构造 `_StubOpener` 替换实例 `_opener`
（同一 `(request, timeout) → response` 契约），断言不变（Mcp-Method/Mcp-Name/
Mcp-Session-Id/Authorization 头与 metadata 全部原样通过）。

**测试**：`TestAud22017RedirectCredentials`（本地 127.0.0.1 HTTP 服务返回
302 → McpHttpTransportError 含"重定向"；重定向目标零请求、零 Authorization）。

## AUD-22101（Major/risk）不可信 JSON Schema 可导致校验线程资源耗尽

**状态：FIXED**

**根因**：`validate_json_schema` 只限深度（max_depth=32），不限
allOf/anyOf/oneOf 分支数与总工作量（分支数^深度级组合爆炸），`pattern`
交给无超时的 `re.search`。

**修复**（mcp_protocol.py）：
1. 单次校验穿线共享 `_SchemaBudget`（入口创建、全部递归路径传递）：
   访问节点总数超 `_MAX_SCHEMA_NODES=2048` 即拒绝（"complexity budget
   exceeded"）——组合爆炸的总求值次数被线性封顶。
2. 单个组合关键字分支数超 `_MAX_SCHEMA_VARIANTS=64` 直接拒绝。
3. `pattern` 长度超 `_MAX_SCHEMA_PATTERN_CHARS=256` 直接拒绝（超长回溯型
   pattern 不进 `re.search`）。
4. 常规 schema 语义不变（既有 63 例 ai_harness 套件全绿）。

**测试**：`TestAud22101SchemaComplexity`（分支数上限 / 8^8 组合爆炸 <5s 拒绝 /
超长 pattern / 正常 schema 双向 sanity）。

## AUD-22102（Major/risk）close→start 后旧 stdout 泄放线程向新队列投毒 None 哨兵

**状态：FIXED**

**根因**：`_drain_stdout` 的 finally 回读**当前属性** `self._stdout_queue`；
close 终止旧进程后旧线程惊醒，若已重新 start（`_spawn` 已换新队列），None
落入新队列 → 新 `_roundtrip` 误判"子进程已退出"。

**修复**（mcp_stdio_transport.py）：`_spawn` 把 proc 与新队列捕获为局部变量，
以线程参数传入 `_drain_stdout(proc, out_queue)`——哨兵只落本代队列；
`_roundtrip` 在入口捕获 `out_queue = self._stdout_queue`，等待固定在本代
队列上（重启不跨代消费）。

**测试**：`TestAud22102QueueGenerationIsolation`（单测：旧线程哨兵只进旧
队列；集成：真实子进程 close→start 重启后仍正常应答，含 0.2s 投毒窗口）。

## AUD-22103（Major/perf）send_request 全程持 RLock，close() 最长阻塞 180s

**状态：FIXED**

**根因**：`close()` 与 `send_request` 竞争同一把 `self._lock`；`_roundtrip`
等满 request_timeout（默认 180s）期间 close 排队等锁，应用退出路径卡死。

**修复**：
1. `close()` **不再获取** `self._lock`：置位 `_started=False`/`_mode=None`
   后直接 `_terminate_current_process()`——终止子进程使泄放线程因 EOF 入队
   None 哨兵，阻塞中的 `_roundtrip` 立即失败返回（docstring 注明与并发
   start 的竞争语义：close 获胜，start 握手失败并自清理）。
2. 新增 `_proc_lock`（仅护 `_proc` 取放的短临界区，锁序恒 `_lock →
   `_proc_lock`），`_spawn` 置入与 `_terminate_current_process` 摘取都在其内
   原子完成——杜绝并发 close+start "清掉新进程却不终止"的孤儿进程窗口。

**测试**：`TestAud22103CloseDoesNotWaitForRequestLock`（他线程持 `_lock`
3s 期间 close <1s 返回且 `_started=False`）。

## AUD-22104（Major/risk）_stdout_queue 无界，空闲期通知无限累积

**状态：FIXED**

**根因**：消费只发生在 `_roundtrip` 等待期，两次请求之间无人消费；行为异常
的 server 持续输出通知 → 进程内无界内存增长。

**修复**：队列改为 `queue.Queue(maxsize=_STDOUT_QUEUE_MAX=1024)`；泄放线程经
`_put_stdout` 有界入队——满时丢最旧并计数（`_dropped_stdout_messages`，

## AUD-22105（Major/risk）无 deadline 且无取消源时 invoke 等待循环永久占锁

**状态：FIXED（本地看门狗方案——plugin_isolation.py 为条目行内明示目标）**

**根因**：`ProcessIsolatedPlugin.invoke` 的退出条件只有收到消息 / 进程死亡 /
取消 / 超时；`PluginExecutionPolicy.timeout_seconds` 默认 None（registry 侧
deadline 随之 None）且 `context` 可为 None——子进程活着但不回包时调用线程在
20ms 轮询上永久自旋且全程持有 `self._lock`，同插件 `health()/deactivate()/
activate()` 全部陪死。

**白名单说明**：任务行内白名单未列 plugin_isolation.py，但本条目（计划表
:832）行内目标即该文件且任务指示"以行内为准"，故按条目行内目标执行修复。

**修复**（plugin_isolation.py）：
1. 新增 `_watchdog_budget_seconds()`：外部 deadline 缺失时的看门狗预算，
   优先级 `policy.timeout_seconds`（activate 时捕获的 context.policy）>
   构造参数 `invoke_timeout_seconds`（默认 `_DEFAULT_INVOKE_TIMEOUT_SECONDS`
   =600s；宿主显式传 None 才不限时）。
2. `invoke` 把看门狗预算换算成本地 deadline，随请求发给子进程
   （`remaining_seconds`，协作插件可先自行超时），等待循环每轮检查——到期
   `_terminate_locked()` + 抛 `PluginInvocationTimedOut`，锁必然释放。
3. 构造参数校验（正数或 None），类 docstring 补契约。

**测试**：`TestAud22105InvokeWatchdog`（预算解析三级优先级 / 非法参数拒绝 /
真实子进程：卡死 invoke 1s 看门狗终止 + 异常 + 锁释放后 health() 立即返回）。
