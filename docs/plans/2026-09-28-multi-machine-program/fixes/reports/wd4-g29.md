## 设计决策与残留说明

- **AUD-11500 "尺寸未知"的取舍（有意为之，需评审知悉）**：审计给出两个方向——"未知即不兼容"或"调用点提供真实尺寸"。纯 strict 方案实测会关闭默认 CONSERVATIVE 模式下绝大多数真实合成的融合（`estimated_bbox` 仅在带用户 ROI 的 preview 请求里存在——`render_scheduler.plan()` 的 ROI 传播被 `roi_enabled` 门控；`timeline_clip_input` 无尺寸参数、`image_input` 加载前 width/height 为 0——中间实现曾因此使 `test_pass_fusion_execution` 两条用例失败，已回退验证）。最终采用分层方案：已知尺寸（cache/bbox/源参数）之间不一致 → 拒绝（检查不再空转，且预览 ROI 路径、参数化源、再分析场景真实生效）；全未知 → 按**融合资格不变量**（线性链、单输入、roi_expansion==0 的逐像素级 → 每级保尺寸）容忍，已在 `_check_size_compatibility` docstring 显式成文。若未来放宽融合资格（允许改变尺寸的节点类型），该不变量失效，需将未知改回拒绝。
- **AUD-4401 的 comp_asset_id 来源现状**：`page.get_composite_data()`（NodeGraph.to_dict）当前代码路径本身不含 `comp_asset_id` 键（该身份字段位于 EditProject 的 composition 记录，经 `_ensure_comp_identity` 注入加载载荷）；发布函数按原样从序列化结果读取（行为不变），本条只消除"每帧全图序列化"的性能危害，不改变身份解析语义（语义属 composite_page/edit 域，超出本批白名单）。
- **AUD-11603 raise 与 node_engine 回退的交互**：`NodeGraph.deserialize_from_bytes`（node_engine.py:2276-2284，白名单外）存在 `except Exception` 后将 delta 信封当全量数据重试的预存结构；版本不匹配的 ValueError 在该入口会被该预存结构吞掉（退化为空图/from_dict 失败，而非静默套用陈旧 delta——仍优于原损坏路径）。模块级 `load_incremental` 的直接调用方（本批测试与未来调用方）获得明确的 ValueError。
- **AUD-4602 方案选择**：审计给出"拒绝烘焙多输出目标"或"按端口生成独立序列"二选一；取拒绝方案（烘焙 UI 尚未接线，A6 里程碑，单一图像序列是现有 BakePlan 数据结构前提；按端口多序列属特性扩展）。当前仓库所有节点类型实际均为单输出（keyer/shuffle 均只有 "result"），该校验是面向未来节点类型的前置守卫（测试用桩图覆盖）。
