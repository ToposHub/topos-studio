## 逐条状态

### AUD-38700 — FIXED
`resolve_debayer_params` 整对象优先级：RawParams 中性默认静默覆盖 TRWM as-shot WB/黑位。

修复：新增 `_raw_params_all_neutral()`（camera_gamut_matrices.py）判定 clip RawParams 是否
完全未被用户调过（数值全中性 + color_space="native"/空 + gamma="preview-2.2"/空 +
display_ootf=True）。全中性对象按"未调过 RAW 面板"处理，走 TRWM as-shot 基线；任一字段
被用户改过则整对象优先——这是 `tests/media/test_cfa_gamut_debayer.py::
TestResolveDebayerParams.test_user_over_trwm` 锁定的既有语义（逐字段混合优先会破坏该
锁定契约，故采用"全中性检测"而非逐字段回退）。

### AUD-38702 — FIXED
black_level 应用点与 GPU shader 不一致（CPU 逐平面"先减后平均" vs GPU"先平均后减"）。

修复：`debayer_cfa_planes`（cfa_cpu_debayer.py）的黑位减除移到 `_assemble_rgb` 双线性
组装与奇数尺寸截取之后、逆曲线之前，与 GPU shader（cfa_gpu_debayer 两模板 150-153/
248-250 的 fetch→插值→减黑位→逆曲线顺序）同点同式。`max` 与平均不可交换，跨黑位采样
（部分采样低于黑位）的阴影区两链漂移随之消除；黑位以上区域数值不变（有回归测试）。

### AUD-38705 — FIXED
`upload_and_render` 的 viewport 参数被 `fbo.use()` 覆盖，形同虚设。

修复：顺序改为 记录前值 → `fbo.use()` → 设定请求 viewport → 渲染 → finally 恢复调用前
viewport（cfa_gpu_debayer.py）。此前 ctx.viewport 在 fbo.use() 之前设置，被 ModernGL 的
FBO viewport 重绑覆盖。

### AUD-38801 — FIXED
帧去重标记的检查与置位不原子（check-then-act 竞态），同帧可被重复解码。

修复：出队与在途标记合并进同一 `_request_lock` 临界区——基类 `get_next_request` pop 的
同时 `_decoding_frames.add((gen, frame))`；`MasterDecodeWorker.get_next_request` 对
master 请求同样处理（锁序 `_master_request_lock` → `_request_lock`，全库无反向嵌套）。
`_run_loop` 改为消费"已标记"的请求，generation 过期跳过与解码完成两路径均负责 discard
标记。`request_frame`/`request_master_frame`/`request_prefetch` 的检查点（481-491/
1057-1064）语义不变，窗口已闭合。

### AUD-38802 — FIXED
`stop()` 超时后状态 ERROR，再次 `start()` 清除停止事件并产生双工作线程。

修复：`start()` 在 `_state_lock` 内先检查残留 `self._thread.is_alive()`——仍存活则记
error 日志并拒绝启动（返回 False），不清 `_stop_event`、不建新线程；旧线程自行退出后
允许正常重启（decode_worker.py）。

### AUD-38905 — FIXED
`shutdown()` 全库无调用点，卸载视频后独立解码会话泄漏。

修复（白名单内自洽方案）：`clear()`（控制器在换素材/卸载视频/开始播放时都会调用，
见 file_controller.py:4909、6774；layer_controller.py:1876）现在同时把"关闭帧服务独立
会话"任务排入后台 worker 执行（close 是阻塞 I/O，不碰 UI 线程）。引入 `_clip_epoch`
世代号：关闭任务携带入队时的世代号，若排队期间又有 `schedule()` 重开会话（epoch 已
变）则自动放弃，不会误关新会话。`_ensure_clip` 每次打开新会话时 epoch+1；`shutdown()`
保留为同步退出路径并复用 clear()。
说明：彻底的"unload 时同步关闭"调用点在 `src/app/controllers/file_controller.py:6774`
（白名单外，未改动）；本修复使泄漏经由既有 clear() 调用点兜底闭合，无需越界改动。
代价：开始播放→再暂停 会重开一次独立会话（后台线程执行，不阻塞 UI）。

### AUD-39000 — FIXED

### AUD-39103 — FIXED
并发 open_clip 共享路径在源打开完成前返回 clip_id，打开失败时吞掉引用并留下死 clip_id。

修复：`ClipSession` 新增 `open_event`（打开完成事件）。共享路径改为：会话在途
（open_event 未置位）→ 锁外等待 → 重新裁决；打开成功（事件已置位且 open_error 为
None）→ 加引用返回；打开失败（open_error 有值或会话已被清理）→ 自建新会话（其打开
同样失败时向调用方抛 MediaOpenError，绝不返回死 clip_id）。创建者在成功/失败两条路径
上置位 open_event；失败时先记 open_error 并唤醒等待者再做清理。两个 open 入口同语义。

### AUD-39106 — FIXED
update_disk_proxy_info/_create_memory_proxy_source 对可能已被关闭的会话赋新源，新源
永不释放。

修复：`ClipSession` 新增 `sources_closed` 标记（`_close_clip_sources` 结束时置位）。
- `update_disk_proxy_info` ready 分支：赋值临界区内校验 `self._clips.get(clip_id) is

  代理源，不赋值）；活跃会话（含直调未注册场景）赋值行为不变；
- `_schedule_deferred_memory_proxy_source` 的回填增加 `not sources_closed` 防护。

### AUD-39200 — FIXED
master 队列容量上限永不可能生效，可无界增长。

修复：`_enqueue_master` 超容量时按 FIFO 淘汰队首（最旧）帧并释放 GPU 帧、计入
`master_dropped`。根因：enqueue 按 `can_drop` 路由，master 队列成员恒为
can_drop=False，旧的"只丢 can_drop 帧"分支永不可达（保留该偏好无意义，已按审计
"路由依据 344-348"改为纯 FIFO）。设计语义"master 不丢目标帧"仍成立——消费方正常
及时出队时上限不触发；只有落后超过 max_master_size（默认 3）才淘汰早已无人认领的
最旧帧。既有 `test_master_queue_preserves_frames`（断言 `<= 4`）与
`test_master_queue_no_dropping`（断言 enqueued > 0）不受影响。
