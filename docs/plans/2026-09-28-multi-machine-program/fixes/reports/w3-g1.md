## AUD-16201 — FIXED

**位置（修复前）**：AddTransitionCommand.apply / .undo、RemoveTransitionCommand.apply、
UpdateTransitionCommand.apply / .undo 共 5 处手工 `EditTrack(...)` 构造
（原行 11106-11120、11159-11173、11432-11446、11641-11655、11685-11699）。

**根因**：转场三命令在 apply/undo 中用仅携带 13 个字段的手工构造器重建轨道，
`strip_eq / effect_chain / automation / automation_mode / sends / output_bus_id /
is_bus / is_sync_locked / color / stem_group / subtitle_clips / caption_metadata /
track_role / is_visible` 等 14+ 字段全部回落默认值（与 1247-1251 行既有修复
注释指认的缺陷模式同源）。

**修复**：5 处统一替换为不可变更新方法
`new_track = track._rebuild(transitions=new_transitions)`（`EditTrack._rebuild`
集中传递全部 22 个字段，新字段遗漏由 `_rebuild` 兜底；该写法在
commands.py 已有先例，如 `track._rebuild(is_locked=...)`）。
每处附中文审计修复注释。其余 6 处手工 `EditTrack(` 构造（677/1048/7636/
9139/9743/9772）均为"新建空轨道"（fresh ID、`clips=()`），无字段可丢，
与审查认定一致，未改动。

**回归测试**：
`TestTransitionCommandsPreserveTrackFields`（5 个用例）——构造带满非默认
字段的音频轨（strip_eq=3-band EQ、automation=volume KeyframeTrack、
sends、output_bus_id、automation_mode="read"、stem_group、color、
is_sync_locked=False 等），对 Add/Remove/Update 三命令的 apply 与 undo
逐一断言 24 个轨道字段（`_TRACK_FIELDS` 清单）逐项相等。

## AUD-16202 — FIXED

**位置（修复前）**：BatchDeleteCommand.undo，原行 10821。

**根因**：`MoveClipCommand.create(track_id, clip_id, new_start, old_start)`
第 3 参是 `new_start`。该处传入 `old_start`（原始位置）作 new_start、
当前位置作 old_start 后误调 `move_cmd.undo`——undo 的语义是恢复到
`old_timeline_start`（即当前位置），片段回移退化为 no-op；随后按原位恢复
被删片段与未移回的片段区间重叠，`with_clip_added` 抛 ValueError 使 undo
中断在半执行状态。

**修复**：
1. 10821 行改为 `current_timeline = move_cmd.apply(current_timeline)`，
   与 RippleDeleteCommand.undo（10249-10255）的正确写法一致，附注释。
2. **根因补全**（编写回归测试时发现，同一发现的影响面）：apply 原在删除
   循环内逐个采集 undo 快照，多选同轨波纹删除时后续片段拿到的是已被前
   一次波纹左移的位置——undo 恢复重叠崩溃依旧，且 `merged_ripple_spans`
   收到错误跨度导致跨轨 sync-lock 跟随位移算错。现改为在任何删除发生
   之前从原始时间线采集 `_deleted_clips` 与 `_moved_clips_per_track`
   （与 `create()` 工厂的预采集语义对齐），删除循环只负责执行删除。

**回归测试**：`TestBatchDeleteRippleUndo`（3 个用例）——单片段波纹删除
undo、多选同轨波纹删除 undo、链接 A/V 对跨轨波纹删除 undo，断言跟随
片段移回原位、被删片段恢复、无重叠异常。（修复前旧代码在这些用例上
抛 `ValueError: Clip overlaps`。）

## AUD-16203 — FIXED

**位置（修复前）**：OverwriteClipCommand.undo，原行 12275-12286。

**根因**：undo 的"清除分裂残留"启发式删除所有
`clip_id not in original_ids and clip_id not in modified_ids and
asset_id != self.asset_id` 的片段——`_modified_clips` 只含与覆盖区间重叠
的片段，同轨上 playhead 之前/覆盖终点之后的所有其他素材（asset 不同）
都被当作"分裂残留"整体删除，撤销一次覆盖即清空整条轨道的无关内容。
另：恢复顺序（先还原原片段、后删残留）会在中间分裂场景触发
`with_clip_added` 重叠校验抛错。

**修复**：
- `OverwriteClipCommand` 新增字段 `_split_clip_ids: tuple[str, ...] | None`。
- apply 用轨道片段 ID 的前后差集（`post_ids - pre_ids`）精确识别本次操作
  新建的片段：其中 timeline_start==playhead 且 asset 匹配者为插入片段
  （`_inserted_clip_id`，含防御回退），其余即分裂残留白名单
  （`_split_clip_ids`）。插入片段识别也因此从"同 asset+同起点"启发式
  收紧到"新建 ID 集合内匹配"，排除同轨既有同素材片段被误选。
- undo 重排为：删插入片段 → 按白名单删分裂残留 → 还原原片段（先删
  残留避免重叠校验崩溃）；删除旧启发式块。白名单为 None（旧序列化
  历史）时不删任何片段——宁可留下残留也不误删用户内容。
- `to_dict`/`from_dict` 同步携带 `split_clip_ids`，序列化往返不丢。

**回归测试**：`TestOverwriteUndoSplitWhitelist`（4 个用例）——
未受影响片段保留 + 分裂残留清除 + 原片段恢复原窗口、完全覆盖片段
恢复、playhead 处同素材既有片段不被误删、白名单序列化往返。
