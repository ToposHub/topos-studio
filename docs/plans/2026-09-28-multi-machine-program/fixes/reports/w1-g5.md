## AUD-24700 [Critical/bug/M] — FIXED

**问题**：RAW_VIEW 第 6 步（饱和度/色彩增强）`vec3 hsv = rgb2hsv(clamp(color, 0.0, 1.0));` 先把颜色夹到 [0,1] 再做 HSV 往返，`color = hsv2rgb(hsv)` 整体替换——>1.0 的高光与 <0.0 的负值（lift 可产生）被永久截断，且后续 log gamma 编码（依赖 >1 输入）失效。预览与全分辨率导出（image_engine 写 f4 float 纹理）同样受害。

**修复**（shaders.py RAW_VIEW_FRAGMENT，现约 485-506 行）：改为保幅度的 HSV 分离，去掉 clamp：

```glsl
vec3 negative_excess = min(color, vec3(0.0));
vec3 hsv = rgb2hsv(color - negative_excess);
... // 仅调整 hsv.y（饱和度/vibrance 逻辑不变）
color = hsv2rgb(hsv) + negative_excess;
```

依据：该 shader 自带的 `rgb2hsv` 的 V 通道就是 max 分量、`hsv2rgb` 按 V 等比缩放输出——对**任意幅度**的非负颜色，HSV 往返是恒等变换，即「按 max 分量缩放的 HSV 分离，饱和度调整后恢复原幅度」；负值 HSV 无法表示，用 `min(color, vec3(0.0))` 分离出来调整后原样加回（与同文件 `apply_lut_hdr_safe` 的域外补偿同模式）。SDR 像素（全在 [0,1] 且无负值）行为与旧实现完全一致，无视觉回归。

**测试证据**（`tests/color/test_fix_shaders_tracking_aud.py::TestAud24700HdrSafeSaturation`，6 用例）：
- 源码级：饱和度块（第 6 步注释到第 7 步注释之间，去注释后）不再含任何 `clamp(`；含 `min(color, vec3(0.0))` 与 `+ negative_excess`。
- 算法级（逐行镜像 shader 内 rgb2hsv/hsv2rgb 公式的 Python 实现）：
  - 中性参数（saturation=1, boost=0）下对 HDR（max 至 12.5）与含负值输入均为恒等变换（旧实现会 clamp）；
  - saturation=0.5 时 max 分量（高光幅度）保持不变且仍 >1（如 (2,1,0.5)→(2,1.5,1.25)）；
  - 全负像素 (-0.3,-0.1,-0.05) 不被夹成 0；
  - 降饱和后通道序（色调方向 R>G>B）保持。

## AUD-24701 [Critical/bug/M] — FIXED

**问题**：锐化/中间细节的 8 次邻域采样 `get_linear_color(texture(u_texture, uv).rgb)` 缺少中心像素（原 405-423 行）的 BGR swizzle 与 sRGB→线性→ProPhoto 预处理。sRGB 源 + sharpness>0 时 Laplacian 混合「线性 ProPhoto 中心值」与「sRGB gamma 域邻域值」，均匀区域整体压暗；BGR 视频帧邻域 R/B 颠倒产生彩边；导出路径同样受害。

**修复**（shaders.py RAW_VIEW_FRAGMENT，现约 400-430 行）：
- 新增 `const mat3 SRGB_TO_PROPHOTO`（单一全局定义，消除原 main 内局部矩阵）；
- 新增 `vec3 prepare_color_space(vec3 c)`：BGR swizzle → `srgb_to_linear` → ProPhoto 矩阵，与原中心像素路径逐步等价；
- 新增 `vec3 fetch_prepared(vec2 uv)` = `prepare_color_space(texture(u_texture, uv).rgb)`；
- main 中心像素改为 `vec3 color = prepare_color_space(tex_color.rgb);`（alpha 仍取 `tex_color.a`，不受影响）；
- 8 处邻域采样全部改为 `get_linear_color(fetch_prepared(...))`。

中心与邻域现在走同一入口，色彩空间严格一致；矩阵只保留一份，杜绝两份拷贝漂移。行为变化仅出现在原来就是错误路径的 sRGB/BGR + 锐化组合上（该组合此前必然渲染错误）。

**测试证据**（`TestAud24701NeighborhoodColorSpace`，5 用例）：`get_linear_color(fetch_prepared(` 恰好出现 8 次；`get_linear_color(texture(` 不再出现；中心像素使用 `prepare_color_space(tex_color.rgb)`；helper 函数体含 `u_bgr_swizzle`/`srgb_to_linear`/`SRGB_TO_PROPHOTO`；`SRGB_TO_PROPHOTO` 恰好 2 次（定义 + 使用）且无 `mat3 srgb_to_prophoto` 局部残留。

## AUD-24904 [Critical/risk/M] — FIXED

**问题**：`_cancel_workers` 中 `self._workers.pop(key, [])` 后局部列表 `workers` 在函数返回时释放；`wait(wait_ms)` 超时的 worker（parent=None，无其他强引用）被 GC 析构，而析构**运行中**的 QThread 是未定义/致命行为（进程 Abort）。原注释「自然泄漏到进程退出」并不成立。

**修复**（tracking_service.py）：
- `__init__` 新增 `self._zombie_workers: List[object] = []`（约 80-85 行），仿 image_engine 的 `_TERMINATED_THREADS`（P1-THREAD-01 同源防御）；
- `_cancel_workers`（约 280-301 行）：超时分支追加 `self._zombie_workers.append(worker)`，日志措辞同步改为 "keeping a reference until it exits"；
- 新增 `_prune_zombie_workers()`：按 `w.isRunning()` 过滤，在每次 `_cancel_workers` 入口与 `_drop_worker`（任务收尾）时调用——worker 自行退出后引用最终被回收，保活列表不会无限增长；卡死 worker 则泄漏到进程退出（与原设计意图一致，只是真正兑现了「不析构运行中线程」）。
- `tracking_worker.py` 无需改动：引用保留责任在持有方（服务），证据报告也已把它定位为「调用方缺陷」。

语义不变项：`is_running`/`running_keys` 仍只看 `self._workers`；正常路径（wait 成功）不产生保活条目。

**测试证据**（`TestAud24904ZombieWorkerKeepAlive`，4 用例，可控假 worker 驱动）：
- wait() 超时后 `cancel()`：worker 被取消、`is_running` 为 False，且仍在 `service._zombie_workers` 中（强引用保留）；
- worker 退出（isRunning=False）后再次 start 触发 prune：保活列表清空；
- 正常取消（wait=True）从不进入保活列表；
- `shutdown()` 超时路径同样保留引用且 `running_keys()` 为空。

## 既有测试失败的甄别（非本批回归，附证据）

`tests/color/test_tracking_worker_lifecycle.py` 在本机当前工作区以 exit 132（SIGILL）崩溃（收集 5 项后在首个用例中静默中止）。甄别过程：

1. **不在改动链上**：该测试直接驱动 `TrackingWorker`（不经 `TrackingService`），import 追踪确认其导入闭包不含 `shaders.py` 与 `tracking_service.py`；
2. **回滚对照**：把本批两个改动文件临时 `git checkout HEAD --` 还原后重跑，**仍然 exit 132**（随后已恢复本批改动，diff 校验一致）；
3. **原生崩溃定位**：macOS DiagnosticReports 显示两份崩溃栈完全相同——`TrackingWorker` 线程内 `np.linalg.inv`（`_umath_linalg` → OpenBLAS `dgesv_64_` → `dgetrf_parallel`）`EXC_BAD_ACCESS / KERN_INVALID_ADDRESS`，即 numpy/OpenBLAS 在二级线程内的原生缺陷，与 Python/GLSL 层改动无关；
4. **pristine 对照**：`git worktree` 检出干净 HEAD：用仓库现存（8 月 27 日）fixture 复现同样崩溃；删除 gitignored 的 `tests/test_videos/tracking_fixtures/` 让其重新生成后 pristine 通过（5 passed）。即该失败在本批改动之前就存在于本机环境（fixture 数据 + OpenBLAS 线程问题），fresh fixture 下工作区与 pristine 的差异表现指向该原生 bug 的时序/内存布局敏感性，而第 2 条回滚对照已排除本批因素。

结论：不构成本批 BLOCKED——失败测试不覆盖本批改动的代码路径，本批交付的 37 个测试全绿。建议另行立项处理（重生成 tracking fixtures / 排查 OpenBLAS 线程安全，如设 `OPENBLAS_NUM_THREADS=1` 或将 `np.linalg.inv` 换成线程内串行求解）。
