## 1. AUD-7906 / AUD-7907 — cv2 未导入（Critical）

**验证属实**：`git show HEAD:…ai_compute_manager.py` 确认模块级无 `import cv2`，`_generate_preview` / `_prepare_outpaint_input` 也没有函数内局部导入（局部导入只存在于 `_process_tiled`/`_run_inference`/`_postprocess`/`_run_generate_inference`/`_generate_placeholder`/`_run_custom_generate_model` 六个方法）。cv2 为声明依赖（requirements.txt:21 `opencv-python>=4.11.0`，venv 内 4.11.0 可用）。

**修复**（按审查建议"模块级导入 + 顺带清理重复局部导入"）：
- 模块顶部 try/except 守护导入 cv2，失败时 `cv2=None` 并记录 `_CV2_IMPORT_ERROR`；
- 新增 `_require_cv2()`：cv2 缺失时抛出带可操作信息（`pip install opencv-python`）的 ImportError；
- `run()` 首行调用 `_require_cv2()` 作为全节点类型的快速失败门禁 → 缺失时经既有 error 信号上报明确降级信息（不再深埋 NameError）；
- 移除六个方法内的冗余局部 `import cv2`。

**测试**：`TestCv2Import` 5 例——模块绑定 cv2、`_prepare_outpaint_input`（修复前必然 NameError）输出形状/mask 语义、`_generate_preview`（fake ONNX session）预览尺寸、`_require_cv2` 缺失时 ImportError 信息、`run()` 缺 cv2 时 error 信号含 "opencv-python"。

## 2. AUD-80001 — 跨瓦片复用首瓦片裁剪的 SOURCE 缓存（Critical）

**验证属实且比审查描述更深**。逐行核实 + GL 实测（headless GL 4.1 / AMD RX 6900 XT）确认两条污染通道，均因 eval-cache key 不含瓦片几何（ROI 后缀仅 PREVIEW+viewer_roi 启用）：

1. **SOURCE 条目**（审查所述）：源节点 key 的输入元数据为空（如 `constant:bg:6e9c…:():E:rm=export:qpfinal`），每个瓦片重算出的 key 相同；`clear_export_cache()` 只清 EXPORT 类别（cache_manager.py:458-468），SOURCE 受保护存活 → 瓦片 2+ 命中首瓦片裁剪纹理。缓存追踪实测（改造前）：瓦片 2 的 constant 直接 HIT 瓦片 1 条目。
2. **evaluator key memo（dirty-skip）**：`base_evaluator.py:679-692` 的脏跳过路径按 `_node_cache_keys` 备忘的 key 取条目而不重算 key，output 节点的全帧 passthrough EXPORT 条目同样泄漏给每个瓦片。

**修复**（全部落在 `composite_export_renderer.py` 白名单内）：
- 新增 `_clear_tile_scoped_cache()`：对 `_SOURCE_NODE_TYPES ∪ _AI_NODE_TYPES` 的节点调用公开 API `invalidate_node()`；并清空 evaluator 备忘 `self._node_cache_keys`（该 memo 挂在渲染器自身 mixin 上，白名单内可及），迫使每瓦片按实际（裁剪后）输入重算 key → miss → 全链路重求值。
- 三条瓦片循环（`_render_tiled_gpu_stitch` / `_render_tiled_with_plan` / `_render_tiled`）改为**循环顶部**调用该 helper（覆盖首瓦片命中上一 pass 残留条目的场景）；`finally` 中再调用一次 + `clear_export_cache()`，防止持久渲染器上末瓦片裁剪条目毒化后续全帧 EXPORT 求值。
- **必要的配套修正**：每瓦片正确重求值后，output 节点产出的是"整帧尺寸、瓦片内容落在全局坐标"的结果纹理（实测 result.width=2560 而瓦片仅 512/2048 宽）。原拼接 UV 与 `_readback_tile` 裁剪都按 padded_roi 相对坐标计算，只匹配瓦片尺寸结果 → 采样/裁剪到错误区域。修正：检测结果尺寸 ≥ 输出尺寸时按全局 output_roi 子矩形采样（GPU-stitch 的 u/v offset）与裁剪（`_readback_tile` 新增 `output_w/output_h` 参数）。

**修复过程的关键取舍（记录给后续批次）**：
- 审查建议的方案 (2) 全量 `cache_manager.clear()` 瓦片间清理**实测不可用**：SOURCE 逐出 + EXPORT 纹理同期回池后，下一瓦片求值复用回收纹理，GPU-stitch 路径右半画面稳定变暗至 ~1/3 linear（机械复现：全清 → 右半 (59,82,113)，单独清 SOURCE 或单独清 EXPORT 均正常）。根因在纹理池/fb_manager 回收链路（`gpu_resource_pool.py`，白名单外），故 EXPORT 条目改为 pass 内保留（其 key 嵌入源裁剪纹理 id，SOURCE 重求值后必然 miss，不会跨瓦片命中）、pass 后 finally 统一清理。
- 既有 `test_preview_large_frame_strategy.py` 固态色用例**无法**暴露本缺陷（固态内容复用首瓦片=像素相同，与审查"无逐瓦片像素断言"结论一致）。新增渐变 gradient 端到端用例：GPU-stitch 两瓦片输出与全帧参考逐像素一致（max diff ≤2）。

**测试**：`TestTileScopedCache` 6 例——旧机制复现（clear_export_cache 留 SOURCE）、helper 逐出 SOURCE/AI 且保留 EXPORT、None manager/snapshot no-op、AST 断言三循环"helper 先于求值且循环体内无 between-tile clear_export_cache"、渐变两瓦片端到端（左右内容不同 + 与全帧参考一致，无 GL 自动跳过）。

## 3. AUD-8701 — Stretch 变形 NaN/inf（Critical）

**验证属实**：`amount=0.5, strength=2.5`（UI 允许：deformer3d_node.py strength≤5、amount≥-5）→ `stretch_f=-0.25` → `np.sqrt` 负数得 NaN（仅 RuntimeWarning，调用方 except 捕 ValueError/TypeError/LinAlgError 不拦截）→ NaN 顶点进 VBO。

**修复**（cpu.py，按任务处方"epsilon + 结果 finite 过滤 + 上传前断言"）：
- `_STRETCH_FACTOR_EPS = 1e-6`：`stretch_f = max(stretch_f, eps)`，squash 上界 1/sqrt(eps)=1000，float32 顶点尺度下不可能溢出；
- 权重先 `np.nan_to_num`（float64）清洗，杜绝 NaN 经 maximum 传播；
- `evaluate_deformer` 出口边界（所有变形器共用的上传前最后关口）：非有限行回退原坐标、原坐标本身非有限时归零兜底——任何非有限值不会离开变形器到达 GPU。"上传前断言"以出口过滤实现（实际上传点 deformer3d_node.py 不在白名单）。

**测试**：`TestStretchFinite` 6 例——审计原始组合/除零/UI 角落（-5,5）参数化断言 finite + dtype + `np.errstate(all="raise")` 下无警告且仍产生变形；合法参数语义不变（Y 跨度增大、X 跨度缩小）；损坏输入行（NaN/inf）被清理；epsilon 常量契约。既有 `test_3d_deformers.py` 全过（合法参数行为不变）。
