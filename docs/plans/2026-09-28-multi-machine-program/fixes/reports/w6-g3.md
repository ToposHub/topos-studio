## BUG-C3-01 [medium] 时间线传输条槽闭包重复连接累积 — FIXED

**根因**：`_configure_composite_timeline_playback_controls` 的连接循环对
13 个 VideoControlBar 信号的 `disconnect(slot)` 作用在**本次调用新建**的闭包上，
首次 disconnect 即抛 TypeError 跳出——上一次进入页面连接的旧闭包从未被拆除，
第 N 次进入后每个信号挂 N 份闭包（捕获旧 controller / 旧 clip 区间）。

**修复**（page_controller.py）：

1. 函数开头（frame/state 槽拆卸之后、`enabled` 早退之前）新增
   `_composite_timeline_bar_slots`（`(bar, [(signal_name, slot), ...])`）的
   对称拆卸循环——与同文件 `_comp_clip_bar_slots` 的正确写法对齐。拆卸放在
   早退之前，因此 `enabled=False` 的禁用路径也会拆干净旧槽。
2. 连接循环删除无效的 disconnect-while 循环，只 `signal.connect(slot)`，
   并记录 `self._composite_timeline_bar_slots = (bar, list(control_connections))`。

**测试影响**：翻转锁定用例
`tests/app/test_page_controller_coverage.py::test_timeline_controls_bar_slots_accumulate_across_rewires`
（`== 2` 钉住现状 → `== 1` + 旧槽已移除 + seek/loop 信号同样不累积）。
新增 `tests/edit/test_fix_w6g3_aud6.py` 覆盖禁用路径与三次重进路径。

## BUG-C3-02 [low] `comp_clip_total_frames()` 返回 None 无兜底 — FIXED

**根因**：callable 分支直接 `int(total_frames())`，返回 None 即 TypeError，
打断整个装配（传输条不显示、Keyframes transport 不装配）；else 分支有
`or 1` 兜底，防御不对称。

**修复**（page_controller.py）：callable 分支改为
`clip_total = int(total_frames() or 0)` + `except (TypeError, ValueError)` 归零，
`clip_total < 1` 时统一回退 `controller.timeline_duration`（与证据文档建议的
"None → 回退 timeline_duration"语义一致，比裸 `or 1` 更强：还能兜住 0/非数值）。

**测试**：新增
`test_timeline_controls_invalid_total_frames_falls_back_to_timeline_duration`
（None/0 参数化 → 37）、`test_timeline_controls_valid_total_frames_still_wins`。

## BUG-C2-04 [低] 首帧中间状态 FRAME_PATH_DEGRADED / TIMEOUT_PROXY 永不可观测 — FIXED

**根因**：Level-1/2 写入的中间状态（FRAME_PATH_DEGRADED / TIMEOUT_MASTER /
TIMEOUT_PROXY）在 Level-3 被 `result.status = PLACEHOLDER` 无条件覆盖
（`should_fallback` 恒 False），而成功路径全部提前 return——调用方
（`load_video`）永远看不到进入占位符路径的原因。

**修复**（video_playback.py，按证据文档建议"Level-3 保留进入原因"）：

1. `FirstFrameResult` 新增字段 `degraded_from: Optional[FirstFrameStatus] = None`
   （docstring 同步）。
2. Level-3 else 分支：`status != NOT_READY` 时先把中间状态存入
   `degraded_from`，再收敛为终态 PLACEHOLDER；日志附带 degraded_from。
   不直接保留中间状态作为终态，因为 `needs_placeholder` 的消费方语义
   （load_video L2999）依赖 PLACEHOLDER/TIMEOUT_PROXY 分组，保留
   TIMEOUT_MASTER 为终态会误入"首帧显示成功"分支。

**测试**：新增 3 用例（超时路径 degraded_from=TIMEOUT_PROXY；处理失败路径
degraded_from=FRAME_PATH_DEGRADED；MASTER_OK 路径 degraded_from=None）。
既有 `TestFirstFrameThreeLevels`（终态断言）不受影响，全部通过。

## BUG-C4-03 [medium] on_mask_hierarchy_updated 静默丢弃结构缺失的遮罩 — FIXED

**根因**：`build_from_struct` 只接收 `structure` 里出现的 id，原树中存在但
新结构缺失的项在 `layer.mask_shapes = build_from_struct(structure)` 时被静默
丢弃（无日志、无恢复路径）——配合层级重建的不可逆操作构成数据丢失。
注：BUG-C4-01（重建前 push undo 快照）已被此前 Wave 修复（函数内已有
`_push_mask_structure_snapshot()`），本条只处理静默丢弃。

**修复**（color_controller.py）：`build_from_struct` 消费项改为
`all_items.pop(item_id)`；重建后若仍有未消费项，记录
`logger.warning("... missing N item(s) ... appended back at root level")`
（报错 + 计数，满足 .clinerules"结构缺失 id 的数据不得静默丢弃"），并按原
顺序 `layer.mask_shapes.extend(all_items.values())` 追加回根级。

**测试影响**：翻转锁定用例
`test_mask_hierarchy_updated_rebuilds_tree_and_drops_unknown_ids_bug_pin`
（断言 orphan 被丢弃 → 断言 `[s1, group, orphan]` 且 `get_mask_item_by_id`
能找回 orphan）。

## BUG-C4-04 [medium] _tracker_frame_context 的 total_frames 回退不可达 — FIXED

**根因**：`frame_start, frame_end = 0, 0` 双双默认 0，无时间线剪辑时
`frame_end < frame_start`（0 < 0）恒 False，total_frames 回退分支死代码；
跟踪范围塌缩 [0,0]、参考帧被钳到 0（会话恢复早于时间线加载即触发）。

**修复**（color_controller.py，按证据文档建议的哨兵方案）：
`frame_end` 初始化改为 `-1`，使 `frame_end < frame_start` 在"剪辑缺失"和
"剪辑时长无效（duration<=0）"两种情况下都能进入回退分支，用
video_controller.total_frames 推导 frame_end；int(total_frames) 失败仍回落
frame_start。剪辑正常解析时行为不变（source_start=4/duration=6 → [4,9] 与
既有断言一致）。

**测试影响**：翻转锁定用例
`test_tracker_frame_context_resolves_timeline_and_total_frames`
第一段（`("c1","/m.mov",0,0,0)` → `("c1","/m.mov",3,0,10)`）；
后两段（有剪辑）断言不变。文档点名的 `test_start_tracker_*` /
`test_ensure_tracker_binding_*` fixture 复核通过（其 fake controller 的
total_frames 缺省路径不变）。

## AUD-R2-005 [环境] test_tracking_worker_lifecycle.py OpenBLAS 多线程崩溃（exit 132）— FIXED

**复现**（修复前）：`pytest tests/color/test_tracking_worker_lifecycle.py`
→ collected 5 items 后进程 SIGILL，exit 132。

**根因与修复**：OpenBLAS 多线程 dgetrf 在 QThread 工作线程中并行崩溃。
关键发现：`tests/conftest.py:5` 在任何测试模块之前 `import numpy`（OpenBLAS
线程池随共享库加载初始化），**仅**在测试文件顶部 setdefault 环境变量为时已晚
（实测仍 exit 132）。因此两级修复：

1. `tests/conftest.py`：在 `import numpy` **之前**
   `os.environ.setdefault("OPENBLAS_NUM_THREADS", "1")`（配置级隔离，生效点；
   测试套件对 BLAS 并行度无依赖）。
2. `tests/color/test_tracking_worker_lifecycle.py`：文件顶部（numpy 经
   src.features.color.tracking.* 导入之前）同款 setdefault + 注释指回
   conftest（单独按文件运行时的自述性兜底）。

**验证**：修复后 `5 passed in 1.48s`，exit 0；全量 tests/color（2006 通过）、
tests/edit（8514 通过）、tests/app（918 通过）、tests/video（946 通过）均无
OpenBLAS 崩溃。
