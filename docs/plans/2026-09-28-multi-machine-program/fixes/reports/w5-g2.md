## AUD-39500 [Critical/risk] 预分配转换缓冲跨线程别名

**状态：FIXED**

**根因**：`upload_and_render_frame` 在调用方（生产者）线程调用
`_convert_frame_to_float_generic(frame, input_format)`，其返回值是
`self._convert_buffer` 这个跨帧复用的暂存缓冲（`_convert_frame_to_float`
L371/L380 直接 `return self._convert_buffer`）。该引用被原样排入
`command_queue`，渲染线程延后消费（`image.astype(np.float16)` /
`texture.write(...tobytes())`）。生产者在消费前处理下一帧（seek/拖动/突发
解码/GPU 繁忙时必现）会就地复写同一缓冲 → 队列中待上传帧被改写，产生
帧撕裂/串帧（新帧数据配旧帧号），astype/tobytes 与写入交错还可能产生
半新半旧的脏帧。违反「预分配缓冲跨线程不得别名」硬约束。

**修复**（`video_async_renderer.py`）：
- `upload_and_render_frame` 入队前 `.copy()` 出独立缓冲：
  `frame_float = self._convert_frame_to_float_generic(frame, input_format).copy()`。
  暂存池仍仅在调用方线程内复用（避免逐通道中间数组分配），队列中的每条
  UPLOAD_FRAME payload 持有独立 numpy 对象。
- 两个转换方法（`_convert_frame_to_float` / `_convert_frame_to_float_generic`）
  的 docstring 补充契约说明：返回值是调用方线程私有暂存缓冲，跨线程传递
  前必须 `.copy()`。

**验证**（`tests/shared/test_fix_video2_aud5.py::TestConvertBufferNoAliasAcrossThreads`）：
- `test_queued_frames_are_independent_buffers`：连续两帧入队后，两条
  UPLOAD_FRAME 的 image 数组 `is not` 彼此，且第一条内容在第二帧转换后
  保持 frame-1 数值（旧实现在此处被复写为 frame-2）；BGR→RGB 交换与
  /255 归一化语义不变。
- `test_scratch_buffer_still_reused_within_producer_thread`：`_convert_buffer`
  对象在线程内仍复用，且队列项均不是暂存缓冲本身。
- `test_uint16_input_also_decoupled_from_scratch`：uint16 高位深分支
  （`_convert_frame_to_float_generic` 非 uint8 路径）同样解耦。

## AUD-39501 [Critical/bug] YUV 渲染路径失效：UPLOAD_YUV_FRAME 从不设置 current_frame_tex

**状态：FIXED**

**根因**：`_do_render_frame`（原 L817）以 `if not self.ctx or not
self.current_frame_tex: return` 为门槛，而 `current_frame_tex` 仅在
`_do_upload_frame`（RGB 路径）赋值；`_do_upload_yuv_frame` 只设置
`_is_yuv_frame`/`_yuv_format`/`_yuv_y_tex` 等状态，渲染路径从不读取。
结果：`upload_yuv_and_render_frame` 提交的 RENDER_FRAME 渲染的是上一帧
RGB（若上传过）或静默不渲染、不发 frame_ready（若没有）——YUV 带宽优化
路径（P4.4）端到端不可用。违反「命令分发的纹理句柄必须被消费端正确建立
current」硬约束。

**修复**（`video_async_renderer.py`）：
- `_do_upload_yuv_frame` 上传成功、更新帧状态后，新增 YUV→RGB 合成步骤：
  通过新方法 `_ensure_yuv_composite_fbo(width, height)` 维护帧尺寸的
  合成目标（f2 RGBA 纹理 + FBO，尺寸变化时 FBO 与颜色附件分别释放重建），
  planar 格式（420/422/444）调用 `YUVGPUUploader.render_yuv_to_rgb`、
  NV12/P010 调用 `render_nv12_to_rgb`（两者内部按 `_last_upload_mode`
  自动分发 float sampler / r16ui usampler shader，yuv_matrix/color_range
  uniform 取自上传前已设置的 uploader 状态），随后
  `self.current_frame_tex = self._yuv_composite_tex`，与 RGB 路径对齐。
- `__init__` 初始化 `_yuv_composite_fbo` / `_yuv_composite_tex`；
  `_cleanup_gl_resources` 释放两者。
- `_ensure_yuv_composite_fbo` 全类型注解；合成失败走原有 try/except
  （记日志并复位 `_is_yuv_frame`），不会使渲染线程崩溃。

**验证**（`TestYuvUploadSetsCurrentFrameTex`，fake ctx/uploader 单元级）：
- planar 上传后 `current_frame_tex is _yuv_composite_tex`，合成 FBO 为
  帧尺寸 (8,4)，`render_yuv_to_rgb` 收到该 FBO 且 `bit_depth=8`，
  `current_frame_index`/`frame_size` 同步更新。
- NV12 上传走 `render_nv12_to_rgb`（不误走 planar 渲染）。
- 帧尺寸变化时旧 FBO/纹理被释放（released 标记）、新目标尺寸正确。
- `_cleanup_gl_resources` 后合成资源为 None 且已释放、`current_frame_tex`
  复位。

## AUD-39600 [Critical/bug] 高位深 BGR packed 帧转 uint8 缺少 *255 缩放

**状态：FIXED**

**根因**：`EnhancedVideoPlaybackEngine._process_decoded_frame`（原
L3499）对 uint16 BGR（bgra64 等 16-bit 打包，full range 0-65535）执行
`(data[..., :3] / (1 << frame.bit_depth)).astype(np.uint8)`：除以
65536（16bit）后值域 [0,1)，astype 截断后全为 0 —— 首帧/HQ seek/静态
预览路径输出纯黑。附带缺陷：`frame.bit_depth` 为直接属性访问，属性缺失
时抛 AttributeError 被外层捕获 → 返回 None（同样黑屏）。同函数 RGB 分支
（L3510）与 `_process_frame`（L667）均为正确的 `/65535.0 * 255.0` 惯例。

**修复**（`video_playback.py:3499`）：改为与相邻代码一致的转换惯例
`(data[..., :3] / 65535.0 * 255.0).astype(np.uint8)`（与 `_process_frame`
逐位相同）。不再读取 `frame.bit_depth`，AttributeError 风险一并消除。

**验证**（`TestBgr16PackedToUint8Scaling`）：
- bgra64 uint16：65535→255、32768→127、0→0，输出非全黑、dtype uint8、
  alpha 通道剥离。
- frame 无 bit_depth 属性时正常转换（旧实现返回 None）。
- bgr24 uint8 路径不变。
- 与 `_process_frame` 同输入同输出（惯例一致）。
- GL 端真渲染回归（见 AUD-39800 的 GL 验证脚本）之外，另按协议更新了
  锁定旧行为的 characterization 测试（见「既有测试处理」）。

## AUD-39800 [Critical/bug] BT.601 矩阵系数误用 PAL 模拟 YUV 值

**状态：FIXED**

**根因**：四处 shader 副本的 bt601 常量为
`mat3(1,1,1, 0,-0.3945,2.032, 1.140,-0.581,0)`——这是 PAL 模拟 YUV
矩阵系数；而 shader 的色度归一化是数字 YCbCr 的
`(C-128<<s)/(224<<s)`（limited range），该约定下标准 BT.601 系数应为
R:+1.402 / G:-0.3441·U-0.7141·V / B:+1.772（Kr=0.299、Kb=0.114 推导）。
红欠饱和约 19%、蓝过饱和约 15%。BT.601 路径真实可达：
`video_playback.py:1728-1729` 将 'smpte170m'/'bt470bg' 映射为
MATRIX_BT601。违反「YUV 矩阵系数按标准正确选择」硬约束。

**修复**（`yuv_gpu_upload.py` 四处副本同改：原 L1998、L2147、L2320、
L2485，对应 float 3-plane / r16ui 3-plane / nv12 r16ui / nv12 float 四个
shader）：

```glsl
const mat3 bt601 = mat3(
    1.0, 1.0, 1.0,
    0.0, -0.3441, 1.7720,
    1.4020, -0.7141, 0.0
);
```

第一处附注释说明数字 YCbCr 约定与系数来源（Kr/Kb 推导）。BT.709/BT.2020
系数未动（已核对无误，且其列布局约定经验证与 601 修正一致）。

**验证**：
- `TestBt601DigitalMatrixCoefficients`：四处副本均含标准系数行
  （`count == 4`）；PAL 系数（-0.3945/2.032/1.140/-0.581）在
  `inspect.getsource(YUVGPUUploader)` 中不再出现；系数与 Kr=0.299/Kb=0.114
  解析推导一致，且同一推导对 shader 中既有 BT.709 行复现（验证列布局
  惯例）；`smpte170m`/`bt470bg` → MATRIX_BT601(2) 映射存在（可达性）。
- `TestBt601GpuPixelVerification`（GL 上下文，standalone ModernGL）：
  上传一帧 limited-range 601 测试色（Y=128, Cb=62, Cr=194）经
  `upload_yuv420` + `render_yuv_to_rgb` 真渲染回读，GPU 输出 [236,103,0]
  与标准数字 601 CPU 参考误差 0（≤1 容差），与旧 PAL 矩阵参考差 20
  （>10，回归敏感度确认）。四个 shader program 均编译通过（float
  3-plane / r16ui 3-plane / nv12 r16ui / nv12 float）。
