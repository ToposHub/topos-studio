## 测试环境

| 项目 | 值 |

| CPU | Intel Core i9-9900K @ 3.60GHz（16 线程） |
| 系统 | macOS 15.3.1（x86_64） |
| Python / PyAV | 3.12.13 / av 17.0.1 |
| 解码路径 A | FFmpeg 软解（`FFmpegMediaSource.read_frame_planar`，生产 planar-YUV 路径） |
| 解码路径 B | macOS VideoToolbox 零拷贝（`MacOSVtZeroCopySource`，Intel 平台部分编码可用） |

## 测试方法

每条路径对每个素材**顺序解码前 120 帧**（与播放方向一致的访问模式），统计：

- **p50 / p95 / 稳态最差单帧延迟**（毫秒，去掉前 10 帧预热后取最差值）
- **吞吐 fps** 与 **实时倍率**（吞吐 ÷ 素材帧率 25fps，1.0× 即刚好能实时播放）
- 会话冷启动耗时（`open()`，含 VT 首次框架加载）

VT 硬解仅测 VideoToolbox 支持的编码；不支持的编码如实标记为「VT 无此解码器」。

## 关键结论

1. **所有素材在两条可用路径上均远超实时播放需求**（最低 1.5×：4K ProRes 4444 走 VT）。单轨顺序播放不是解码瓶颈。
2. **在本机（Intel）上 FFmpeg 多线程软解的中位延迟几乎全面优于 VT 硬解**：2K 段 p50 为 VT 的 1.5–2.9 倍快，4K ProRes 约 1.4–1.5 倍快。唯一例外是 4K_H265 的总吞吐（VT 130 vs FFmpeg 119 fps），原因是 FFmpeg 在 HEVC 上抖动大（见下条）。
3. **FFmpeg 软解存在明显的帧级尖峰**：4K_H265 稳态最差单帧 200ms、4K_ProRes4444 103ms、4K_H264 88ms；而 VT 的尖峰普遍 ≤ 34ms。对播放卡顿感（单帧超预算）而言，VT 的稳定性显著更好，4K HEVC 上「吞吐略高 + 尖峰小 8 倍」使它成为更均衡的选择。
4. **DNxHR 只能走 FFmpeg**（VideoToolbox 无此解码器），且 FFmpeg 解 DNxHR 表现优异：12-bit 4K 达 159fps（6.4× 实时），2K 达 677fps——比同级 ProRes 422 HQ 快约 1.7 倍。
5. **分辨率/复杂度的耗时扩展**（2K→4K，p50）：H.264 约 2.1 倍，HEVC 约 4.7 倍，ProRes 422 HQ 约 4.9 倍，DNxHR 约 4.3 倍。H.264 因压缩率低、解码计算量小而扩展最平缓；帧内编码的中继格式（ProRes/DNxHR）近似随像素量线性增长。
6. **最重素材是 4K_ProRes4444**（12-bit 4:4:4，约 1.1 Gbps）：FFmpeg 单帧 p50 已达 17ms，25fps 播放帧预算 40ms 下单轨余量充足，但多轨叠加时解码余量会首先在这里耗尽。
7. **VT 会话冷启动成本**：进程内首个 H.264 会话 open() 耗时 0.6–1.9s（两次独立运行分别为 1924ms / 617ms），明显影响首帧出画时间。

## 建议

- **路由策略**：H.264 / ProRes / DNxHR 优先 FFmpeg 软解（p50 与吞吐均更优）；**4K HEVC 优先 VT**（吞吐略高且抖动小一个数量级）。DNxHR 必须路由到 FFmpeg。
- **预热**：对 VT 路径在应用启动后做一次后台空会话预热，消除 0.6–1.9s 的首会话冷启动。
- **代理门槛**：4K ProRes 4444（及未来的 4444 XQ）在多轨时间线场景建议强制走代理，全分辨率留给调色渲染输出。
- **抖动兜底**：FFmpeg 路径的单帧尖峰（可达 200ms）应继续由异步解码队列（DecodeWorker + ReadyFrameQueue）吸收，本测试的同步延迟数据可用于校准预缓冲深度。

## 复现

```bash
.venv/bin/python tools/bench_decode_speed_report.py --n 120
```

注意：结果对机器敏感（本报告基于 Intel i9-9900K；Apple Silicon 上 VT 硬解含 ProRes 加速，结论会不同）。数据为顺序解码吞吐，不含 seek、GPU 上传与色彩转换。
