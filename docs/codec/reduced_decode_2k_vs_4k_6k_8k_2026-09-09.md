# 2K / 4K / 6K / 8K 降分辨率解码对比（2026-09-09）

## 测试口径

- macOS Release，Topos slice worker 固定 8 个；codec-only，不包含 GPU 上传、调色、合成和 present。
- 同一类确定性 BGR8 渐变素材，YUV422、10-bit、VLC、QP24；预热 5 次，热态计时 20 次。
- 2K 基线为 1920×1080 V2 `full` 解码到 1920×1080。
- 高分辨率使用 V7-B `AUTO_2K` base-only 路径；未请求的 residual enhancement 段不读取，telemetry 中 `segments_skipped=60`（20 帧 × 3 个 residual 段）。
- FPS = 1000 / p50 毫秒；倍数以 2K 基线 p50 为 1.00×。

## 结果一：当前默认 2048 base，严格输出目标几何

| 输入 → 输出 | 解码路径 | 输出几何 | p50 | p95 | p50 FPS | 相对 2K |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 2K → 2K | V2 full | 1920×1080 | 14.24 ms | 16.75 ms | 70.24 | 1.00× |
| 4K → 2K | V7-B base-only + base→1920 重采样 | 1920×1080 | 66.88 ms | 72.81 ms | 14.95 | 4.70× |
| 6K → 2K | V7-B base-only | 2048×1152 | 24.19 ms | 25.42 ms | 41.34 | 1.70× |
| 8K → 2K | V7-B base-only + base→1920 重采样 | 1920×1080 | 66.72 ms | 72.43 ms | 14.99 | 4.69× |

4K/8K 的高耗时主要来自默认 base 为 2048×1152，而严格的 1/2、1/4 目标是
1920×1080；当前路径会先解码 2048 base，再做一次面积重采样。

## 结果二：base 直接编码为目标 2K 几何

| 输入 → 输出 | base 几何 | p50 | p95 | p50 FPS | 相对 2K |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2K → 2K | 1920×1080 | 14.24 ms | 16.75 ms | 70.24 | 1.00× |
| 4K → 2K | 1920×1080 | 18.69 ms | 20.29 ms | 53.49 | 1.31× |
| 6K → 2K | 2048×1152 | 24.19 ms | 25.42 ms | 41.34 | 1.70× |
| 8K → 2K | 1920×1080 | 19.64 ms | 22.44 ms | 50.93 | 1.38× |

## 结论

当前实现已经是 base-only 降分辨率解码：4K/6K/8K 的 enhancement residual 不参与
读取和解码。但在当前默认 2048 base 配置下，4K/8K 若要求精确 1920×1080，会额外
产生重采样成本；将 base 几何直接匹配目标后，4K/8K 约为 2K 解码的 1.31×/1.38×，
6K 约为 1.70×。

因此目前不能说所有分辨率都已经“与 2K 完全同速”。真正接近 ProRes 风格的下一步是：
让编码策略根据预览目标生成匹配的 base 几何，或为 1920 目标增加不经过面积重采样的
专用 base 输出路径；另外还需完成 30/60fps 的完整 codec+upload+present 门禁。

原始单项 JSON 保存在本机 `/tmp/topos_decode_*_to_2k*.json`，本报告数值来自这些运行结果。
