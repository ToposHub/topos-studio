# TOPOS 编码全面检查与优化计划（2026-09-27）

## 检查口径与结论

- 检查对象：当前工作树 `2fe1b0c3`；原生 C12 编解码/容器、Python 绑定、视频与图片序列导入导出、测试素材和发布质量门禁。运行环境为 macOS、项目 `.venv/bin/python` 3.12.13。未修改编码实现或素材。
- 原生 Debug 构建成功，`ctest --test-dir native/topos_codec/build/debug --output-on-failure -j 6` **90/90 通过**；聚焦 Python 音频/色彩/容器/基准协议测试 **45/45 通过**。这些结果只证明已覆盖路径，不能抵消下面的反例。
- 真实素材矩阵不一致：`topos_test_media_manifest.json` 的 12 个产物中 10 个路径在本机不存在，现有对应视频多为另一套名称且有 **487 帧**，清单写 **96 帧**。抽查 61 个相关 Python 用例，**11 通过、50 跳过**。`benchmark_media_manifest.json --check` 报 **26 项漂移**；质量门禁默认模式通过，但 `--require-media` 报 **3 项违规**。因此当前质量、码率和真实媒体回归不能据默认门禁宣称通过。
- 大范围 `tests/media/test_topos_*.py` 共收集 1359 项；两次都在运行末段/pytest 清理阶段以 **exit 139** 结束，第二次 faulthandler 指向垃圾回收，未产出可信汇总。另一次禁用 pytest unraisableexception 插件的诊断运行在导入音频播放模块时 **exit 134**；根因尚未定位，不能归咎于编码器。该项是测试稳定性问题，须隔离复现。

下表的“已复现”指检查中有具体输入与观测；“代码路径”表示由控制流确定但还需故障注入或目标平台验证。优先级按数据安全、结果正确性、发布证据、资源与性能排序。工期与性能收益不作无实测承诺。

## 执行顺序与验证门

1. **先保数据与恢复证据（C01–C03）**：修序列导出的提交/取消语义；统一真实素材矩阵并重建基线。完成前不更新“画质或速度已达标”的结论。
2. **修编码和读取正确性（C04–C08）**：每项都补最小反例测试，再跑 native golden、截断流与相关 Python 用例。容量错误保证失败原子性；音频/图片序列保证语义一致。
3. **收口生命周期与组合回归（C09–C13、C18）**：覆盖 open、close、abort、写失败、取消及 macOS GPU lease；定位进程崩溃和 RAW 直出偏差后再宣布相关全套测试通过。
4. **清理协议与性能债（C14–C17）**：同步公开文档；用当前真实素材量化长音轨随机读取、编码/解码 p50/p95、峰值 RSS。性能改动须同一 commit、动态库 SHA、素材 SHA、线程数做交替 A/B，并保持像素/音频逐值一致。
5. **按性能收益实测推进（F01–F09）**：先完成 F01 的素材与基线，再对 F02–F05 做分项测量和最小改动；F06–F08 按实际时间线/平台负载排序，F09 须通过 V8/V9 专属门禁后才进入产品路径。
