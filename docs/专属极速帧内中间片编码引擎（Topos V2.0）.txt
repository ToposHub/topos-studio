## 0. 文档使用原则

本文档用于指导 AI 和开发者按依赖顺序逐步实施 Topos Video Codec。它不是现成的位流标准，也不包含可以直接复制到生产环境的示例代码。

实施时必须遵守以下原则：

1. 一次只推进一个阶段，不跨阶段同时修改多个核心模块。
2. 每个阶段先完成规范和测试，再实现代码。
3. 标量参考实现通过一致性测试前，不得开始 SIMD 优化。
4. Elementary bitstream 稳定前，不得把 MOV、UI、导出和性能优化混入核心算法。
5. 所有新行为必须有自动化测试，失败、取消、损坏输入和资源释放路径与正常路径同等重要。
6. 所有 OpenGL/ModernGL 操作继续由 Topos Color 现有渲染线程执行。
7. 不新建与现有 DecodeWorker、FrameProvider、缓存和渲染队列冲突的全局线程调度系统。
8. 每完成一个阶段，AI 必须输出变更文件、测试结果、未解决问题和下一阶段的前置条件。

## 1. 产品定义

### 1.1 产品定位

Topos Video Codec 是一套私有帧内中间片编解码方案，优先服务于 Topos Color 内部工作流：

- 时间线实时剪辑与随机拖拽；
- 高位深调色和 HDR 中间缓存；
- 动态图形、字幕和透明素材；
- 代理文件、渲染缓存和中间母版；
- 可控环境下的跨平台文件交换。

编码器使用 QuickTime MOV 作为主要容器，并使用私有 FourCC 标识 Topos elementary stream。MOV 容器合规不代表其他 NLE 会自动支持该编码；第三方互操作需要另行开发插件或解码组件。

### 1.2 核心设计目标

按优先级排序：

1. 码流可解析、可验证、不会因损坏输入越界或无限循环；
2. 10-bit / 12-bit 图像和 Alpha 的语义明确且可重复还原；
3. 帧独立、支持快速随机访问和帧级并行；
4. 画质适合多代编解码及专业调色；
5. 与 Topos Color 现有媒体、色彩、GPU 和导出架构一致；
6. 标量、AVX2 和 NEON 路径输出一致；
7. 在正确性稳定后逐步提高吞吐量和降低尾延迟；
8. 提供稳定、可版本化的 C ABI 和 Python 集成层。

### 1.3 非目标

首个可用版本不承诺：

- 与 Apple ProRes 位流兼容；
- 输出码率与 ProRes 精确一致；
- 所有第三方 NLE 或播放器直接识别；
- 任意硬件上固定达到某个 FPS；
- CPU 解码数据天然实现 GPU 零拷贝；
- 所有损坏文件均可恢复画面；
- 首版同时支持所有容器、音频和高级元数据。

## 2. 档位与码率策略

### 2.1 档位定义

ProRes 只用于描述大致的市场档位和存储区间，不作为精确码率验收标准。

以下数据以 1920×1080、25fps、无 Alpha 为参考。实际码率允许根据画面复杂度、分辨率、帧率和编码器版本变化。

| Topos 档位 | 颜色格式 | 位深 | 参考数据率 | 主要用途 |
| --- | --- | --- | --- | --- |
| Topos Proxy | YUV 4:2:2 | 10-bit | 约 4–7 MB/s | 离线代理、远程剪辑 |
| Topos LT | YUV 4:2:2 | 10-bit | 约 9–13 MB/s | 轻量中间缓存、粗剪 |
| Topos Standard | YUV 4:2:2 | 10-bit | 约 14–19 MB/s | 常规剪辑和渲染缓存 |
| Topos HQ | YUV 4:2:2 | 10/12-bit | 约 20–28 MB/s | 调色、中间母版 |
| Topos Pro 444 | YUV/GBR 4:4:4 | 10/12-bit | 约 30–44 MB/s | VFX、动态图形、合成 |
| Topos Extreme | YUV/GBR 4:4:4 | 12-bit | 约 45–68 MB/s | 高宽容度 HDR 和多代制作 |

这些区间是调参目标，不是格式定义。版本升级后允许改进量化矩阵和码率控制，但必须通过 codec configuration 和 bitstream version 保持解码兼容。

### 2.2 Alpha 策略

所有档位可以选择携带 Alpha。首版默认采用“受限近似 Alpha”模式，目标是在保持透明边缘可用的前提下控制文件增长。

| Topos 档位 | Alpha 目标占颜色主码流比例 | Alpha 硬上限 | 默认策略 |
| --- | ---: | ---: | --- |
| Proxy | 约 20% | 25% | 受限近似，优先节省空间 |
| LT | 约 20% | 25% | 受限近似 |
| Standard | 约 25% | 30% | 受限近似，平衡质量和空间 |
| HQ | 约 25% | 30% | 高质量受限近似 |
| Pro 444 | 约 25% | 30% | 高质量受限近似 |
| Extreme | 约 30% | 30% | 最高 Alpha 预算 |

比例的分母是当前帧压缩后的颜色主码流大小，不是 RGB 未压缩数据大小。编码器必须分别统计颜色 payload、Alpha payload 和总 payload。

必须遵守：

- Alpha 是独立、全分辨率平面，不进行色度式 4:2:2 降采样；
- 无 Alpha 时不分配、不编码、不解码 Alpha 平面；
- 默认存储 straight alpha，并在元数据中明确标记；
- 如输入为 premultiplied alpha，必须明确转换或保留标志，禁止静默猜测；
- Alpha 使用独立预测、游程和熵编码参数，不经过颜色 DCT 的死区量化；
- 编码器先尝试无损或近无损压缩，达到 Alpha 目标比例后停止增加码率；
- 如果复杂 Alpha 无法在硬上限内表示，必须执行显式的近似策略并记录最大误差；
- 如果调用方要求 Alpha 无损，则允许超出比例、提示空间增长或直接返回可诊断错误，不能静默破坏无损承诺；
- 文件头必须记录 Alpha 模式、目标比例、实际比例和最大误差；
- 任何单帧 Alpha payload 都不得无提示地超过颜色主码流的硬上限。

### 2.3 码率控制原则

编码器采用帧内 VBR：

- profile 决定基础量化矩阵和目标 bits-per-pixel 区间；
- 帧级分析决定该帧的初始量化尺度；
- slice 级预算用于减少局部爆码；
- Alpha 使用独立的目标比例和硬上限，默认不超过颜色主码流的 25%–30%；
- 最大帧大小必须有明确限制；
- Raw/near-raw escape mode 只能作为有界的格式能力，不能同时声称严格锁定总码率；
- 画质优先档允许为复杂帧适度增加码率；
- 代理档允许更强量化，但不得破坏解码安全和时间线稳定性。

## 3. 总体架构

### 3.1 分层设计

~~~text
Topos Color
  ├─ MediaSource / DecodedFrame / VideoMetadata
  ├─ FrameProvider / DecodeWorker / Cache
  ├─ AsyncRenderer / YUV(A) GPU Upload / HDR Color Pipeline
  └─ Export / Proxy / Deliver
              │
              ▼
Topos Python Binding
              │
              ▼
Stable Topos C ABI
              │
              ▼
Native Codec Core
  ├─ bitstream syntax and validation
  ├─ scalar transform / quantization / entropy
  ├─ encoder / decoder
  ├─ profile and rate control
  ├─ AVX2 / NEON runtime dispatch
  ├─ optional GPU compute backends
  └─ MOV integration through a mature container library
~~~

V2.0 的规范性路径是 CPU scalar；GPU、SIMD 和混合数据流都属于可替换的执行后端，不能改变
码流语义、重建结果和错误模型。后续增加 GPU 时，优先加在 transform、quantization、Alpha
预测等规则明确且数据并行度高的环节，避免把 GPU 设备句柄或驱动依赖写入基础码流格式。

### 3.2 推荐代码布局

~~~text

~~~

最终路径可在阶段 0 根据仓库现状调整，但 native codec、绑定层和应用集成层必须保持分离。

### 3.3 容器策略

首选使用 libavformat 或经过验证的等价库完成 MOV mux/demux，不在首版手写完整 MOV parser。

容器要求：

- 私有视频 FourCC，暂定 TPIC；
- 独立 codec configuration atom，暂定 tpcC；
- 使用标准 stsd、stts、stsc、stsz、stco/co64 等 sample table；
- 每个视频 sample 对应一帧 Topos frame packet；
- 写入完整的 time base、duration、色彩、像素比例和场序信息；
- FastStart 作为封装完成后的重排步骤，不要求编码开始前就知道 moov；
- 大文件必须支持 64-bit chunk offset；
- 未识别的私有扩展必须能够按 atom size 安全跳过；
- 首版只保证 Topos 自有解码器可读，第三方兼容性单独验收。

## 4. Elementary Bitstream 规范要求

### 4.1 版本化

码流至少包含：

- magic；
- major/minor version；
- header size；
- frame size；
- profile；
- pixel format；
- bit depth；
- coded width/height；
- visible width/height；
- plane count；
- Alpha mode；
- frame type 和 GOP/reference 标识（V2.0 固定为独立 I 帧，字段为可扩展项）；
- slice count；
- quantization matrix ID；
- flags；
- header checksum 或等价完整性校验。

Major version 表示不兼容变更；Minor version 只能增加旧解码器可安全忽略的能力。

### 4.2 帧与 Slice

- V2.0 Intra profile 的每帧独立，不依赖其他帧；
- 未来 Inter profile 只允许在闭合 GOP 内引用前向参考帧，并在 frame header 中声明 frame type、
  GOP 标识和 reference distance；
- 任何 profile 都不得跨 GOP 引用，也不得使用 B 帧或隐式的长期参考帧；
- 每帧分为多个可独立验证的 slice；
- slice header 必须提供 byte size、block range、plane、quant scale 和 entropy restart state；
- slice 之间不得共享无法重建的自适应状态；Inter profile 的参考帧只作为显式输入，不改变 slice 独立性；
- slice 可独立并行解码；
- 任意 size、offset、count 在使用前都必须验证；
- 解码器必须设置最大分辨率、最大帧大小、最大 slice 数和最大系数长度；
- 损坏 slice 可以返回明确错误或受控 concealment，禁止越界继续解析。

### 4.3 颜色平面编码

第一版颜色压缩路径：

1. 按位深进行 level shift；
2. 对边界 block 做确定性 padding；
3. 执行规范化的 8×8 整数 DCT；
4. 使用 profile 和 plane 对应的量化矩阵；
5. 对 DC 和 AC 系数进行明确的预测与扫描；
6. 对零游程和幅值进行统一的熵编码；
7. 在 slice 边界重置所有预测状态。

必须在规范中固定：

- 每一步的整数位宽；
- 舍入方式；
- 右移行为；
- 饱和或错误策略；
- 最大中间值证明；
- 量化与反量化公式；
- block 扫描顺序；
- 负数符号映射；
- 标量和 SIMD 的一致性要求。

### 4.4 熵编码

正文只保留一种正式方案，建议使用：

- 零游程编码；
- Zigzag/plane-specific scan；
- 有符号映射；
- 有上限的 Golomb-Rice 或等价低复杂度码；
- Escape code 处理大幅值；
- slice 级 restart。

禁止无界 Unary 解码。编码器和解码器都必须检查剩余位数和输出系数数量。

### 4.5 Alpha 编码

Alpha 不经过颜色 DCT 路径。根据 Alpha 模式，分别使用无损或受限近似路径：

- 行内或二维预测；
- residual zigzag mapping；
- 零游程；
- 有上限的 Rice/escape 编码；
- slice 级独立重启；
- 无损模式执行 bit-exact 对比；
- 受限近似模式记录最大绝对误差和实际 payload 比例。

必须测试全透明、全不透明、硬边、羽化边缘、噪声 Alpha、动画遮罩和随机数据。

## 5. 像素与色彩规范

每个文件和解码帧必须明确以下信息：

- YUV、YUVA、GBR 或 GBRA；
- 4:2:2 或 4:4:4；
- 10-bit、12-bit 或 16-bit Alpha；
- 内存字节序和有效位位置；
- full/limited range；
- color primaries；
- transfer characteristics；
- matrix coefficients；
- chroma siting；
- sample aspect ratio；
- progressive/interlaced 和 field order；
- straight/premultiplied Alpha；
- coded size、visible size 和边界 padding。

Topos Color 内部继续使用现有 VideoMetadata、DecodedFrame 和 PlaneInfo 表达这些信息，禁止新建不兼容的重复模型。

## 6. C ABI 设计要求

最终 C API 同时覆盖 decoder 和 encoder，并使用 opaque context。

所有公开 struct 必须包含：

- struct_size；
- abi_version；
- 保留字段；
- 明确的所有权说明。

### 6.1 Decoder 能力

- 从文件路径或 IO callbacks 打开；
- 查询 stream info；
- 按帧号或时间戳请求；
- 解码到调用方提供的 CPU plane buffer；
- 查询所需 plane size、stride 和 alignment；
- 支持取消；
- 支持 flush/close；
- 返回稳定状态码和可读错误详情；
- 明确 context 是否可重入，以及哪些函数可并发调用。

### 6.2 Encoder 能力

- 配置 profile、pixel format、bit depth、色彩和 Alpha；
- 提交带 PTS/duration 的帧；
- 输出 packet 或写入 IO callbacks；
- flush；
- 查询实际颜色、Alpha 和总码率；
- 取消并释放未完成任务；
- 支持编码器版本和 codec configuration 导出。

### 6.3 Frame Buffer

每个 plane 独立描述：

- data pointer；
- capacity；
- stride；
- width/height；
- sample type；
- bit depth；
- byte order；
- alignment；
- ownership/lifetime。

不得只提供一个共享 stride_uv，也不得仅用 uint8 pointer 暗示 10/12-bit 的具体存储方式。

### 6.4 可选加速扩展

基础 ABI 首版只要求 CPU plane buffer，保证在没有 GPU、驱动或特定运行时的环境中仍可工作。
为后续升级预留独立 extension/capability API，不修改既有函数和 struct 的含义：

- 使用 opaque device context、GPU buffer 和 fence/同步对象，不在基础 ABI 中暴露厂商私有结构；
- 每个 GPU buffer 必须声明设备归属、字节容量、读写方向、同步状态和释放责任；
- GPU 路径失败、设备丢失或不支持时，能够回退到 CPU，并返回可诊断状态；
- CPU↔GPU 拷贝、等待和生命周期必须显式计时，禁止把“零拷贝”作为默认承诺；
- 扩展通过 capability query 和新版本号启用，旧调用方仍可只使用 CPU API。

## 7. AI 分阶段实施路线

以下阶段按依赖顺序执行，不对应固定日历周期。

### 阶段 0：决策冻结与基线建立

目标：在写核心代码前消除格式歧义。

任务：

- 检查 AGENTS.md、.clinerules 和相关媒体架构；
- 建立受影响文件和调用链清单；
- 冻结首版支持矩阵；
- 决定 native language、build system、binding 和 MOV library；
- 编写 bitstream specification v0 草案；
- 建立 ProRes、DNxHR、无压缩序列的现有性能和画质基线；
- 明确基准硬件、编译器、线程数、缓存状态和测试素材。
- 冻结后端边界：CPU scalar 是规范性参考，SIMD/GPU 是可替换实现；记录允许的 GPU 扩展点、
  同步规则、回退行为和内存上限。
- 记录未来 Inter profile 的兼容边界：闭合 GOP、仅前向参考、无 B 帧、I/P frame header 预留字段，
  以及随机访问索引的扩展方式；V2.0 仍只实现 Intra。
- 冻结数据流原则：中间系数不作为 GPU↔CPU 往返的常规接口；若采用混合路径，优先只回读
  最终压缩 packet。

首版建议范围：

- 10-bit YUV 4:2:2；
- Standard 一个颜色 profile；
- 可选无损 Alpha；
- progressive CFR；
- CPU planar output；
- MOV + CLI；
- macOS 当前开发机和一个可移植标量路径。

交付物：

- architecture decision record；
- bitstream_spec_v0.md；
- benchmark_protocol.md；
- test_vector_manifest.json；
- 风险清单。

#### V2.1 Profile

- `Topos IP-2`：固定闭合 GOP，结构为 `I P`，GOP 长度 N=2，作为首个实现目标；
- `Topos IP-4`：固定闭合 GOP，结构为 `I P P P`，GOP 长度 N=4，在 IP-2 稳定后实现；
- 不使用 B 帧、开放 GOP 或跨 GOP 长期参考帧；
- P 帧只参考同一 GOP 中紧邻的前一张已重建帧；
- V2.0 Intra、V2.1 IP-2 和 V2.1 IP-4 必须是明确可查询的 profile capability，不能靠隐式参数猜测。

#### 运动估计与运动矢量编码

- 首版只支持整像素、固定块大小和有界搜索；先检查零运动矢量，再执行小范围搜索；
- 搜索范围、块大小、SAD/失真阈值必须写入 profile 和 bitstream specification，不允许运行时无界扩大；
- 运动矢量使用有符号、定长或有界熵编码，并在 slice 边界重置预测状态；
- Skip 判定必须在重建误差、量化参数和位深约束下验证，不能只依据未经标定的 SAD 阈值；
- 运动估计失败、矢量超界或残差过大时，必须安全回退到合法的 I 帧编码。

#### P 帧残差与 I 帧回退

- P 帧使用“参考帧预测 → 残差 → 现有 transform/quantization/entropy → 重建”的独立路径；
- P 帧必须保存完整重建结果作为下一帧参考，不能使用未量化或未验证的中间结果；
- 当 P 帧 packet 大小、失真或累计误差超过 profile 门槛时，编码器自动改写为 I 帧；
- 场景切换、高噪声、快速运动、参考帧缺失和编码取消都必须触发受控回退；
- I/P frame header、GOP 标识、reference distance 和随机访问索引必须能被 decoder 直接验证。

#### Micro-GOP Alpha 预测

- Alpha 必须拥有独立的参考帧、预测状态、错误上限和 payload 统计；不能强制与颜色通道共享运动矢量；
- 支持 Alpha 无损模式和受限近似模式；近似模式继续遵守对应 profile 的 20%–30% 颜色码流预算；
- Alpha 残差过大、遮罩突变或参考帧不可用时，Alpha 平面单独回退为 I/无损编码；
- Alpha 的 P 帧错误不得污染颜色平面，也不得跨 GOP 累积；
- 必须覆盖透明度动画、硬边、羽化、噪声 Alpha、随机 Alpha 和 Alpha 场景切换。

#### V2.1 完整测试门槛

- **码流正确性**：IP-2/IP-4 编解码 round-trip、I/P 重建、截断/损坏 P 帧、超界运动矢量和非法 reference distance 均有 conformance vectors；
- **随机访问**：从任意 GOP 起点开始解码，目标帧最多顺序解码 3 个 P 帧；seek index、PTS/DTS 和 MOV sample flags 一致；
- **剪辑行为**：GOP 边界裁切、精确出入点、反向播放缓存、并发 seek 和取消不会出现花帧、死锁或错误引用；
- **码率与画质**：静止、微动、高运动、镜头切换、颗粒和随机噪声分别测试；不得把 40%–55% 体积下降作为保证，P 帧变大时必须回退 I 帧；
- **性能**：分别报告编码、解码、seek、CPU、内存和文件大小的 p50/p95/p99；覆盖 1080p/4K、10/12-bit、无 Alpha/有 Alpha、cold/warm cache；
- **Alpha**：无损模式 bit-exact，近似模式满足最大误差和码率上限，完成 decode→GPU→composite→encode→decode round-trip；
- **兼容性**：V2.0 Intra 码流和 CPU API 行为不改变；不支持 Inter profile 的 decoder 必须返回明确状态，不能静默输出错误画面；
- **验收原则**：只有在 CPU 消耗、Seek 尾延迟、峰值内存和画质均不劣于既定基线时，才将 IP-4 标记为推荐 profile；否则保留 IP-2 或 Intra。

## 8. 测试与验收矩阵

### 8.1 素材类型

- 纯色和接近纯色；
- 1-LSB 与低幅渐变；
- 高频棋盘格、文字、线条和 UI；
- 胶片颗粒、传感器噪声和随机噪声；
- 肤色、天空、霓虹灯和高饱和颜色；
- SDR、PQ、HLG 和线性工作流；
- 全透明、全不透明、硬边和羽化 Alpha；
- 奇数宽高、非 8 倍数尺寸；
- 大分辨率和极短/极长文件；
- 损坏、截断和恶意构造输入。

### 8.2 画质指标

不得只使用单一 PSNR 门槛。至少记录：

- Y/U/V 或 RGB 各通道 PSNR；
- SSIM；
- 必要时的感知指标；
- 色差和灰阶/渐变检查；
- Alpha bit-exact 或最大绝对误差；
- 1、3、5、10 代编解码曲线；
- 相同大致码率下与现有 ProRes/DNxHR 的参考对比。

### 8.3 性能指标

所有报告必须写明：

- CPU/GPU/内存/存储；
- 操作系统；
- 编译器和优化选项；
- codec/profile/pixel format；
- 分辨率、帧率和 Alpha；
- 线程数；
- cold/warm cache；
- p50/p95/p99 和最大值；
- 输入读取、解码、GPU 上传和呈现是否分别计时。

Seek 至少拆成：

1. index lookup；
2. packet read；
3. decoded frame ready；
4. GPU frame ready；
5. first frame presented。

### 8.4 安全与资源

- bit reader/writer 边界；
- size/offset/count checked arithmetic；
- 最大分辨率和帧大小；
- 超长 Rice/Unary 防护；
- 失败和取消释放；
- context close 与并发调用；
- native buffer 与 Python object 生命周期；
- GPU deferred release；
- 临时输出的原子提交。

## 9. 风险与处理策略

| 风险 | 处理策略 |
| --- | --- |
| 位流在实现中频繁变化 | 先冻结 spec 和 golden vectors；不兼容变化提升 major version |
| AI 直接从 SIMD 开始 | 阶段门禁禁止；scalar conformance 未通过不得优化 |
| 高噪声导致爆码 | 有界 escape、最大帧大小、profile 质量策略；明确 VBR |
| Alpha 增大码率 | 默认按档位限制在颜色主码流的 25%–30% 内；无损模式超限时提示空间增长或返回错误 |
| Alpha 在渲染/导出中丢失 | 独立端到端 Alpha 阶段和 round-trip gate |
| MOV 结构不合规 | 使用成熟 mux/demux 库；建立 atom 和大文件测试 |
| 私有 FourCC 无第三方支持 | 明确受控生态定位；第三方插件单独立项 |
| 应用层与 codec 重复并行 | codec 只做有界 slice 并行，服从现有任务调度 |
| SIMD 与 scalar 输出不同 | 每个优化路径运行 differential conformance |
| GPU 同步或回读抵消收益 | 先测量端到端 p50/p95/p99；默认只回读最终 packet，收益不足时保留 CPU/SIMD 路径 |
| GPU buffer/fence 生命周期复杂 | 使用 opaque extension API、显式所有权和 deferred release；device lost 时回退 CPU |
| 两阶段熵编码增加内存和实现复杂度 | 仅作为可选优化；限定临时 buffer 上限，并与单阶段 CPU 熵编码做基准对比 |
| HDR 色彩解释错误 | 完整传递 H.273 元数据，不允许缺省猜测掩盖错误 |
| 损坏流触发越界或 DoS | 全面边界验证、上限、fuzz 和 sanitizer |
| 原生库难以打包 | 在早期建立 CMake、ABI、CI 和最小 Python binding |

## 11. 全项目完成定义

Topos Video Codec 只有同时满足以下条件才视为完成：

- bitstream specification、C ABI 和 MOV mapping 已版本化；
- scalar encoder/decoder 有永久 golden vectors；
- 10/12-bit 颜色和声明的 Alpha 模式符合质量目标；
- 损坏输入不会越界、无限循环或触发无界分配；
- Topos Color 可以导入、播放、拖拽、调色、合成、导出和生成代理；
- Alpha 从解码到最终输出没有静默丢失或降位深；
- scalar、AVX2、NEON 路径通过一致性测试；
- 性能按 profile 和完整测试环境报告；
- 已实现的 native/GPU 后端资源在正常、失败、取消和关闭路径正确释放；V2.0 不因未启用
  GPU 后端而视为未完成；
- 旧版本码流兼容策略和迁移规则明确；
- 构建、打包、SDK 和已知限制文档齐全。
