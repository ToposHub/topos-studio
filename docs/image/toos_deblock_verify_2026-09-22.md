## 1. 画质还能再提升吗：解码端已探尽

### 1.1 强度旋钮的真实形状：α 只在 qp ≥ 70 才"活"

`deblock_alpha()` = `clamp(2·step, 3, 48)`，`step = max(1, scale·3/173056)`。
`scale = tc_qp_scale_tbl(qp)` 每 4 个 qp 翻倍，于是：

| qp | 0–68 | 70 | 74 | 76 | 78 | 80 | 82 | 84 | ≥86 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| scale | ≤65536 | 92682 | 185364 | 262144 | 370728 | 524288 | 741455 | 1048576 | … |
| **α** | **3** | 4 | 6 | 10 | 12 | 18 | 26 | 36 | 48（封顶） |

即"强度随 qp 推导"在 **qp ≤ 68 时被 floor 3 吸收**（α 恒 3、clip = α/2 = 1、
beta = 3——一个固定强度滤波器）。产品图片档全部落在死区：422-low/medium/high/
ultra 是 qp 63/61/58/58，raw12 是 45–70，只有 raw16 高档与 raw12-16 进生效区，
而 **RAW 又不带 bit2**（§3）。所以**图片链路的去块恒为 α=3**，任何强度旋钮
（`DB_STEP_*`、`DB_ALPHA_MAX`）在图片档上按定义无效——实测确认（4K 422-ultra，
改 `DB_ALPHA_MIN`/`DB_ALPHA_MAX` 后输出 SHA 完全相同）。

> 视频交付档走**码率控制**（`target_bpp` netproxy 0.29 / proxy 0.64 / lt 1.35 /
> standard 2.11 / hq 3.15，`qmatrix_id=4`），帧级 `qp_base` 由 RC 决出：低档
> （netproxy/proxy）会把 qp 推进 ≥ 70 的生效区，高档（standard/hq）落回 floor 3。
> 图片档是**固定 qp**（档位表即质量锚），故图片侧不存在"强度自适应"。

### 1.2 唯一没试过的杠杆：抬起 floor——实测是纯亏

用调参库把 α 抬到 6/8/12/20（qp 不动，4K 422-ultra 单帧，母版参照）：

| α | block_h / block_v（全尺寸） | Y PSNR | 边缘 PSNR | 预览 block_h / block_v |
| ---: | ---: | ---: | ---: | ---: |
| **3（现行 spec）** | 0.308 / 0.287 | **69.53** | 68.83 | 0.335 / 0.184 |
| 6–8 | 0.284 / 0.247 | 69.14（**−0.38**） | 68.78 | 0.124 / 0.162 |
| 12 | 0.257 / 0.187 | 67.38（**−2.15**） | 68.45 | −0.068 / 0.004 |
| 20 | 0.158 / 0.126 | 60.61（**−8.92**） | 65.13（−3.70） | −0.142 / −0.296 |

残余块界台阶（0.3 LSB）不是"没滤干净"，而是该档**真实量化台阶就那么大**：
在 69.5 dB（≈1 LSB 量化）的档位上把门控放宽 4×，滤掉的就不再是伪影而是信号
（`grid` 指标同步恶化 1.11 → 1.62，即块内结构被误伤）。**结论：α=3 的 floor
是正确工作点，没有免费空间。**

> 2K 同档位复验（α≈8）：Y PSNR 67.88 → 65.98（**−1.90 dB**）、block_h 0.233 →
> 0.145。档位越高（PSNR 越高、量化越细），抬 floor 的代价越大——与"高保真档的
> 残余台阶本来就是真实信号"一致。

### 1.3 生效区（低档）的强度也已到点

2K proxy（qp 落在生效区，α 当前 ≈ 48 封顶）同一码流扫参（`tools/sweep_topos_deblock.py`，
5 帧均值）：

| 设置 | block_h | block_v | Y PSNR | 边缘 PSNR |
| --- | ---: | ---: | ---: | ---: |
| 基线 α×2 | −0.2454 | −0.7606 | 38.040 | 34.430 |
| α×1.5 | −0.2288 | −0.7282 | 38.000 | 34.420 |
| α×1 | **+0.0674** | −0.5656 | 37.952 | 34.415 |
| α×3 | −0.2590 | −0.7046 | 37.990 | 34.420 |
| α×5 | −0.2704 | −0.7858 | **38.053** | 34.438 |
| spread=0 | −0.3474 | −0.8644 | 38.034 | 34.430 |

强度改 ±2.5× 只换来 ≤0.1 dB 与 ≤0.3 LSB，且方向互相抵消（提高 PSNR 的那端让
block 更负、反之亦然）。**过了门控的点上，强度已不是瓶颈。**

### 1.4 那就没有别的免费杠杆了吗

有，但都不满足用户约束，故不动：

| 杠杆 | 收益 | 代价 | 判定 |
| --- | --- | --- | --- |
| 编码端预算留白（`target_bpp` 0.7448） | Y PSNR +0.45 dB、台阶减半 | **文件体积 84.8% → 98%** | 与"体积不变"冲突，不做 |
| 真 SIMD（掩码/早退内核） | 解码吞吐（非画质） | 工程时间 | 归下一批（§5 of 视频文档） |
| GPU 滤波 | 预览块效应 | 实测省下的绝对量 < 一帧预算 4% | 按"不是远快就不做"，不做 |
| CLI 图片默认开 DEBLOCK | 图片块界台阶↓ 10–65% | **解码时间 +（滤波占 ~45%）** | 见 §2.4，需产品决策 |

## 2. `.toos` 图片链路核实：App 已吃到修复，CLI 没有

口径：`tools/compare_toos_deblock.py`，母版 `4K_prores4444.mov` 的 f240 经
`reformat` 到目标尺寸（与视频 A/B 同口径），编成图片档 `.toos` 后**只换解码库**；
`features=0` = CLI 等价（`reserved[5]=0`），`features=1` = App 路径等价
（`reserved[5]` bit0 → flags bit2）。**同一 coded payload**，故差异全部来自滤波。

### 2.1 全尺寸图片（三态：无滤波 / v2.0 / v2.1）

| 档位 | 指标 | 无滤波 | v2.0（门控 bug） | v2.1（现行） | v2.1−无滤波 |
| --- | --- | ---: | ---: | ---: | ---: |
| 2K 422-ultra | block_h / block_v | 0.233 / 0.243 | 0.245 / 0.206 | 0.224 / **−0.032** | −0.009 / **−0.275** |
| | Y PSNR | 67.883 | 67.873 | 67.810 | −0.073 |
| 2K 422-high | block_h / block_v | 0.299 / 0.183 | 0.237 / 0.154 | **−0.128** / 0.080 | **−0.427** / −0.103 |
| | Y PSNR | 55.100 | 55.100 | 55.098 | −0.003 |
| 4K 422-ultra | block_h / block_v | 0.353 / 0.351 | 0.349 / 0.347 | 0.308 / 0.287 | −0.045 / −0.064 |
| | Y PSNR | 69.720 | 69.694 | 69.525 | −0.195 |
| 4K 422-high | block_h / block_v | 0.475 / 0.502 | 0.458 / 0.488 | 0.318 / 0.306 | **−0.157** / **−0.196** |
| | Y PSNR | 60.650 | 60.647 | 60.625 | −0.025 |

要点：图片档的台阶绝对值本来就比视频交付档小一个量级（ultra 0.23–0.35 LSB vs
2K proxy 2.67/3.23），所以**全尺寸图片的改善幅度天然小于视频低档**（v2.1 相比
无滤波：block 降 10–65%）；Y PSNR 变化在 −0.20 ~ −0.003 dB（10-bit 域的
0.02% 量级），`sharp` 逐档不变（0.9946/0.9968 三态相同）——**没有以锐度换光滑**。

### 2.2 预览 / 缩略图（缩放交付，目标网格 unit=4）——图片侧最大受益点

| 尺寸 | 档位 | block_h 前 → 后 | block_v 前 → 后 | Y PSNR |
| --- | --- | ---: | ---: | ---: |
| 2K→960×540 | 422-ultra | 0.259 → **0.041** | 样本不足（nan） | 32.66 → 32.66 |
| 2K→960×540 | 422-high | 0.481 → **0.193** | 样本不足 | 32.69 → 32.69 |
| 4K→1920×1080 | 422-ultra | 0.764 → **0.335** | 0.513 → **0.184** | 36.03 → 36.03 |
| 4K→1920×1080 | 422-high | 0.851 → **0.447** | 0.418 → **0.209** | 36.06 → 36.06 |

这正是"预览里能看到小色块"的那条路径——图片链路的预览/缩略图（`decode_preview`
→ `tc_image_decode_preview` → 缩放交付）此前完全不过滤，v2.1 之后按目标网格过滤，
块界台阶减半以上而 PSNR 不变（抽样误差主导）。

### 2.3 "开位"的体积/速度代价：体积零、速度另计

同一帧 features=0 与 features=1 两次编码（2K 422-ultra）：

- 包长 **2600911 B vs 2600911 B（逐字节长度相同）**；4K 422-ultra 7013303 B 相同；
- 差异仅 **5 个字节，偏移 9 起，全部落在帧头（<128 B）**；偏移 128 之后两包
   **SHA-256 完全相同** ⇒ coded payload 逐字节一致 ⇒ **文件体积零影响**；
- 解码侧当然要付滤波时间（视频文档 §5 实测滤波 ≈ 45% 解码时间；图片链路同理，
  单帧绝对值 = 视频单帧的同一量级）。

### 2.4 CLI `toos encode` 的图片没吃到修复（实测）

- 源码：`native/topos_codec/src/cli/image_cli.c` 只设 `reserved[0]/[1]/[2]`，
  **从不设 `reserved[5]`** ⇒ flags bit2 = 0；App 图片导出则经
  `src/shared/export/topos_encoder.py:1182` + `_output_features()`（`:1095-1112`，
  域 = pf0 + 10-bit + profile 3）置位。
- 实测：真 CLI 产物 `/tmp/cli_still.toos`（`--tier 422-ultra`，2601236 B）在
  **前后两个库上解码 Y 平面 SHA-256 完全相同**（`5fc84ddb70220452…`）⇒ 无滤波。
- 这是一个**零体积代价**的可用杠杆（打开后图片块界台阶按 §2.1 下降），但它
  增加解码时间，与"不影响解码速度"的约束冲突 ⇒ **未改默认**，留产品决策。

> 注：App 的 4K 图片（`standard`/`hq`，宽 ≥3840）在置 bit2 之外还会置 QPT2
> （bit3）。QPT2 换细化量化表后 coded payload 与本文的 `features=1` 流不同，
> 但在 qp ≥ 45 两个表**逐值相同**（实测 `tc_qp_scale_tbl` 在 qp45/50/58/63 两表
> 相等）⇒ 去块强度 α 不变，本文的滤波结论照旧成立。

## 3. RAW：未受影响，且按设计不应受影响

### 3.1 结构性结论

RAW 是 `pf=3`（CFA 4 相位平面）+ `bit_depth∈{12,16}` → 帧头 `profile = 7`
（`codec.c` 的 `cfg_to_frame_header` 派生）。输出特性位有**三重域校验**：

- 位流侧：`frame_header.c` 要求 `major 7 + entropy_mode 7 + I + profile 3 + bd 10`
  才允许 flags bit2/bit3；
- 编码器侧：`codec.c:487-499` 要求 `profile==3 && pixel_format==0 && bit_depth==10`；
- 实测（编码器直接拒绝，消息即证据）：
  `reserved[5] output features 1 require profile 3 / 4:2:2 / 10-bit`。

即 **RAW 档位在物理上开不出 DEBLOCK**——不是"忘了开"，是域外。

### 3.2 字节级核实（合成 CFA，非真 DNG）

用母版 BT.709 limited → RGB → RGGB 相位下采样合成 CFA（pf=3 / 12-bit / profile 7 /
qm0 / transfer LOG0），三档编码后换库解码：

| 档位 | 2K 体积（比率） | 2K CFA PSNR | 4K 体积（比率） | 4K CFA PSNR | 前后库字节相同 |
| --- | ---: | ---: | ---: | ---: | :---: |
| raw12-2 (qp45) | 3.18 MB（1.30:1） | 110.32 dB | 11.67 MB（1.42:1） | 111.61 dB | ✅ |
| raw12-4 (qp59) | 2.27 MB（1.83:1） | 72.70 dB | 8.03 MB（2.07:1） | 72.72 dB | ✅ |
| raw12-8 (qp66) | 1.80 MB（2.30:1） | 62.65 dB | 6.18 MB（2.68:1） | 62.69 dB | ✅ |

> **口径警告**：源是合成 CFA（母版亮度/色度相位下采样），不是真传感器 DNG，
> 体积比率与 PSNR 都会比真素材乐观（真 DNG 标定见
> `tools/traw_batch4_2026-09-13.json`：4:1 档 3.0–6.2:1）。此表的用途只有一个：
> 证明 **RAW 解码输出与去块改动无关（逐字节相同）**。

### 3.3 为什么"顺手给 RAW 也开一下去块"是错的

CFA 的 4 个相位平面在空间上**不是相邻样本**（R/Gr/Gb/B 各自相隔 2 像素的采样
格），跨"相位平面内 8 周期边界"的台阶不是块效应而是**被误判的真实细节**：
对单相位平面做 8 周期平滑，等于在拜耳域抹掉 2 像素周期的纹理，再经 debayer
放大成彩色摩尔纹。RAW 的画质杠杆只有档位 qp（与编码端 debayer），没有滤波。

## 4. 复现

```bash
# 图片链路 A/B（同一 .toos 换库；含全尺寸 + 预览 + RAW 域校验）

  --old-lib /tmp/topos_prefix_wt/native/topos_codec/build/release/topos_codec.dylib \
  --new-lib native/topos_codec/build/release/topos_codec.dylib
# 旧库 = git worktree add /tmp/topos_prefix_wt 967219d8（6751dae9 的父提交）+ Release 构建

  --file tests/test_videos/2K_topos_422_Proxy.mov \
  --set "base:" --set "a50:DB_STEP_DEN=346112" --set "spread0:DB_SPREAD_SHIFT=0"

# 抬 α floor 的探针（图片档；旋钮经环境变量给 TC_DB_TUNE 库，工具自动 re-exec）
.venv/bin/python tools/compare_toos_deblock.py --size 4K --frame 240 \
  --old-lib native/topos_codec/build/tune/topos_codec.dylib \

```

## 5. 未做 / 待决

1. **CLI 图片是否默认开 DEBLOCK**：零体积代价、换块界台阶↓，但要付解码滤波
   时间（~45% 量级的解码开销）。与"不影响解码速度"冲突，未改；一句话决策即可动手。
2. RAW 侧的画质杠杆（档位 qp / 编码前 debayer 质量）与本次滤波改动无关，未动。
3. 预览采样器（视频文档 §4：整数纹理 NEAREST ⇒ 点采样）仍是预览观感的独立
   议题，超出本文范围。
