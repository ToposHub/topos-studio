# 4K/6K → 2K native target-size 解码测试（2026-09-08）

## 结论

当前降分辨率解码功能已经打通，输出确实是 2048×1080；但性能还不能称为成熟的“高分辨率素材按 2K 负载播放”。在本机、当前 Preview/YUV422/10-bit 配置下：

| 场景 | p50 解码耗时 | p50 解码帧率 | p95 解码帧率 | 相对原生 2K |
| --- | ---: | ---: | ---: | ---: |
| 原生 2K → 2K | 10.012 ms | 99.88 fps | 73.81 fps | 基线 |
| 4K → 2K | 39.185 ms | 25.52 fps | 25.12 fps | 帧率低 74.45%，耗时 3.91× |
| 6K → 2K | 78.493 ms | 12.74 fps | 10.74 fps | 帧率低 87.25%，耗时 7.84× |

这些是同一进程内 `ToposImageCodec` 的 native decode 调用，不包含 GPU 上传、色彩转换、调度和最终 present。因此它们比实际播放链路更乐观：4K→2K 虽然 p50 接近 25 fps，但加入播放管线后不能保证稳定 24/25 fps；6K→2K 明显达不到实时播放。

## 测试条件

- CPU：Intel Core i9-9900K，8 核 16 线程；内存 32 GiB；macOS 15.3.1。
- release native library，git `ea091fcf`，热缓存，native slice threads 使用默认值。
- 测试帧：确定性 mixed synthetic 内容；2K 为 2048×1080，4K 为 4096×2160，6K 为 6144×3240。
- 三者均为 Image Preview / YUV422 / 10-bit / VLC / QP58 / RDO off，目标输出统一 2048×1080。
- 每组预热 3 次、计时 20 次；FPS 按 `1000 / decode_ms` 计算。

## 工程判断

这证明了“只申请目标平面、按目标网格重建”的路径确实工作，但它仍需要顺序读取并熵解码整个 4K/6K 压缩包；下采样不能把源素材的解码复杂度直接变成 2K。下一步最高收益应是减少目标路径的全源块重建/标量采样成本，并进一步做跨帧批量解码和 SIMD，而不是继续放宽分辨率上限。
